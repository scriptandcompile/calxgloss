# KRAKEN's automation surface — one command registry, and the CLI / MCP / daemon / Python that hang off it

> Part of the [KRAKEN overview](README.md). The automation stack end to end: the
> command registry as the single definition of every operation, the `krakend`
> daemon that owns sessions and runs the commands, the `kraken-ipc` wire, the
> CLI as a generated clap tree with `--json`, the MCP server that turns each
> command into a tool, the PyO3 Python layer, and the generated JSON Schema +
> samples that pin the wire contract. Then the comparison against calxgloss's
> separate CLI + two-router web API, and the deliberate absence of an agent
> surface there. The edit log, undo and the GUI viewmodel were covered in
> [ch. 32](32-edit-log-undo-gui.md); engine internals in [ch. 31](31-analysis-engines.md).
> KRAKEN claims cite the clone at `68718c6`, paths relative to the clone root.

## What KRAKEN does

### 1. The registry: one Rust definition per operation (`kraken-registry`, 23,223 LOC)

Design doc 0003 is the charter: "Every operation is defined once in Rust… The
CLI (clap), MCP tools (rmcp), GUI command palette and the command reference in
these docs are generated from that definition"
(`docs/design/0003-one-command-registry.md:10-12`). One honesty note: 0003
names a `#[kraken_command]` proc macro, but no such macro exists in this
revision — commands are hand-written unit structs implementing a `Command`
trait, collected by one `register_all` call. The single-source property is
delivered anyway; the macro is simply not how.

The pieces, all in `crates/kraken-registry/src/command.rs`:

- **`CommandKind`** (`:19-30`): `Query` (reads, no side effects), `Mutation`
  (transactional edit logged under author + run), `Job` (returns a `job_id`;
  poll with `job_status`/`job_await`), `Stream`. **`Permission`** (`:33-41`):
  `Safe`, `Mutating`, `Dangerous` (always asks an `ApprovalRequester`).
- **`CommandSpec`** (`:44-63`): `name` (snake_case, unique), `summary`, a
  short `doc` that *is* the tool description a model reads (usage, argument
  advice, a worked `Example:` call — `:49-57`), a `details` field kept out of
  tool lists for the human reference only, plus kind, permission, and `needs:
  Vec<Cap>` — engine capabilities the command requires.
  `tool_description()` (`:98-104`) composes summary + doc for MCP and the
  built-in assistant alike.
- **The `Command` trait** (`:119-136`): associated `Args`/`Output` types that
  are `DeserializeOwned + JsonSchema` / `Serialize + JsonSchema`, a static
  `spec()`, and `async fn run(&self, s: &Session, ctx: &CallContext, args)`.
  `Registry::register` (`:280-291`) snapshots schemars-generated
  `args_schema`/`output_schema` (`:155-158`, `:163-166`) beside the type-erased
  handler, keyed by name in a `BTreeMap` (`:262-265`).
- **One call path, `Entry::call_json`** (`:202-249`), in fixed order:
  cancellation check → JSON args → engine-capability check
  (`Entry::available`, `:184-194`; unsupported calls answer `unsupported`) →
  approval gate when `permission == Dangerous` (`:225-243`; a denial is an
  `unsupported` error carrying `details.approval = "denied"`) → `run`, with
  engine errors passed through `ProtoError::sanitized` so binary-derived text
  in error strings stays sanitized.
- **`Session`** (`crates/kraken-registry/src/session.rs:1-7,24-31`): the unit
  of owned state — a project directory with `project.kraken.sqlite`, the
  engine's rebuildable cache dir, and `meta.json` (binary path + hash + cache
  epoch). Engines come from an injected `EngineFactory` (`:37-45`); the
  registry never depends on a concrete engine crate.
- **The mutation pipeline** (`crates/kraken-registry/src/mutate.rs:1-7,188`):
  every edit funnels through one `submit`: read-set, validation, agent
  classification (ch. 32), log append, engine push.
- **The job table** (`crates/kraken-registry/src/jobs.rs:1-17,26-60`):
  in-memory tokio tasks with `JobStatus` (running/succeeded/failed/cancelled),
  `JobProgress` (phase, done/total, engine step, elapsed ms), terminal jobs
  kept to 256. Cancellation is cooperative (`CancellationToken`); design 0003
  says commands can declare non-cancelable phases
  (`docs/design/0003-one-command-registry.md:20`).

The surface as generated: `cargo xtask docs` renders
`docs/reference/commands.md` straight from `Registry::standard()`
(`xtask/src/docs.rs:1`, `:12-28`), stamped "Generated by `cargo xtask docs`…
Do not edit by hand" (`docs/reference/commands.md:3`). Counted from that
file's table (`:13-92`): **78 commands — 47 query, 8 job, 23 mutation; 43
safe, 34 mutating, exactly 1 dangerous** (`patch_export`, `:52` — it writes a
patched copy of the binary, so it always asks). A quality gate keeps the
model-facing text honest: summaries ≤ 110 chars, every argument described,
each `Example:` line valid JSON with real argument names
(`crates/kraken-registry/tests/doc_quality.rs:1-10,58-68`).

There is **no per-command version field**. Surface identity is coarser: the
IPC `PROTOCOL_VERSION = 2` plus a build handshake — the daemon refuses a
mismatched client with "restart the daemon"
(`crates/kraken-ipc/src/wire.rs:8-10`, `crates/kraken-ipc/src/server.rs:327-331`;
`docs/design/0004-process-model.md:20`) — and machines introspect the exact
surface with `kraken commands --json`, which emits each command's spec, flag
projection and both JSON Schemas (`crates/kraken-cli/src/app.rs:483,902`).

### 2. One definition → CLI subcommand, MCP tool, GUI palette entry, Python call

| Surface | Projection of the same `Entry` |
|---|---|
| CLI | clap subcommand named `kebab-case` (`schema.rs:64-66`), `--flags` derived from the args JSON Schema (`crates/kraken-cli/src/schema.rs:1`), summary as `about`, `tool_description()+details` as `long_about` (`app.rs:390-430`) |
| MCP | one tool per command: snake_case name, `tool_description()`, args schema as `inputSchema`, output schema as `outputSchema`, annotations mapped from permission — safe→`read_only`, dangerous→`destructive` (`crates/kraken-mcp/src/tools.rs:16-37`) |
| GUI | command palette merges registry commands (`Backend::commands()`) with GUI-only app actions (`crates/kraken-viewmodel/src/palette.rs:8-26`) |
| docs | `docs/reference/commands.md`, generated (`xtask/src/docs.rs:26-28`) |
| Python | `conn.rs` calls the same names through the same backends (ch. 33 §6) |

The anti-drift mechanism is a *contract test*, not a comment: every registry
command runs through the CLI in `--json` mode and through an rmcp client
against an in-process `kraken-mcp`, and the output JSON must match
(`crates/kraken-cli/tests/contract.rs:1-3`); a second test pins three paths —
in-process, CLI→`krakend` over a real socket, and `kraken mcp --daemon`
routed through that daemon — as identical
(`crates/kraken-cli/tests/daemon_contract.rs:1-7`).

### 3. The daemon (`krakend`, 5,260 LOC) and the wire (`kraken-ipc`, 3,136 LOC)

`krakend` is the answer to design 0004's "something must own the project, the
log and the Ghidra process" (`docs/design/0004-process-model.md:10-14`): one
`Session` per canonical project directory, opened on demand, idle-closed per
session, at most `max_sessions` warm at once (LRU eviction), each with a
single ordered write queue for mutations and job starts
(`crates/krakend/src/host.rs:1-8`). Defaults: daemon idle 600 s, session idle
1800 s (`crates/kraken-host/src/config.rs:75-77`); the warm-project story is
the CLI's own help text — the daemon "is started on demand, keeps projects
and the Ghidra sidecar warm between invocations and exits when idle"
(`crates/kraken-cli/src/app.rs:39-41`); `start` takes a single-instance lock,
binds the socket and spawns the server, idle monitor, maintenance tick, event
forwarder and sidecar listener (`crates/krakend/src/daemon.rs:1-8`).

The wire, top down (`crates/kraken-ipc`):

- **Transport**: Unix domain socket or Windows named pipe
  (`src/transport/mod.rs:1-12`), bound in a per-user mode-0700 runtime dir
  with a deliberately short socket path (`src/paths.rs:7-14`; design 0004:23).
  *Not* the socketpair — that framing belongs to the engine sidecar, whose
  stdin *is* the channel (`CLAUDE.md:52`).
- **Auth**: 32 random bytes in a 0600 token file, constant-time compare
  (`src/token.rs:1-49`). The hello handshake carries a `ClientKind`
  (cli/gui/mcp) and yields a `CredentialClass` — `User` or `Agent` — derived
  *only* from the token presented, never from what the client claims
  (`src/wire.rs:15-34`). Agent-class connections share one quota
  (`crates/krakend/src/handler.rs:32`), can never approve anything, and are
  refused user-only methods.
- **Framing**: 4-byte big-endian length + UTF-8 JSON, 16 MiB cap, lower cap
  pre-auth (`src/frame.rs:1-6`); JSON-RPC 2.0 messages
  (`src/wire.rs:1-6`). Daemon methods: `call`, `commands`, `status`, `events`,
  `shutdown` (`crates/krakend/src/handler.rs:57`,
  `crates/kraken-host/src/daemon.rs:47`).
- **Approvals**: anything needing a person — a dangerous command, an agent
  opening a project — publishes an `approval_requested` event; the GUI shows
  a dialog, the CLI lists them (`kraken daemon approvals`), and a *user-class*
  connection answers `approval_decide`; no answer in 120 s is a denial, and at
  most 16 may be pending so an agent cannot bury the person
  (`crates/krakend/src/approvals.rs:1-9,26,30`).

**Jobs over this wire**: `analyze` returns `{job_id, already_running}` — a
second start joins the running job rather than duplicating work
(`crates/kraken-registry/src/commands/jobs.rs:42-65`); `job_status` shows
progress, `job_await` blocks with a `timeout_ms` early-return
(`:276-333`), `job_cancel` requests cancellation; edits made during analysis
queue and flush when it finishes. "Resume" is stage-and-cache granularity, not
mid-stage resume: analysis is staged with an engine save between stages, and
the cache epoch keyed by binary hash makes re-opens fast
(`docs/design/0004-process-model.md:27`; `crates/kraken-registry/src/session.rs:4-7`).

### 4. The CLI (`kraken-cli`, 13,757 LOC)

Every registry command is a clap subcommand; the tree is *built from the
registry* at startup (`app.rs:390-430`), flags generated from each command's
args schema with a small reserved set (`--help --version --json --project
--yes --args-json --no-wait`, `src/schema.rs:8-17`), objects and arrays passed
as JSON text, `--args-json` supplying the whole argument object
(`app.rs:418-424`). Scripting ergonomics (`docs/cli.md`): `--project` or
`KRAKEN_PROJECT` (`:7`); **`--json` makes stdout exactly the command's result
JSON, one line, progress on stderr, errors on stderr as JSON** (`:11`);
binary-derived text arrives wrapped `{"untrusted": true, "value": ...}` so
scripts read `.value` (`:31`); `--yes` pre-approves dangerous commands,
without them they are denied (`:41`); exit codes 0/2/3/4/5/6 map to
success/invalid/not-found/conflict-or-denied/unsupported-or-internal/
cancelled-or-timeout (`:43-53`). Author identity is either the OS user or an
explicit agent+run pair for scripts acting as agents (`app.rs:49-63`).

Where commands *run* is a `CommandBackend` seam — `LocalBackend` (in-process
session, the 0.1a path) or `DaemonBackend` (forward to `krakend`), both
returning "exactly the registry's output JSON, so a surface does not care
which one it has" (`crates/kraken-host/src/backend.rs:1-8`); the CLI starts
the daemon on demand and `--no-daemon` runs in-process (`app.rs:39-41`).

### 5. The MCP server (`kraken-mcp`, 2,734 LOC)

`kraken mcp` speaks MCP over stdio (`src/server.rs:337`). Tools: §2's mapping,
one per command, verified by a test that every standard command becomes a
tool with a non-empty description, object `inputSchema` and an
`outputSchema` (`src/tools.rs:44-74`). Dangerous commands are approved by MCP
*elicitation* — `McpApprover` asks the connected client's user and denies when
the client did not declare elicitation (`src/approval.rs:1-26`;
`docs/mcp.md:90`). `kraken mcp --project DIR` binds the server to a
human-chosen project and *removes* `project_create`/`project_open` from the
tool list, refusing them if called (`src/server.rs:32-44,218,288`) — agents
cannot roam the filesystem; unbound, project opening needs approval
(`docs/mcp.md:91`). Author = the client's name, one run id per connection
(`src/server.rs:75-79`). Default backend is the server process itself;
`--daemon` routes through `krakend` so the GUI can share the session and host
approvals (`src/lib.rs:16-19`).

**Token-budget discipline lives in the core commands, not in an MCP
projection**: page sizes capped at 500 (default 100) protocol-wide
(`crates/kraken-proto/src/page.rs:6-8`), `MAX_DECOMPILE_BYTES` 64 KiB, comment
4 KiB, name 200 chars (`crates/kraken-registry/src/validate.rs:7-11`),
`Untrusted` sanitization at the type level (`crates/kraken-proto/src/untrusted.rs:8-14`),
and the `doc`/`details` split plus the doc-quality caps that keep tool lists
small (`command.rs:49-57`; `docs/mcp.md:83`). Design 0003's sentence about a
surface applying "its own projection, such as an MCP token budget"
(`docs/design/0003-one-command-registry.md:18`) has no visible code-level
projection in this revision — the caps are enforced centrally.

Beyond tools: **6 prompts** (`getting-started`, `explain-function`,
`name-components`, `prepare-rewrite`, `analyze-binary`, `rewrite-program` —
`src/prompts.rs:54,245-269`; table in `docs/mcp.md:53-62`) that bundle rules +
live program context, and **read-only resources** (`kraken://project/summary`,
`kraken://gui/selection`, `kraken://function/{address}/decompile`,
`kraken://glossary…`, `docs/mcp.md:64-73`) — the "UI context is a resource,
not a command" rule of design 0003:24, made concrete by `gui_navigate` as the
routed intent (`docs/mcp.md:79`).

### 6. Python (`kraken-py`, 1,512 LOC)

A **PyO3 extension module, not a subprocess wrapper**: Cargo's `python`
feature pulls optional `pyo3 = 0.30` with `abi3-py310`
(`crates/kraken-py/Cargo.toml:16,30`); the native module `kraken._native` is
"thin wrappers" with arguments and results crossing the boundary as JSON text
so the unsafe-adjacent surface stays small (`src/py.rs:1-6`), every blocking
call releasing the GIL and honouring Ctrl-C
(`src/py.rs:18-21,47-50`). The Python-independent core is `conn.rs` —
connections either to `krakend` (found on `PATH` / `KRAKEN_KRAKEND`) or
in-process, with the same `Author::{User, Agent}` model
(`src/conn.rs:1-13,22-33`). `docs/python.md:1-8` positions it "in the spirit
of PyGhidra and IDAPython… a thin, typed layer over the same command
registry: whatever `kraken <command>` can do, a script can do, with the same
safety rules". Script edits are *user* edits with undo (`docs/python.md:44-46`).

### 7. The wire schema and its 53 samples

`kraken-proto` is the contract for the *engine-sidecar* wire (ch. 31):
`cargo xtask schema` regenerates `schema/kraken-proto.schema.json` from the
Rust types (`xtask/src/main.rs:50,118`; 66 `$defs`), and a test fails if the
committed file drifts (`crates/kraken-proto/src/lib.rs:157-165`).
`cargo xtask samples` writes exactly one JSON sample per top-level type and
variant to `schema/samples/` — 53 files — after a Rust round-trip assertion
per sample (`xtask/src/samples.rs:1-2,20-32`), deleting strays
(`xtask/src/main.rs:204-221`; stale-file test `xtask/src/samples.rs:577-588`).
Their consumer is Java: the Ghidra sidecar's `--self-test` parses and
re-serializes every sample as a wire-conformance check
(`java/kraken-ghidra/src/main/java/kraken/ghidra/KrakenSidecar.java:78`;
`Proto.java:12` "serializes to exactly the JSON the Rust types produce"), and
`cargo xtask ghidra-ext-test` feeds it the samples directory
(`xtask/src/main.rs:257`). Note the scope: samples pin the *engine* contract;
the 78 command args/results are schemas-on-demand (schemars at register time,
surfaced by `commands --json` and MCP `inputSchema`/`outputSchema`), not
committed files.

## Drift KRAKEN prevents, and the seams that remain

Prevented: one registry kills the command-list drift (docs, CLI help, MCP
tool list, `commands --json` all regenerate), the contract tests kill output
divergence across backends, the handshake kills client/daemon version skew,
the schema/sample freshness tests kill Rust↔Java wire skew, and the
doc-quality tests keep model-facing text honest. What still drifts is small
and telling: (1) the `kraken-mcp` crate doc lists four prompts
(`src/lib.rs:21-22`) where `prompts.rs` now serves six — a stale doc comment
*inside* the crate whose whole point is generated single-sourcing; (2) design
0003's `#[kraken_command]` macro does not exist (hand-written `spec()`s are
the reality); (3) the CLI has non-registry conveniences — `explain`,
`overview`, `auto-name`, `glossary`, `auto`, `daemon status|stop`, `setup`,
`eval` — that live only on that surface (`docs/cli.md:58-66`); (4) the GUI
palette carries app actions with no registry command behind them
(`palette.rs:8-26`); (5) in 0.1a the MCP default holds its own session, so an
MCP agent and the GUI do not share state unless both use `--daemon`
(`src/lib.rs:16-19`; `docs/design/0004-process-model.md:31`).

## calxgloss comparison

calxgloss's automation surface (baseline §Automation,
`docs/research/kraken/10-calxgloss-baseline.md:198-233`, all re-verified in
repo): **29 CLI subcommands**, one hand-written clap enum
(`crates/interface/calxgloss-cli/src/cli_types.rs:196-1048`; counted 29
variants); **33 web routes in two tables** — `shared_routes()` at
`crates/interface/calxgloss-web/src/server/mod.rs:863` (26 route registrations,
answered from persisted artifacts everywhere) and `live_only_routes()` at
`:1040` (7: `/api/progress*`, WebSocket, pipeline control) — by ADR-0002
(`docs/adr/0002-two-router-web-api-with-progress-records-in-calxgloss-types.md`);
pipeline control as a shared state machine over REST, live-only (ADR-0004,
`docs/adr/0004-pipeline-control-shared-state-machine-over-rest.md:1`); views
read-only over artifacts (ADR-0006, `docs/adr/0006-web-views-read-only-over-existing-artifacts.md:1`).
**No `--json` flag** — the global CLI flags are only verbose, log-format,
config, target-dir, workspace (`cli_types.rs:16-46`); **no daemon** — `live`
and `serve` are foreground processes (`10-calxgloss-baseline.md:216-217`);
**no Python, no IPC, no MCP** (`:217-218`, and re-grepped this pass: nothing).

| Axis | KRAKEN | calxgloss |
|---|---|---|
| Command definition | 78 commands, one registry; docs/CLI/MCP/GUI/Python generated (`commands.md:3`; `contract.rs:1-3`) | ~29 CLI + 33 REST routes + SPA, three separately-written surfaces over shared `calxgloss-types` records (ADR-0002) |
| Machine-readable output | `--json` = exact result JSON; `commands --json` introspects every schema (`docs/cli.md:11,31`) | none; prints human-formatted; JSON is roadmap, not shipped (`10-calxgloss-baseline.md:214-215`) |
| Session ownership | `krakend` owns warm sessions + sidecars; any client starts it; idle exit 600 s (`host.rs:1-8`; `config.rs:75-77`) | cold process per invocation; warm state only inside `live`, deliberately foreground |
| Long work | job table, `job_status`/`job_await`/`job_cancel`, MCP progress notifications (`commands/jobs.rs:276-333`; `kraken-mcp/src/lib.rs:5-7`) | progress records in `calxgloss-types` (`crates/shared/calxgloss-types/src/lib.rs:23-24`) + live-only REST/WS (ADR-0002) |
| Agent access | 78 MCP tools + 6 prompts + resources, credential classes, approval board, per-run agent quota (`krakend/src/approvals.rs:1-9`; `handler.rs:32`) | deliberately none — LLM works *inside* the pipeline through seam prompts only; "no MCP server or any MCP surface" verified in baseline §AI; ADR-0051 makes the attempt one seam |

**Why each fits its mission.** KRAKEN is an interactive workbench where
several clients — a person in a GUI, a terminal, and agents — co-edit *one
live session*: the daemon must own state, and one registry is load-bearing
because the same operation must be checkable wherever it arrives, with the
approval board routing "the MCP server runs under the agent's control and
cannot vouch for you" (`docs/mcp.md:90`). calxgloss is an unattended factory:
its "agent" is the pipeline's own LLM call, already fenced by compile +
baseline-test verification (ADR-0051), and the human steers at run/queue/
verdict granularity over a read-only web view (ADR-0006). An MCP surface
would let an external agent bypass the verification gate by editing
interactively — the exact thing the pipeline exists to prevent. The
run-equals-`--show` report identity (ADR-0054,
`docs/adr/0054-the-seam-admission-line-is-a-run-path-only-exemption-to-the-run-equals-show-report-identity-because-capability-is-live-session-state-not-a-filed-document.md:1`)
is the anti-daemon theorem in miniature: calxgloss results are filed
documents re-read cold, not warm session state, so a `krakend` would add a
second source of truth it already legislated away. calxgloss's own drift
risk sits between its hand-written surfaces, and it mitigates the biggest
instance exactly KRAKEN-style: each of the 15 scan commands rides one
registry descriptor row, and ADR-0052 records that the hand-written twins
"could drift; they already had once"
(`docs/adr/0052-one-cli-scan-command-rides-the-registrys-descriptor-rows-each-engine-contributes-one-cli-side-entry-engine-loading-folds-into-the-generic-command-and-force-rescan-rides-the-overwrite-policy.md:15-25`;
table at `crates/pipeline/calxgloss-translator/src/scan_registry.rs:606-624`).

### Steal

1. **`--json` from the same definition as the help text.** calxgloss's clap
   enum already carries the full doc corpus (`cli_types.rs:198-1047`);
   KRAKEN's lesson is that the *result* type, not the printer, should carry
   the machine shape — `--json` printing exactly the `Verify`/scan report
   struct's serde JSON, one line, progress on stderr (`docs/cli.md:11`).
2. **A generated command reference from the clap enum + ADR-0052 rows.**
   KRAKEN's `cargo xtask docs` stamp ("Do not edit by hand",
   `docs/reference/commands.md:3`) is cheap insurance for calxgloss's
   hand-maintained command docs; the descriptor table already names every
   scan command and its document path.
3. **Size caps as protocol constants.** KRAKEN's `MAX_PAGE_LIMIT = 500` /
   default 100 (`page.rs:6-8`) and the byte caps for large text (`validate.rs:7-11`)
   are the discipline calxgloss's evidence bundles want — bundle sections fed
   to prompt templates have no cap today (ch. 32 §steal-2 overlaps here).

### Confirm

Record-level sharing of a *data* contract across surfaces (`calxgloss-types`,
ADR-0002) is calxgloss's version of the same instinct as the registry — same
output shape to CLI, dashboard and stored records; keep it.

### Don't copy

The daemon (conflicts head-on with cold runs + run-equals-`--show`); the MCP
server and any external-agent surface (ADR-0051's seam-only admission is the
safety model); the 78-command per-address edit vocabulary (calxgloss steers
at unit level); the `CommandSpec` metadata layer over hand-written enums
(29 commands × 1 enum is still readable — ADR-0052 fixed the duplication that
actually hurt).
