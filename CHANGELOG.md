## [Unreleased]

### Added

#### Output directory structure

- **Crate-based output layout** — `translate` and `batch-translate` now produce `crates/<dll_stripped>/Cargo.toml` and `crates/<dll_stripped>/src/<function>.rs` (one file per function) instead of the previous `src/modules/<function>/translated.rs` layout. The DLL/EXE extension is stripped (e.g. `EqGame.exe` → crate `EqGame`). Each crate has a `Cargo.toml` and a `mod.rs` auto-generated in `src/` that registers every translated function as `pub mod <function>;`.

#### Context tier selection

- **`ContextTier` enum** (`calxgloss-types::context_tier`) — five tiers (`Stub`, `Disassembly`, `WithTests`, `ModuleContext`, `FullModule`) defining the context scope sent to the LLM per function. Each tier is a superset of the previous.
- **`select_context_tier()`** — selects the starting tier from function complexity classification and API call count. Historical success rate tracking is reserved for a follow-up.
- **`SuccessRate` struct** — tracks past success/failure counts for tier selection optimization.
- **`ProgressEvent::ContextTierSelected`** — emitted after complexity analysis with the selected tier label, complexity classification, and API call count.
- **`Translation.context_tier`** — new field recording which tier was used for each translation, enabling token usage tracking and future tier optimization.
- **Tier 0 stub prompt** — minimal context prompt that sends only the function name, inferred C signature, and call graph neighbors (no disassembly, no decompiler output). Reduces token usage for trivially simple functions.
  - `StubPromptData` struct with `from_function_info()` constructor
  - `StubTemplate` Askama template struct
  - `build_stub_prompt()` convenience function
  - `extract_signature_from_decompiler()` helper that parses the first non-blank line of Ghidra decompiler output as the C signature
  - Template `stub_translate.j2` renders the minimal prompt format
  - `TranslationPipeline::translate()` routes to stub prompt when `ContextTier::Stub` is selected
- **Tier 1 disassembly prompt** — sends full disassembly, Ghidra pseudo-C decompiler output, tagged Windows API calls, and call graph neighbors (no baseline tests, which are reserved for Tier 2). Reduces token usage over the full complexity prompt while preserving ground truth for accurate translation.
  - `DisassemblyPromptData` struct with `from_function_info()` and `from_request()` constructors
  - `DisassemblyTemplate` Askama template struct
  - `build_disassembly_prompt()` convenience function
  - Template `disassembly_translate.j2` renders disassembly, decompiler output, API mappings, call graph neighbors, external function handling rules, and translation requirements
  - `TranslationPipeline::translate()` routes to disassembly prompt when `ContextTier::Disassembly` is selected
  - Module docs updated to document all tier-specific prompt builders
- **Tier 2 with-tests prompt** — sends full disassembly, Ghidra pseudo-C decompiler output, tagged Windows API calls, call graph neighbors, and baseline test results with pass/fail status and error details. Enables the LLM to match concrete behavioral output on initial translation or fix specific failures on retry.
  - `FormattedTestResult` struct with `from_baseline()`, `from_baseline_with_failure()`, and `from_baseline_passing()` constructors
  - `WithTestsPromptData` struct with `from_request()` and `from_request_with_results()` constructors
  - `WithTestsTemplate` Askama template struct
  - `build_with_tests_prompt()` convenience function
  - Template `with_tests_translate.j2` renders function metadata, test summary, disassembly, decompiler output, tagged APIs, call graph neighbors, baseline test results with PASSED/FAILED markers and error details, external function handling rules, translation requirements, and example output format
  - Template handles empty test results gracefully with fallback text when no tests are available yet
  - `TranslationPipeline::translate()` routes to with-tests prompt when `ContextTier::WithTests` is selected
 - **Tier 3 module context prompt** — sends full disassembly, Ghidra pseudo-C decompiler output, tagged Windows API calls, call graph neighbors, baseline test results with pass/fail status, full neighboring function context (disassembly + pseudo-C for each neighbor), and shared data structure definitions (fields, types, byte offsets). This tier is used for complex functions whose translation requires understanding shared calling conventions, data layouts, or helper patterns from adjacent functions in the same module.
   - `ModuleContextPromptData` struct with `from_request()` and `from_request_with_context()` constructors
   - `ModuleContextTemplate` Askama template struct
   - `build_module_context_prompt()` convenience function
   - Template `module_context_translate.j2` renders function metadata, test summary, disassembly, decompiler output, tagged APIs, call graph neighbors, baseline test results with PASSED/FAILED markers and error details, full neighboring function context (disassembly + pseudo-C for each neighbor), shared data structure definitions (name, size, fields with types and offsets), external function handling rules, and translation requirements
   - Pipeline fetches neighboring function code and data structures from Ghidra via `extract_call_graph_neighbors()`, `extract_neighboring_context()`, and `extract_data_structures()` helpers when `ContextTier::ModuleContext` is selected
 - **Tier 4 full module prompt** — sends everything from Tier 3 plus shim layer source code for crate-replacement DLLs and PAL trait definitions for platform abstraction. This tier is used when translating functions that call through shim layers (e.g., DirectX → wgpu) and need the full translation-layer context including shim source and PAL trait interfaces to map correctly.
    - `FullModulePromptData` struct with `from_request()` and `from_request_with_full_context()` constructors
    - `ShimCode` struct — represents a generated shim layer (source DLL, target crate, mapping count, full Rust source)
    - `PalTraitDef` / `PalTraitMethod` structs — represent PAL trait definitions with method signatures, used to abstract platform-specific APIs
    - `FullModuleTemplate` Askama template struct
    - `build_full_module_prompt()` convenience function
    - Template `full_module_translate.j2` renders function metadata, test summary, disassembly, decompiler output, tagged APIs, call graph neighbors, baseline test results, full neighboring function context, shared data structures, shim layer source code blocks, PAL trait definitions with method signatures, external function handling rules, and translation requirements
    - Pipeline fetches shim layers from `re/shims/<dll>/shim.rs` in the workspace and PAL traits from the function's Windows API categories when `ContextTier::FullModule` is selected
    - Exhaustive match on all `ContextTier` variants (unreachable `_` catch-all removed)
- **Automatic context tier escalation** — when `escalate_on_failure` is enabled and a retry attempt fails, the tier is automatically bumped to the next level and a new prompt is built with escalated context. Escalation happens independently of strategy escalation. `ContextTierSelected` progress events are emitted when the tier changes. A `build_escalated_prompt()` helper reconstructs the appropriate prompt for any tier using the initial translation's data, fetching additional Ghidra/workspace context (neighboring functions, data structures, shim layers, PAL traits) for Tiers 3–4. Tier-escalated attempts are labeled `escalated(<tier_label>)` in progress events and attempt records. Failed tier escalation gracefully falls back to the strategy-based prompt.

#### Fault detection

- **Fault types** (`calxgloss-types::fault`) — `FaultCategory` (7 categories: `ContextWindowExceeded`, `Hallucination`, `InfiniteLoop`, `BehaviorDivergence`, `ResourceExhaustion`, `SlowResponse`, `PromptCorruption`), `FaultSeverity` (Warning/Error/Critical), `ContextWindowFault` (with truncation signal detection and suggested chunk count), `FaultEvent` (with factory constructors for context-window and hallucination faults), `FaultLog`, and `FaultStats` (aggregate statistics with serde serialization). Full test suite with serialization round-trips.
- **Context-window detector** (`calxgloss-llm::context`) — `ContextWindowDetector` checks LLM response size vs. model limit, scans for common truncation markers (Ollama, vLLM, llama.cpp, GPT), and pre-checks prompt size. `FunctionSplitter` divides disassembly into equal-sized chunks with metadata for the LLM. 13 unit tests.
- **Hallucination detector** (`calxgloss-llm::hallucination`) — `HallucinationDetector` cross-references LLM-generated code against Ghidra symbols (functions + imports) and the PAL API catalogue. Extracts function-call patterns from generated Rust, filters Rust keywords and standard-library type constructors as false positives, and reports non-existent API references with close-match suggestions. 21 unit tests.
- **`TranslationPipeline::with_hallucination_detector()`** — builder method to attach a pre-built detector; `hallucination_detector` field is `Option` so unit tests can construct the pipeline without a runtime. `build_hallucination_detector` exported as `pub async fn` for callers to initialize before pipeline construction.
- **Fault logger** (`calxgloss-analysis::fault_log`) — `FaultLogger` persists `FaultEvent` instances to `re/analysis/fault_log.json` with automatic directory creation, corrupted-file recovery, and `compute_stats()` aggregation. 7 unit tests.
- **Infinite-loop detector** (`calxgloss-llm::infinite_loop`) — `InfiniteLoopDetector` tracks `(prompt_hash, output_hash)` pairs across retry attempts. When the same bad output repeats three or more times in a row (configurable threshold, default 3), `detect()` returns an `InfiniteLoopSignal` with streak details. The detector fires before wasting tokens on a dead-end path. 15 unit tests + 1 doctest.
- **Behavior-divergence detector** (`calxgloss-llm::behavior_divergence`) — `BehaviorDivergenceDetector` identifies when a Rust implementation passes all baseline tests but fails on edge-case inputs not covered by the baseline suite. Generates targeted edge-case tests from disassembly hints (zero checks, null checks, overflow, negative values), compares results, and emits signals with confidence scoring and actionable recommendations. 36 unit tests.
- **`disassembly_hints` field** — added to `FunctionInfo` (with `#[serde(default)]` for backward compatibility) and `Translation`; propagated through all construction sites in `calxgloss-translator`, `calxgloss-analysis`, and `calxgloss-cli` to feed edge-case test generation.
- **Behavior-divergence detection integrated into retry loop** (`calxgloss-translator::retry`) — `try_translate_with_retry()` now runs the behavior-divergence detector after each successful compilation pass, emitting `ProgressEvent::BehaviorDivergenceDetected` when baseline/edge-case results diverge.
- **`FaultEvent::infinite_loop()`** — new factory constructor producing a `FaultCategory::InfiniteLoop` event with severity `Critical`, streak count, and streak attempt range.
- **`FaultEvent::behavior_divergence()`** — new factory constructor producing a `FaultCategory::BehaviorDivergence` event with severity `Warning` (confidence ≥ 7) or `Error` (confidence < 7), confidence score, and actionable recovery advice.
- **`ProgressEvent::InfiniteLoopDetected`** — new event emitted when the infinite-loop detector fires, carrying `dll`, `function`, `streak`, `streak_start_attempt`, `streak_end_attempt`, and `strategy` fields.
- **`ProgressEvent::BehaviorDivergenceDetected`** — new event emitted when the behavior-divergence detector fires, carrying `dll`, `function`, `attempt`, `strategy`, baseline/edge-case pass/fail counts, failing edge-case labels, and a confidence score.
- **Resource exhaustion monitoring** — `ResourceExhaustionDetector` with sliding-window failure tracking, streak detection, and configurable thresholds. Detects when the local LLM model is overloaded (OOM, swap thrash, too many concurrent requests) or requests time out. Integrates with `LlmClient::complete()` to catch HTTP 429/503/507 as `LlmError::ResourceExhausted`. Retry loop records failures, emits `ResourceExhaustionDetected` progress events, logs to the fault logger, and provides `should_queue_work()` / `should_switch_model()` helpers. 11 unit tests.
- **`ProgressEvent::ResourceExhaustionDetected`** — new event emitted when the resource-exhaustion detector fires, carrying `dll`, `function`, `attempt`, `strategy`, reason, elapsed seconds, and recommended backoff time.

#### `calxgloss-types`
- **Token usage types** (`calxgloss-types::token_usage`) — `TokenUsageEntry` (per-attempt token count with DLL, function, attempt number, strategy, and success status), `TokenUsageLog` (collectible entries with serde), `TokenUsageStats` (aggregate totals with per-DLL breakdown into `DllTokenStats`), and `current_timestamp()` helper. Full test suite with serialization round-trips.
- **Token usage with context tier tracking** — `TokenUsageEntry` now carries a `context_tier` field (serialized only when non-empty) and a `new_with_tier()` constructor. `log_token_usage()` accepts and persists a tier label alongside token counts. All retry loop code paths (initial, strategy-based, tier-escalated, resource exhaustion, empty code) log their tier with token counts to `re/analysis/token_usage.json`.
- **`Confidence` evidence score** (`calxgloss-types::confidence`) — a shared 0–100 confidence score for recovered and inferred findings, replacing the bare `u8` restated at each site. Clamped to `0..=100` on construction, `#[serde(transparent)]` so persisted documents keep the bare-number shape, comparable directly against bare `u8` numbers so detector thresholds stay plain, and convertible to/from `u8`. The 0–10 diagnosis scores in `fault.rs` and `progress.rs` are a separate scale and deliberately stay `u8`. 5 unit tests.
- **`ScanMetadata` scan provenance** (`calxgloss-types::scan`) — the per-binary scan provenance (binary name, finish timestamp, scan duration) every persisted scan artifact carries, plus the `now_unix_secs()` helper, moved out of `calxgloss-typesdb` so each engine crate keys its artifacts with the same shape instead of forking its own copy. 2 unit tests.

#### `calxgloss-typesdb`
- **Type database document and persistence** — `types.rs` gained `TypeDatabase` (the per-binary document: named types in Type Manager path order, vtables in address order, inferred candidates confidence-first; empty sections are omitted from the JSON) and `ScanMetadata` (binary name, finish timestamp, scan duration), with `find_named_type`/`find_vtable` lookups keyed on the stable identities — paths and addresses, since type names repeat across categories. `persist.rs` implemented `TypeDatabasePersistor`: `new(workspace)` files one pretty-printed JSON document per binary under `re/analysis/typesdb/`, `with_cache_dir` points at an explicit directory, `exists()` is the cache check that gates a rescan, and `load()` surfaces a missing file as the new `TypesDbError::NotFound` and a corrupt document as `Json`; a rescan replaces the previous document. 10 unit tests.
- **Recovery orchestration** — `engine.rs` gained `TypesDBEngine` (generic over the same source traits as the scanners it drives; `with_source` constructors let tests run the whole flow over canned responses): it runs the three recovery scans concurrently — their endpoint sets are disjoint — and assembles one `TypeDatabase` stamped with scan provenance; a server failure mid-scan aborts the run rather than returning sections built against different programs. Configuration (`with_category`, `without_tagging`, `with_string_filter`, `with_min_confidence`, `with_min_fields`, `with_pointer_size`) reaches through to the right scanners. 5 unit tests + 10 integration tests (`tests/integration_tests.rs`, no server needed: scan → save → load round trip, workspace file layout, cache gating, rescan replacement, path/address lookups with layouts/methods/RTTI/evidence intact, and prompt rendering of a named struct, an enum, and an inferred candidate).
- **Prompt conversions** — recovered records convert into prompt data: `From<&NamedType>` and `From<&InferredStruct>` render a `calxgloss_prompts::StructuredData` — structure fields keep their offsets, enum members arrive as fields whose type is the member value at unknown offset (`-1`), and inferred fields carry the suggested C declaration. typesdb gained a `calxgloss-prompts` dependency for the target type. 4 unit tests.
- **String-guided struct inference** — `types.rs` gained `InferredStruct`, `InferredField`, `FieldType` (string/integer/float/boolean/unknown, each with a suggested C declaration and size), and `NameOrigin` (literal prefix / function stem / address), all `Serialize`/`Deserialize`. `string_infer.rs` gained `StringInferenceEngine` (generic over a `StringSource` trait so unit tests run canned; `GhidraClient` implements it) with `infer_structures()`: collects the `list_strings` listing through a quality screen (length bounds, format strings/paths/prose/non-ASCII rejected, deduped by value), fetches one `get_xrefs_to` read per literal, and unions literals through their referencing functions — hub functions pointing at 24+ literals are skipped so a logging call cannot merge unrelated objects. Each cluster becomes a candidate: the shared qualifier (`player.x` → `Player`) or the shared function stem (`Widget_getSize` → `Widget`) names the struct, the literals name the fields, `key=value` shapes type them, offsets accumulate on 4-byte boundaries, and a 0–100 confidence score (breadth, function agreement, naming origin, name cleanliness) filters against a configurable threshold (`with_min_confidence`, default 40). Unreadable xrefs degrade one literal; a listing or server failure aborts the run. 23 unit tests (20 engine + 3 model) + 3 live tests, verified live against the v6.0.0 bridge with `eqmain.dll` open: candidates inferred from the 1,812 defined strings, and eqmain's startup-flow field list (`startupflow`/`flowname`/`screen`/`nextflow`/…, all read by `FUN_18000b620`) recovered as one candidate.
- **Vtable detection** — `types.rs` gained `Vtable` and `VtableMethod` (`Serialize`/`Deserialize`, keyed by address since Ghidra names every MSVC vtable `vftable`); a table paired with a preceding `vftable_meta_ptr` entry is RTTI-confirmed (`is_confirmed()`). `vtable.rs` gained `VtableDetector` (generic over a `VtableSource` trait so unit tests run canned; `GhidraClient` implements it) with `detect_vtables()`: scans the paged `list_data_items` listing for `vftable` items, reads each table's bytes via `read_memory` to resolve method pointers to function names and addresses (element size from the declared `pointer[N]` count), walks the MSVC RTTI chain — metadata pointer → CompleteObjectLocator → TypeDescriptor and ClassHierarchyDescriptor, x64 RVAs resolved against the image base — to demangle the owning class (`.?AVUdpRefCount@UdpLibrary@@` → `UdpLibrary::UdpRefCount`) and recover base classes, flags COM interfaces by the QueryInterface/AddRef/Release slot prefix, and tags confirmed methods with `add_function_tag` (`without_tagging()` for read-only scans). RTTI/read misses degrade one vtable to method-pointer fidelity; a listing failure aborts the scan. 18 unit tests (16 detector + 2 model) + 2 live tests, verified live against the v6.0.0 bridge with `eqmain.dll` open: 50+ vftables detected, all RTTI-confirmed, class names and base classes recovered.
- **Named type recovery** — `types.rs` gained `NamedType`, `TypeKind` (struct/class/union/enum/typedef/other), `StructField`, and `EnumMember`, all `Serialize`/`Deserialize`, keyed by Type Manager path (names are not unique). `scanner.rs` gained `TypeLibraryScanner` (generic over a `TypeLibrarySource` trait so unit tests run canned) with `scan_named_types()`: it lists the Type Manager, fetches one `category`-filtered listing per kind word to bucket types, confirms structs/enums with `get_struct_layout`/`get_enum_values` probes, and degrades probe misses (`NotFound`/`Malformed` prose sentinels) to listing-only records while aborting on server failures. Pointer/array/builtin/demangler entries are skipped; results sort and dedup by path. Verified live against the v6.0.0 bridge: its `category` filter matches the word as a case-insensitive substring against the category name **or** the type's classification, so bucket membership whose category name also contains the kind word is marked suspect and probed, and certain (classification-only) memberships are trusted first — a typedef in a category named e.g. `unions` would otherwise be recorded as a union. 20 unit tests + 4 live tests (`tests/live.rs`, `#[ignore]`d), all passing with `eqmain.dll` open.
- **New crate: data structure recovery** — scaffolded `calxgloss-typesdb` as a workspace member. Module skeleton: `types`, `scanner`, `vtable`, `string_infer`, `persist`, `error`. `TypesDbError` (thiserror) with `Ghidra`/`Io`/`Json`/`EmptyTypeName`/`ScanFailed` variants plus a crate-wide `Result` alias. Dependencies wired for the recovery engines (`calxgloss-ghidra`, `calxgloss-types`, `serde`, `serde_json`, `tokio`, `tracing`, `thiserror`, `regex`; unused-dependency lint allowed until the engines land, same as `calxgloss-web`). Re-exported from the `calxgloss` meta-crate.

#### `calxgloss-ghidra`
- **Auto-paged string listing** — new `GhidraClient::list_strings()` collects the whole `list_strings` listing across `offset`/`limit` pages (a program holds thousands of defined strings; reasoning over them — clustering the ones a function shares into candidate structs — needs the full listing, not a window), and `strings_page()` exposes one windowed page directly. The existing `strings()` keeps its single-window behavior, now served through `strings_page()`. 1 new live test, passing against the running bridge with `eqmain.dll` open.
- **Raw memory reads and function tagging** — new `GhidraClient::read_memory()` returns the raw bytes at an address (the `data` array of the bridge's `read_memory` response, parsed by `parse_memory_bytes`; a prose sentinel or an out-of-range byte makes the whole response untrustworthy) — the only way to see a defined data object's contents, e.g. a vtable's method pointers or an RTTI locator. New `add_function_tag()` POSTs a JSON body to attach a tag to a function by address or name (the tag is created on demand; a data address is refused). GET and POST now share a `deliver()` transport helper. 1 new parser unit test + 1 new live test, passing against the running bridge with `eqmain.dll` open.
- **Type Manager and defined-data client wrappers** — new `GhidraClient` methods for the bethington bridge's type/data endpoints: `list_data_types()` (category filter, auto-paged) and `data_types_page()`, `get_struct_layout()`, `get_enum_values()`, `list_data_items()` (auto-paged) and `data_items_page()`. New model types `DataTypeEntry`, `DataItem`, `StructLayout`/`StructFieldLayout`, `EnumDefinition`/`EnumMember` with parsers written against live-captured v6.0.0 responses — these endpoints answer `text/plain`, not JSON, and misses arrive as prose sentinels (`Structure not found: X`) that surface as `GhidraError::NotFound`. 8 new parser unit tests + 4 new live tests, all passing against the running bridge with `eqmain.dll` open.

#### `calxgloss-cli`
- **`typesdb` command** — `calxgloss typesdb --dll <dll>` recovers the per-binary type database on demand: it runs `TypesDBEngine::scan` against the program currently open in Ghidra and saves the result to `re/analysis/typesdb/<dll>.json` in the workspace — the same file batch translation's pre-processing reads, so a manual scan seeds (or rebuilds) the cache the pipeline consumes. `--show` prints a cached database without connecting to Ghidra: file location, scan timestamp and duration, named-type counts broken down by kind, a vtable table with RTTI/COM confirmation and base-class notes, and inferred struct candidates with confidence coloring, each section collapsing past ten entries. `--no-tag` runs the vtable scan read-only, skipping the `vtable-method` tag write-back. Like `config` and `gc`, the command is exempt from the `target_dir` requirement — it reads the open Ghidra program and writes to the workspace. Verified live against the running bridge with `eqmain.dll` open: 300 named types, 73 RTTI-confirmed vtables, and 38 inferred candidates recovered in 52s; `--show` re-reads the saved file, and a missing cache fails with a message pointing at the recovery command.
- **`typeinfer` command** — `calxgloss typeinfer --dll <dll>` infers parameter types on demand: it runs `TypeInferEngine::scan` against the program currently open in Ghidra and saves the result to `re/analysis/typeinfer/<dll>.json` in the workspace — the same file batch translation's pre-analysis reads, so a manual scan seeds (or rebuilds) the cache the pipeline consumes. `--show` prints a cached result without connecting to Ghidra: file location, scan timestamp and duration, inference counts broken down by record kind, a per-detector-method breakdown (wrapping onto continuation lines when the seven methods all show up), top confidence, and an inference table naming each target — parameter, local variable, or call-site argument — with its narrowed type and confidence colored by score beside the method behind it, collapsing past ten entries. Like `config`, `gc`, and `typesdb`, the command is exempt from the `target_dir` requirement — it reads the open Ghidra program and writes to the workspace.

#### `calxgloss-typeinfer`
- **New crate: type inference and propagation** — scaffolded `calxgloss-typeinfer` as a workspace member. Module skeleton: `types`, `this_ptr`, `param_size`, `known_type`, `confidence`, `persist`, `error`. `TypeInferError` (thiserror) with `Ghidra`/`Io`/`Json`/`EmptyFunctionName`/`ScanFailed` variants plus a crate-wide `Result` alias. Dependencies wired for the inference detectors (`calxgloss-ghidra`, `calxgloss-types`, `serde`, `serde_json`, `tokio`, `tracing`, `thiserror`, `regex`; unused-dependency lint allowed until the detectors land, same as `calxgloss-typesdb`).
- **Inference record model** — `types.rs` gained `InferredParamType` (function, parameter position and name, narrowed C type, method, scope, 0–100 confidence, and the supporting decompiled line as evidence), `InferenceMethod` (`vtable_call`/`first_param_usage`/`com_interface`/`string_function`/`integer_bit_pattern`/`pointer_arithmetic`/`known_signature`, with `is_this_pointer()` grouping the this-pointer variants), and `InferenceScope` (`function`/`class`/`program` — how far a reading reaches beyond the function it was made in), all `Serialize`/`Deserialize` with snake_case labels. 5 unit tests.
- **C++ this-pointer detection** — `this_ptr.rs` gained `ThisPointerDetector` (stateless over `DecompiledFunction` text, so one detector serves a whole concurrent scan) with `detect_this_pointer()`: a string-aware scan finds every indirect call in a decompiled body and resolves each dispatch to a vtable slot — a `[N]` index, a `+ 0xNN` byte offset over the x64 pointer size, or slot 0 for a bare double-deref, with an offset added to the object itself (`**(param_1 + 0x10)`, a secondary table behind a field) correctly read as slot 0 of that table. A parameter passed as the first argument through the table its own first word points at — inline (`(**(code **)*param_1)(param_1)`) or through a hoisted base (`pcVar2 = *(code **)*param_1;` then `pcVar2[3](param_1);`) — reads as a `this` pointer: unnamed readings narrow to `void *` at class scope (confidence 85 inline, 75 hoisted); a qualified member call in the body or the analyzed function's own demangled name names the class (`Widget *`, confidence 90 beside a dispatch, 80 on the name alone), refusing `std` and `operator` segments so library and operator plumbing name no class while whole-segment matching keeps namespaces like `MyStd`; and dispatches at two or three of the first three slots (QueryInterface/AddRef/Release) read the parameter as an `IUnknown *` COM interface pointer (`com_interface`, confidence 88). A delegate call that passes something other than the object it loaded from, a dispatch table, and a single dereference are all refused; at most one strongest-evidence record is emitted per parameter. 34 unit tests.
- **Parameter size detection** — `param_size.rs` gained `ParameterSizeDetector` (stateless over `DecompiledFunction` text like the this-pointer detector, so one detector serves a whole concurrent scan) with `detect_parameter_sizes()`: one pass over a decompiled body reads each parameter's usage shapes into `InferredParamType` records. A string-aware direct-call scan matches callees against the C string-function family (`strlen`/`strnlen`, `strcpy`/`strncpy`, `strcat`/`strncat`, `strcmp`/`strncmp`/`strcasecmp`/`strncasecmp`, `strchr`/`strrchr`, `strstr`, `strpbrk`/`strspn`/`strcspn`, `strtok`, `strdup`/`strndup`, and the `sprintf`/`snprintf`/`vsprintf`/`vsnprintf` line — each entry names the argument positions its contract reads as `char *`, so `snprintf`'s format behind its size argument still reads while a count, character, buffer-size, or variadic-tail position never does) and narrows a parameter sitting there to `char *` (`string_function`, confidence 70), seeing through Ghidra casts (`strcmp((char *)param_1, ...)`). A whole-word occurrence scan reads a parameter shifted or bitwise-ANDed as the default word `u32` (`integer_bit_pattern`, confidence 55) — a logical `&&`, a unary address-of, and a field's own bit operations (`param_1->flags & 0xff`) are refused — with the constants beside the operations weighed for width: a mask needs its own bit length and a shift the parameter is the operand of needs one bit more than its count, so a mask beyond the word (`param_1 & 0xffffffff00`), a beyond-the-word shift (`param_1 >> 0x20`), a left-hand mask (`0x100000000 & param_1`), and a compound `&=` mask widen the reading to `u64` (confidence 60) backed by the pinning line, while constants the word covers keep the default, a shift whose count the parameter supplies bounds nothing, and a parameter behind a cast (`(ulonglong)param_1 << 0x20`) keeps the word because the cast types the expression; and reads a parameter through a dereferencing star (`*param_1`, `(code *)*param_1`), a numeric offset inside a dereferenced group (`*(undefined4 *)(param_2 + 4)`), an arrow into a field (`param_1->count`, chained `param_1->next->value` — the arrow only exists on a pointer), or an array index (`param_2[2]` — the decompiler indexes what it types as a pointer) as a pointer to an unnamed pointee `void *` (`pointer_arithmetic`, confidence 65), refusing multiplies and bare offsets nothing reads through. - **Persisted result model** — `types.rs` gained the document the pipeline will consume: `InferredLocalType` (function, decompiled variable name, and the narrowed-type payload) and `InferredCallType` (function, callee as spelled at the site, argument position, optional argument name, and payload) as siblings of `InferredParamType`; `InferredType` as the union over the three record kinds, serde-tagged by `kind` (`param`/`local`/`call_site`) with `function()`/`inferred_type()`/`confidence()` accessors reaching through every variant, so one list can hold every inference for a binary and conflict resolution can weigh records across kinds; and `TypeInferenceResult` — the per-binary document for `re/analysis/typeinfer/{dll}.json`, pairing the shared `ScanMetadata` (now re-exported from `calxgloss-types`, matching the typesdb convention) with the inference list in scan order, the empty list omitted from JSON, plus `new`/`for_function`/`is_empty`. 9 unit tests.

#### `calxgloss-algorithm`
- **New crate: algorithm recognition** — scaffolded `calxgloss-algorithm` as a workspace member. Module skeleton: `types`, `cfg_patterns`, `string_hints`, `callback_db`, `confidence`, `persist`, `error`. `AlgorithmError` (thiserror) with `Ghidra`/`Io`/`Json`/`EmptyFunctionName`/`ScanFailed` variants plus a crate-wide `Result` alias. `Send + Sync`, holding no Ghidra client and never writing back, one matcher serving a whole concurrent scan) with `match_patterns()`: reads a `DecompiledFunction` body against every configured signature in order and emits one hint per fit — the line floor runs before any regex, a body shorter than `min_lines` being too small to carry a real shape, then every required regex must match and no exclusion may; each hint is marked `cfg_pattern` at confidence 60 (regexes over pseudo-C approximate the algorithm rather than prove it) and carries the trimmed body line holding the first match of the signature's first required regex as evidence; a signature asserting nothing fits nothing, and an uncompilable regex can make no claim — a match source matches nothing, an exclusion rejects nothing. Regex sources may carry a `{name}` placeholder the matcher replaces with the regex-escaped scanned function name, letting a signature speak of the function itself. `default_patterns()` carries the standard signature set and `with_default_patterns()` builds a matcher that scans against it: `comparison_sort` (loop inside a loop + ordering `<` + the three-assignment swap the decompiler emits, excluding bodies calling `qsort`), `binary_search` (probe loop + halved range `/ 2`/`>> 1` + midpoint comparison), `linear_search` (scan loop + `==` target test + early `return`/`break`, excluding halved ranges and `% ` bucket folding so a hash probe reads as a lookup), `hash_table_lookup` (`% ` digest fold + `[` bucket access + probe check), `state_machine` (state/status/mode-named variable + `if`/`switch` dispatch + `else`/`case` chain), `recursion` (self-call via `{name}`, its floor dropped to 6 because a self-call is precise evidence even in a short body, the `);` tail keeping the signature line from reading as a call), and `linked_list_traversal` (walk loop + `->` field reads + cursor advance). 6 + 26 unit tests.
- **String-guided algorithm hints** — `string_hints.rs` gained `StringHintEngine` (holds the configurable signature set a scan reads against — supplied whole with `with_signatures` or grown one at a time with `add_signature`, reported in configuration order so alike engines scan identically; `Send + Sync`, holding no Ghidra client and never writing back, one engine serving a whole concurrent scan) with `detect_string_hints()`: reads a `DecompiledFunction` body beside the program's `StringLiteral` listing against every configured signature in order and emits one `AlgorithmHint` per fit — a signature fits when any of its markers appears as a substring of the body or of a listing string, the body read first so a marker the function's own text carries wins the hint at confidence 60 (a substring hit evidences use rather than implementation, the hint standing beside a control flow match as a hypothesis) with the trimmed body line carrying the first marker match as evidence, while a listing-only match stands at 30 (program-wide evidence: it ties the program to the algorithm, not the function to its implementation) with the listing string itself as evidence. `StringSignature` (named algorithm, category, and marker spellings, `Serialize`/`Deserialize` like `AlgorithmPattern`) carries a per-signature `case_insensitive` flag — set with a `case_insensitive()` builder toggle and omitted from JSON when false, so signatures persisted without it read back case-sensitive — whose markers answer any casing of the scanned text, the fold running over chars so the found offset stays a boundary of the original text and the evidence keeps the text's own casing. Signatures naming the same algorithm report it once per function: the strongest-evidence hint wins, ties keep the signature configured first, and the survivor holds the place the algorithm first appeared, so the hints keep configuration order and two scans diff cleanly. `default_signatures()` carries the standard fifteen — crc, checksum, inflate, deflate, gzip, bz2, lzo, serialize, deserialize, md5, sha, hmac, http, tcp, udp — each naming one algorithm by the spellings it actually appears under (the uppercase acronym where strings and names shout it, the lowercase spelling decompiled identifiers carry; `sha` names only its digit-suffixed family so `shadow` suggests no digest), case-sensitive so every marker stays an exact spelling of what it saw. 31 unit tests.
- **Callback pattern detection** — `callback_db.rs` gained `CallbackPattern` (the callback contract shape: the recognized role (`qsort_compare`), the host algorithm's category, host-name regex sources matched against caller names, the arity the contract expects, and two optional fields omitted from JSON when empty — body-shape regex sources the callback's body must carry, and the `TypeHint`s the contract implies for the callback's own signature, each pairing a `TypeTarget` (the return or a 0-based parameter) with the C spelling the contract states for that position, e.g. `const void *` / `int`), `Serialize`/`Deserialize` like the other detector records, and `CallbackPatternDb` (holds the configurable contract set a scan reads functions against — supplied whole with `with_patterns` or grown one at a time with `add_pattern`, reported in configuration order so alike databases scan identically; host names are word-anchored, so `qsort_s` stays outside the two-parameter contract. `detect_callback_patterns()` demands both halves at once: the function takes exactly the contract's arity, read from Ghidra's inferred signature line, its body carries every required shape (a contract demanding no body shape fits on signature and usage alone), and one of the contract's hosts reaches it through the call graph — each fit reports a `CallbackDetection` pairing an `AlgorithmHint` (marked `callback_pattern` at confidence 75 — two independent signals agree, but the reading rests on regexes over pseudo-C rather than a resolved indirect-call target — with the host caller name as evidence) with the contract itself, whose type hints carry over to the analyzed function's signature. `default_patterns()` carries the standard three: `qsort_compare` (Sorting, host `\bqsort\b`) and `bsearch_compare` (Searching, host `\bbsearch\b`) — two opaque element pointers, an ordering `int` answer, a comparison between two pointer touches required in the body, the `[^-]` guard keeping a field-access arrow from reading as one — and `hash_comparator` (Hashing, hosts `\bhash_(?:insert|lookup|find|add)\b`), narrowed to `==` since a comparator answers equality, not ordering. ### Changed

#### `calxgloss-translator`
- **Type context from the persisted inference cache** — `extract_type_info()` (previously an empty stub) now loads `re/analysis/typeinfer/{dll}.json` through `TypeInferPersistor` and keeps the inferences made for the target function — parameter, local-variable, and call-site readings whose evidence lives in that function's decompiled body — rendered into `TypeInfo` by the typeinfer crate's prompt conversion. It is synchronous now — taking workspace/dll/function instead of a Ghidra client and function name, so the escalate call site reads the `workspace` field it already carried — and a missing or corrupt cache degrades to no type context rather than failing the prompt. 5 unit tests.
- **Data structure context from the recovered type database** — `extract_data_structures()` (previously an empty stub) now loads `re/analysis/typesdb/{dll}.json` through `TypeDatabasePersistor` and keeps the records tied to the target function: inferred struct candidates whose literals the function cross-references, plus named types of classes whose vtable lists the function as a method. It is synchronous now — taking workspace/dll/function instead of a Ghidra client and address, so `EscalatePromptCtx` gained a `workspace` field — and a missing or corrupt database degrades to no data structure context rather than failing the prompt. 7 unit tests.
- **Type database pre-processing in batch translation** — `TranslationPipeline::ensure_type_database(dll)` runs at the top of `batch_translate` and `batch_translate_from_callgraph`: the persisted file is the cache (`exists()` → skip the scan), otherwise `TypesDBEngine::scan` recovers and saves the database so every function in the batch can see type context. A missing workspace, an unreachable Ghidra server, or a failed save only log a warning and the batch proceeds. `auto`/`live` now set the pipeline workspace so the database files land under the output repo. 3 unit tests.
- **Type inference pre-analysis in batch translation** — `TranslationPipeline::ensure_type_inference(dll)` runs at the top of `batch_translate` and `batch_translate_from_callgraph` beside the type database pre-processing: the persisted file is the cache (`exists()` → skip the scan), otherwise `TypeInferEngine::scan` infers parameter types across the whole program and saves the result to `re/analysis/typeinfer/{dll}.json` so every function in the batch can see type context. A missing workspace, an unreachable Ghidra server, or a failed save only log a warning and the batch proceeds. 3 unit tests.
- **Boxed pipeline futures** — `try_translate_with_retry()` boxes the initial-translation and retry-loop futures (`Pin<Box<dyn Future<Output = _> + Send>>`) so downstream crates' `Send` checks stop at the boundary instead of recursively descending through the whole pipeline, which overflowed the compiler's trait-evaluation recursion limit (rust-lang/rust#159228).
- **Translation attempt context tier** — `TranslationAttempt` now carries a `context_tier` field recording which tier was used for each attempt. Enables post-hoc analysis of which context scope yields the best pass rates.
- **Per-attempt token logging** — `try_translate_with_retry()` now logs token usage to disk for every LLM call: the initial translation attempt, each retry attempt (compile_fix, test_fix, escalate, edge_case_fix), and empty-code failure cases. The log includes DLL name, function name, attempt number, strategy label, token count, and success/failure status. Tier-escalated attempts are also logged with their tier label.

#### Fault detection integration
- **Fault event persistence** — all detected faults (context-window exceeded, hallucination, infinite loop, behavior divergence, resource exhaustion) are now recorded to `re/analysis/fault_log.json` via `FaultLogger`. The translation pipeline wires the logger at the emission sites in both the main `translate()` path and the retry loop.
- **Hallucination detection in the translation pipeline** — `TranslationPipeline::try_translate_with_retry()` scans each LLM response for non-existent API references using the hallucination detector. Detected hallucinations are logged as warnings and emitted as `ProgressEvent::HallucinationDetected` for real-time dashboard visibility.

### Fixed

#### `calxgloss-cli`
- **`println_content` blanked lines carrying multi-byte characters** — the shared report-line padding helper compared the visible *byte* length against the 78-column width while the truncation cut counted characters, so a line whose visible text was under 78 characters but whose byte length was over 78 (a `●` bullet plus ANSI escapes does it) entered the truncation branch, where the cut never reached the limit and the whole line printed empty. ### Documentation

### `calxgloss-translator`
- **`batch_translate()` accepts a per-function callback** — the batch method now takes an optional `&mut dyn FnMut(&str, &str, &mut FunctionResult) -> bool` closure that is invoked immediately after each function's translation pipeline (including retries) completes, before the next function is processed. The callback can perform post-processing (e.g. writing files, git operations) incrementally. Returns `true` to continue the batch or `false` to stop early.

### `calxgloss-cli`
- **`auto-shim` subcommand** — generates shim layers for all crate-replacement DLLs automatically. After `classify` marks DLLs as `CrateReplacement`, this command runs the full pipeline: generate API mappings (LLM) → generate source code → generate tests → verify → persist. Artifacts are written to `re/shims/<dll_name>/` and committed to git. Supports `--dll <name>` to process a single DLL.
- **Incremental git commits during batch translation** — `run_translation_for_dll()` and `handle_batch_translate()` now commit and merge each function immediately after its translation succeeds, rather than deferring all git work until the entire batch finishes. Each function's Rust code is written, a `re/{dll}/{function}v1` branch is created, the file is committed, and the branch is merged to `main` before the next function is processed.

### `calxgloss-types`
- **Shim layer types** — `ShimApiMapping`, `ShimLayer`, `ComplexityScore`, and `ReturnMapping` define the API contract for translating a Windows DLL's exported surface to an equivalent Rust crate. Mappings carry original and target signatures, parameter transformation descriptions, complexity scores, and optional return-value handling. `ShimLayer` provides aggregate helpers (`total_complexity()`, `overall_complexity()`, `mapping_count()`) and converts to existing `ApiMappingItem` for prompt inclusion.
- `ShimVerificationResult` — result of verifying a shim layer against tests; reports compilation status, per-mapping test counts (main + edge-case), failures, and per-mapping breakdowns. Provides `total_tests()`, `total_passed()`, `all_passed()`, and `pass_rate()` helpers.
- `ShimMappingTestResult` — per-mapping test result with `original_api`, `crate_api`, pass count, total count, and detailed failures.
- **`ShimSuggestion`** — per-DLL shim layer estimate with `source_dll`, `target_crate`, `estimated_mappings`, `estimated_complexity` (Low/Medium/High), and `estimated_confidence` in `[0.0, 1.0]`. Produced automatically from classification data without an LLM call.
- **`ShimSuggestionReport`** — aggregation of all `ShimSuggestion` instances for crate-replacement DLLs. Provides `total_dlls()`, `low_complexity_count()`, `medium_complexity_count()`, `high_complexity_count()`, `is_empty()`, and `average_confidence()`.
- **`ProgressEvent::FunctionCompleted`** — new event emitted immediately after each function completes during batch translation, carrying `dll`, `function`, `success`, `attempts`, and `branch` fields.
- **`ProgressEvent::HallucinationDetected`** — emitted after the LLM response is scanned and one or more hallucinated calls are detected. Carries `dll`, `function`, `attempt`, `strategy`, and `hallucinated_apis` fields.

- **Shim mapping auto-generation** (`shim` module) — `generate_shim_mappings()` sends a structured prompt to the LLM containing the DLL name, target crate, and all exported function signatures; the LLM returns a JSON array of `ShimApiMapping` entries. - **Shim test generation** (`shim_test_gen` module) — `generate_shim_tests()` produces a complete Rust test module from a `ShimLayer` mapping table. For each mapping: generates a parameter correctness test verifying the shim calls the correct crate API with properly transformed parameters, returns the correct value type, and documents all transforms as inline comments; generates edge-case tests for boundary values (`zero`, `null`, `max`, `empty`, `negative`, `overflow`) found in parameter transforms; provides thread-local mock call recorders and per-crate mock modules (e.g. `mock_fmod_rs`, `mock_cpal`) that record invocations and arguments for verification; includes a summary test asserting the mapping count. Uses a merge-sorted priority queue keyed by `(depth, level, node_id)`. Level-aware tie-breaking ensures shim layers appear before PAL traits before function translations at the same topological depth. Cycle detection is non-fatal: nodes not involved in cycles are still correctly ordered.
- **`ReviewDashboard::sorted_queue()`** — canonical ordering for batch operations, using the full topological sort with level tie-breaking. Returns `Queued` / `PendingReview` units in dependency order, with already-accepted units at the end.
- **`ReviewDashboard::next_in_dependency_order()`** — returns the next unit to review in proper dependency-then-level order, replacing the deprecated `next_to_review()`.
- **`ReviewDashboard::pending_in_dependency_order()`** — returns only `Queued` / `PendingReview` units sorted by dependency depth, ready for batch acceptance.
- **`ReviewDashboard::auto_block_units()`** — automatically marks units as `Blocked` when their dependencies are in a failing state (`SendBack` / `PatchRequested`). Propagates transitively: if A depends on B and B fails, A is blocked; if C depends on A and A is blocked, C is also blocked. Skips terminal statuses (`Accepted` / `Merged` / `Blocked`) and the failing units themselves (they keep their original status). Scans both `review_queue` and `recent_activity`. Returns the count of units changed to `Blocked`. Idempotent.
- **`ProgressEvent` enum** — typed events emitted at pipeline milestones: `TranslationStarted`, `GhidraFetchComplete`, `ApiTaggingComplete`, `TestsGenerated`, `LlmCallStart`, `LlmCallComplete`, `TranslationAttemptCompleted`, `TranslationCompleted`, and `TranslationFailed`. All variants carry `dll`/`function` identifiers plus attempt-specific metadata; fully serializable via `serde` for JSON transport over WebSockets.
- **`TranslationEvents`** — broadcast-channel wrapper (`tokio::sync::broadcast`) for publishing progress events. `emit()` returns the subscriber count, `subscribe()` creates a new receiver. Callers don't need to handle errors — lost events when no subscribers are present are silently discarded.
