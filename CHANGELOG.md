## [Unreleased]

### Added

- **Closure signatures via injected type inference (P6.5-4).** `calxgloss callback` and the batch pre-analysis now fill the real closure contract into callback suggestions when the workspace caches a type-inference result: **`Box<dyn Fn(i32) -> bool>` instead of `Box<dyn Fn(...)>`** — the type-inference scan's persisted per-binary document is read, its per-function parameter and return records composed into a signature map, and the callback scan runs with it injected, so **no extra flags** appear and the callback crate gains **no dependency** on the type-inference crate. A contract joins the map only when it is **fully read** — parameter records covering positions 0..*n* contiguously, plus a standing return record — because a gap proves an untyped middle parameter the contract would misplace, no parameter records cannot tell a zero-parameter callback from an unread one, and a missing return would assert a unit return nobody read; a `void` return simply drops its arrow clause. **Function-pointer-array and jump-table suggestions are untouched** — their callees are unnamed — and so are event-system suggestions, where no single contract stands for a crowd of handlers. A **missing, corrupt, or partial type-inference document degrades silently** to today's open suggestions — a bad neighbor artifact never fails the scan — and running the callback scan standalone stays first-class. The enrichment is scan-time, so the persisted JSON, the CLI report, and the escalate prompt all carry the same enriched string. The decision to inject rather than depend is recorded in **ADR-0036** (issue #173, P6.5-4).
- **Event system reconstruction: `event_system` findings (P6.5-3).** `calxgloss callback` now reconstructs a binary's event architecture on the cross-function pass built for chains: **two or more registrations to the same registration name across the scan**, plus **at least one dispatch site — a function-pointer-array or jump-table reading — in any kept body**, reconstruct as one `event_system` finding at confidence **60** — the reconstruction is a pattern inference over fragments, visibly weaker than the chain's two-ended evidence — attached to the **earliest registering function** in listing order, naming the **registration point**, the **registered callbacks** (duplicates collapsed, each handler named once however many sites hand it over), and the **dispatching functions**, carrying **every registration and dispatch line** as pipe-joined evidence (`FUN_A: register_callback(on_message); | FUN_B: register_callback(on_shutdown); | FUN_C: handlers[uVar1](param_1);`) and suggesting the **observer pattern** — registered `Box<dyn Fn(...)>` handlers dispatched through a table. **Registrations with no visible dispatch site report nothing**: a handful of unrelated callbacks is not over-read as an event architecture, and fewer than two registrations to one name claim nothing either. The pass **keeps honoring the detectors' configured name sets** — custom registration spellings and custom table names and jump-table prefixes reach the reconstruction through the same builders, and a retired standard name gates nothing and joins no evidence. A function whose decompile failed contributes nothing — it binds no registration and dispatches through nothing. The finding **rides the tagged union** with its own `event_system` kind tag, round-trips through serde into the persisted JSON, renders into the escalate prompt through the existing union accessors, and appears in the CLI report's kind breakdown; reconstruction findings **append after the chain findings**, in listing order of their earliest registering body, keeping the scan-order contract and the persisted document diffable, and the rule is **unit-tested directly over hand-written bodies on the pure cross-function module**, pinning the two-registration gate, the dispatch gate, earliest-registering-body attachment, one finding per registration name in first-registration order, jump-table and custom-prefix dispatch sites, the unbound and truncated registration silences, and the configured-set contract, with engine and integration tests proving the finding rides the whole scan into the persisted document and the escalate prompt (issue #172, p6.5-3).

- **Cross-function callback chains: `chain` findings (P6.5-2).** `calxgloss callback` now sees the callback lifecycle neither body shows alone: the scan keeps the decompiled bodies from its per-function pass and a new pure cross-function pass derives, per body, the registrations the registration detector binds — through its own site reading, which also reports **every plain identifier the call's arguments spell**, so a table handed over beside the handler (`register_callback(on_message, &handler_table)`) is matched without a second walk or a second argument parse — the direct-call targets of the shared call-site scan, and the tables the fp-array and jump-table detectors read being called. A callback **registered in one function and called by name in another**, or a **table named at a registration site being the same table a function-pointer-array or jump-table reading calls through**, lands one `chain` finding **per (registering function, calling function) pair** on the earlier function in listing order, naming the partner function, the callback, and the table it runs through (`table` omitted from the JSON for a direct-name chain) at confidence **70** — both ends are explicit body evidence — with both ends' call lines as evidence (`FUN_A: register_callback(my_handler); | FUN_B: my_handler(param_1);`). A registration whose callback is never visibly called in any kept body claims nothing, a body that registers and calls in one function says nothing about a boundary, and one chain per pair keeps a pair tied by two callbacks reading once. Everything keys on the **detectors' configured name sets** — custom registration spellings and table names reach the pass through `with_registration` and `with_fp_array`, not a private default — and the pass adds **no extra Ghidra round trips**: the exactly-once-decompile, scan-order, and skip-rate-breaker contracts stay green untouched, chain findings **append after the per-function findings** in listing order, a function whose decompile failed binds nothing and fabricates nothing, and the kind rides the tagged union into the persisted JSON, the CLI kind breakdown, and the escalate prompt. The decision to run the pass over the kept bodies is recorded in **ADR-0035** (issue #171, P6.5-2).

- **Plugin architecture detection: `plugin` findings (P6.5-1).** `calxgloss-callback` now spots the dynamic-loading boundary a plugin binary leaves in plain call form: a new per-body detector reads loader pairs — `LoadLibrary`/`LoadLibraryEx` or `dlopen` beside `GetProcAddress` or `dlsym` — plugin entry-point names (`Plugin_Init`, `Plugin_Unload`, `GetPluginInfo`, `GetPluginAPI`, `GetExportTable`, `RegisterPlugin`, `InitializePlugin`), and the host API table handed to an entry point. A **full load-and-resolve pair in one body** lands one `plugin` finding at confidence **70** with the loader call line as evidence — both halves of the boundary were read — while a **lone resolve call or a lone entry-point name** is a **fragment** at **60**, the same rung a half-seen lifecycle pays elsewhere, since only half the shape stands in this body; a lone load call claims nothing, because a DLL pulled in for its exports is not a plugin boundary. A **host API table — a plain identifier the decompiler did not mint, seen through casts and `&`, passed into an entry point — deepens the same finding, never a second one**, and minted names (`param_*`, `local_*`, `*Var*`) and `NULL` name no table. Each record suggests the trait-object plugin boundary — **`Box<dyn Plugin>` (loader crate)** — so the plugin contract survives translation instead of collapsing into opaque loader calls, and its visible parts (loader, resolve, entry point, host table) ride as optional fields on the tagged `plugin` kind into the persisted JSON, the CLI kind breakdown, and the escalate prompt. The reading stays blind where the crate's other detectors are blind: string literals invent nothing — `"Plugin_Init"` inside a `GetProcAddress` argument is not a call — longer or qualified names match nothing, and a truncated body detects nothing. Within one body plugin shapes land **after the jump tables**, keeping the scan-order contract diffable, and the engine's **`with_plugin`** builder swaps the three name sets whole — custom loader, resolve and entry-point spellings call findings, the standard names they replace call nothing (issue #170, P6.5-1).

- **Cross-function data-race analysis: `data_race` findings (P5.5-5).** `calxgloss sync` now sees the unsynchronized global neither body shows alone: the cross-function pass ADR-0033 built reads the same kept bodies for one function **storing into a program global** another function **reads** with no lock either side respects — a global being any plain identifier the decompiler did not name as its own local (`param_*`, `local_*`, `*Var<digits>` are a function's own frame, not shared data), and an access standing **outside every recognized acquire→release span**, paired by the mutex detector's own rule so the two readings cannot disagree about what a span covers. One function writing a global under no lock and another reading it lands **one `data_race` finding per function pair and global** on the earlier function, naming both functions and the variable at confidence **60** — one rung below the evidence-based kinds, because the claim is that no lock was *found* — with each side's access statement as evidence (`FUN_A: DAT_counter = iVar1 + 1; FUN_B: uVar1 = DAT_counter;`). **One lock object held over every access on both sides suppresses the claim** — properly locked data is not a race — while an unprotected access on either side, or two sides guarded by *different* locks, leaves it standing; and a pair claims only when the two bodies show **both a store and a read**, so two functions each blindly overwriting one slot stay quiet. The reading stays blind where the pass is blind: call arguments (lock objects and operation constants included), string literals, qualified names, and type words name no shared data, and a function whose decompile failed contributes nothing. Race findings **append after the lock-order findings**, the kind rides the tagged union into the persisted JSON, the CLI kind breakdown, and the escalate prompt, the pass adds **no extra Ghidra round trips**, and the exactly-once-decompile, scan-order, and skip-rate-breaker contracts stay green untouched. The decisions behind it are recorded in ADR-0034 (issue #168, P5.5-5).

- **Cross-function lock-order analysis: `lock_order` findings (P5.5-4).** `calxgloss sync` now sees lock discipline across function boundaries: the scan keeps the decompiled bodies from its per-function pass and a new pure cross-function pass derives, per function, the sequence of distinct lock objects acquired in body order — reading the mutex detector's configured acquire names and the pairing detector's own lock-object extraction, with **no extra Ghidra round trips**. Two functions that acquire the same two locks in **opposite relative orders** land one `lock_order` finding **per conflicting lock pair** on the earlier function, naming both functions and both lock objects at confidence **70**, with the two acquire orders as evidence (`FUN_A: local_20 -> local_40; FUN_B: local_40 -> local_20`); functions sharing one consistent order claim nothing, and a function whose decompile failed forms no sequence and fabricates no conflict. Cross-function findings **append after the per-function findings**, both groups in listing order, so two scans still diff cleanly and the exactly-once-decompile and scan-order contracts stay green untouched. The kind rides the tagged union into the persisted JSON, the CLI kind breakdown, and the escalate prompt, and the decision to run the pass over the kept bodies is recorded in **ADR-0033** (issue #167, P5.5-4).

- **Futex-based synchronization detection: `futex` findings (P5.5-3).** `calxgloss sync` now spots raw futex calls: direct `futex` calls and `syscall(SYS_futex, …)` shapes in decompiled bodies yield a new `futex` finding per call site at confidence 70, naming `FUTEX_WAIT`/`FUTEX_WAKE` when the body spells it and otherwise the call spelling, and suggesting standard synchronization (`std::sync::Mutex`/`Condvar`) instead of transliterated syscalls. Findings ride the union's tagged `futex` kind, render through the usual accessors, and appear in the CLI kind breakdown, slotting after `async_runtime` within a function; custom name sets reach the scan via the engine's builder like every other detector. Issue #166.


- **Thread-local storage detection: `tls` findings (P5.5-1).** `calxgloss sync` now sees the per-thread globals hiding in plain call form: a new detector reads the Win32 TLS family — `TlsAlloc` creating a key, `TlsGetValue`/`TlsSetValue`/`TlsFree` using it — and the POSIX thread-key family — `pthread_key_create` creating one through its pointer argument, `pthread_getspecific`/`pthread_setspecific`/`pthread_key_delete` using it. A key **created and accessed in one body** lands as one finding at confidence **70** naming both spellings — `TlsAlloc→TlsGetValue` in the target, the creation line and the access lines as evidence — because the whole lifecycle was read; a lone access with no creation in view is a **fragment** at **60**, the same rung the thread-without-join reading pays, since only half the lifecycle stands in this body. The tie is by **variable**: the access names the same slot the creation wrote (`local_4 = TlsAlloc(); TlsGetValue(local_4);`), and further accesses of that slot fold into the one finding rather than stacking duplicates — while a creation never accessed claims nothing, because an allocated key nobody reads is not a usage. The reading is blind where every other detector is blind: string literals invent nothing, longer or qualified names match nothing, and a truncated body detects nothing. Each finding suggests **`thread_local!`** storage, lands under the new **`tls`** kind, slots **after the thread spawns** in within-function order so two scans still diff cleanly, and reaches the persisted JSON, the CLI kind breakdown, and the escalate prompt's CONCURRENCY section like every other detector's records — and custom creation and access name sets replace the built-in families whole, like every other detector's name hook (issue #164, P5.5-1).

- **Per-type `Drop` suggestions: named handle types (P4.5-5).** When the decompiled body spells a real type for a paired handle — `HANDLE hFile = CreateFileW(...);` or a hoisted `FILE *local_10;` — the pairing's guard suggestion upgrades from the generic "RAII guard struct with Drop impl" to **`impl Drop for HANDLE`**, naming the type the `Drop` impl belongs to, and the record carries the name in a new optional `type_name` field so documents saved by earlier builds read back untyped. The type comes **only from the body's own declaration** — a binding spelled `<Type> <variable>;` or `<Type> <variable> = ...;` — never from casts or convention: a bare assignment declares nothing, a primitive or `undefined8` declaration names nothing worth a `Drop` impl, and the reading stays blind inside string literals and to longer names that merely end where the variable's does (`hFile2` never names `hFile`). **The scoped narrowing still outranks the name**: a handle read after its close takes the scoped guard whatever its type is called, and the named upgrade rides the plain pair at its own confidence 70 — the name refines what to call the guard, not how strongly the lifecycle was read. The decisions behind it are recorded in ADR-0031 (issue #162, P4.5-5).

- **Smart-pointer upgrade: `Rc<T>` for kept pointers (P4.5-4).** A cross-function claim now reads what the callee *keeps*: when an allocated pointer is handed to a scanned callee and that callee's body stores the parameter somewhere the call survives — into a **global** (`global_ptr = param_1;`, seen through casts) or a **struct field** (`this->ptr = param_1;`) — the allocating function's suggestion upgrades from `Box<T>` to **`Rc<T>`** and the store line joins the evidence, because more than one place holds the block and a moved `Box` would leave the stored copy dangling. The upgrade **rewrites the claim that already exists** — pair or transfer — keeping its confidence (70 pair, 65 transfer): the keep refines which pattern, not how strongly the relationship was read, and one claim per allocation means Box and Rc never contradict each other for one pointer. A callee that only reads the parameter keeps nothing; a store into the callee's own frame (`local_8 = param_1;`) is gone when the call returns; a store through a bare dereference names no place the scan can tell from a stack slot; and a keep can only be read where a body was read — returned pointers and callees outside the scanned set keep the plain reading, with **zero new Ghidra reads**. `Arc<T>` stays the reference-count detector's spelling; thread-awareness is out of scope. The decisions behind it are recorded in ADR-0030 (issue #161, P4.5-4).
- **Resource leak detection: `leak` findings (P4.5-3).** The scan now reports the absence it was built for: an allocation a function makes, never releases, and never lets escape — not handed to any callee, not returned — lands as a new `leak` kind naming the **allocation family**, with the acquisition line as its evidence (a leak is an absence; the only positive fact is where the resource was taken) and a `Box<T>` suggestion at confidence **60** — one rung below the transfer (65), below the pair (70), because an absence is only what this body shows. **The escape rule is the false-positive gate**: the same hand-off or whole return the ownership reading reports suppresses the leak, so a pointer that leaves is a transfer, never a leak, and the pairing detector's pinned silence on unpaired allocations stays untouched — leaks come only from the cross-function pass, which has checked every way the value could leave. **Handles ride the same rule**: the handle pairing gained an open-list accessor mirroring the allocator's, and an unclosed handle that escapes nowhere leaks by its **opener** with the RAII guard suggestion, while one handed over or returned says nothing. Within one function the group keeps its order — open allocations in allocation order, then open handles — and the kind rides the tagged union so persistence, the CLI kind breakdown, and the prompt conversion pick it up with no shape change. The decisions behind it are recorded in ADR-0029 (issue #160, P4.5-3).
- **Ownership transfer detection: `ownership` findings (P4.5-2).** The cross-function pass now reports the moves its pair reading leaves silent: an allocation a function leaves open and **hands over without a readable release** — passed as a plain argument at any call site, including a library routine or a callee that never frees, or **returned whole** to the caller (`return pvVar1;`, seen through any cast) — lands as a new `ownership` kind naming the **direction** of the move (`handed_to_callee` with the callee's spelled name as partner, or `returned_to_caller` with no partner) and the transferred variable, with the allocation line and the hand-off or return line as evidence, and suggests `Box<T>` at confidence **65** — one rung below a read release (70), level with the short-lived stack reading, because the far side of the move is unseen. **One open allocation, one claim**: where a variable both reaches a releasing callee and escapes elsewhere, the pair wins — one moved block moves once, and the pair is the claim whose release was actually read. A member call (`obj.FUN_x(pvVar1)`) stays invisible to the pair — the implicit receiver shifts the positional tie — but the pointer still leaves, so it transfers with the dotted callee named verbatim. A return of anything but the block whole — `return pvVar1 + 1;`, a bare `return;` — transfers nothing. The decisions behind it are recorded in ADR-0028 (issue #159, P4.5-2).
- **Cross-function allocation tracking: `cross_function` findings (P4.5-1).** `calxgloss memory` now sees lifecycles that cross a function boundary: a new cross-function pass runs **after the per-function walk, over the bodies the scan already decompiled** — no extra Ghidra round trips — and reports an allocation one function made and a callee it was handed to released. The finding lands on the allocating function as a new `cross_function` kind naming the partner function and the transferred variable, with evidence spanning both bodies (the allocation line, the hand-off call, the callee's release), and suggests `Box<T>` for ownership moved into the callee at confidence **70**, level with an in-body pair. The tie is positional: the argument at position *i* arrives in the parameter the callee's signature declares at *i*, and the release must name that parameter, seen through any cast. Only functions this scan decompiled can release — a library callee or a function whose decompile failed claims nothing — and the **first releasing callee in source order wins**: one moved block moves once. The pass starts from the pairing walk's own open-allocation list, so the pairing detector's contract — report only pairs, stay silent on unpaired allocations — is untouched and the two readings can never disagree about what stands open. Findings append after the per-function findings in listing order, so the persisted document stays diffable, and the exactly-once-decompile and skip-rate-breaker contracts are unchanged. The decisions behind it are recorded in ADR-0027 (issue #158, P4.5-1).
- **Parallel algorithm scan (P3.5-5).** `calxgloss algorithm` now scans a large binary faster without flooding the Ghidra bridge: the per-function pass runs with **bounded concurrency** — at most eight decompiles in flight at once — instead of one sequential round trip at a time. The observable contract is unchanged: hints still land in listing order so two scans of one program diff cleanly, each function is still decompiled exactly once, the string listing is still fetched once, and caller fetches stay gated on arity. The **skip-rate breaker** still catches a wrong-program scan: it counts decompile failures across the concurrent pass and stops issuing new decompiles the moment it trips, aborting with the counts instead of persisting a phantom-clean record. The decisions behind it are recorded in ADR-0026 (issue #156, P3.5-5).
- **Correlation patterns in the pattern database (P3.5-4).** The JSON pattern database behind `calxgloss algorithm --patterns` gained its fourth section, `correlation_patterns`, so the call relationships the correlation detector reads are data like every other signature set: a file can teach the scan a relationship that exists nowhere in the built-ins — a named host call whose partner callee carries a named shape — without recompiling. The section replaces the built-in relationship set **whole**, mirroring the other sections: a file that names only its own relationships retires `divide_and_conquer` and `comparison_sort` alongside it, and only a scan with no file supplied keeps the built-in set. Entries carry exactly the relationship shape the detector already reads — a named algorithm and category, body shapes with the `{name}` placeholder, partner shapes the callee's body must fit, a line-count floor, and an optional per-entry confidence — and a malformed section fails the run loudly, naming the path. The decisions behind it are recorded in ADR-0025 (issue #155, P3.5-4).
- **Multi-function correlation: `cross_function` hints (P3.5-3).** The algorithm scan now sees the algorithms that live **between** functions, not just inside one: a new fourth detector reads a **call map derived from the bodies the scan already decompiles** — which program functions each body names, covering direct calls and callbacks handed to a host like `qsort(a, n, 4, FUN_x)` — and claims an algorithm when one function's body fits a **relationship** and a named partner's body carries the other half. Each claim lands as a hint under a new `cross_function` detection method at confidence **70** — above a single-body match (60), below a call-graph-confirmed callback contract (75) — with the body line naming the partner as its evidence, and the whole pass adds **zero extra Ghidra round trips** — it reads only the bodies the scan already fetched. The built-in set is deliberately small — **`divide_and_conquer`** (a self-call beside a halving, self-carried with no partner needed) and **`comparison_sort`** (a `qsort` host whose named comparator callee actually compares its two arguments) — and relationships are data: a named algorithm and category, body shapes the calling function must fit, partner shapes the callee must fit, a line-count floor, and an optional per-entry confidence. Correlated hints join ADR-0022's resolution — a correlated claim outweighs a weaker body match for the same algorithm — and the minimum-confidence floor drops them like any other; unrelated functions stay quiet. The method appears in the hint, the persisted JSON, and the `algorithm --show` breakdown, and the decisions behind it are recorded in ADR-0024 (issue #154, P3.5-3).
- **JSON pattern database: `--patterns` (P3.5-2).** `calxgloss algorithm` can now be taught new algorithm shapes **without recompiling**: `--patterns <file>` runs the scan with the file's control flow signatures, string signatures, and callback contracts **instead of the built-in standard sets** — the swap is whole, never a merge, so the file is exactly what the scan knows and a built-in signature that misfires on one binary can be retired. The database is **one JSON document with a section per detector**, and its entries are exactly the pattern types' existing serde shapes — what a scan persists and what a database carries are the same thing. Each entry may carry its own **confidence** that overrides the detector's standard score, so a hand-tuned signature can outweigh a standard-score claim for the same algorithm in resolution — and a distrustful entry at a lower score still loses: the override wins only by being stronger. File entries keep the detectors' semantics whole: the **`{name}` placeholder** works exactly as in the built-ins, and an **uncompilable regex** inside an entry can fabricate or veto nothing. A **malformed file fails the run loudly**, naming the path and reason — a typo never silently degrades recognition to a partial set — and with no file supplied the built-in standard sets remain the default, so existing scans are unchanged. The decisions behind it are recorded in ADR-0023 (issue #153, P3.5-2).
- **Confidence resolution and minimum-confidence floor: algorithm scan (P3.5-1).** When several detectors claim the same algorithm for one function, `calxgloss algorithm` now reports it **once with the strongest evidence** — a tie keeps the claim the scan surfaced first, and the survivor stands where that algorithm first appeared, so two scans of the same program still diff cleanly. Different algorithms claimed for one function always coexist: a function doing a hash lookup and a recursion reports both. The scan gained a configurable **minimum-confidence floor**: hints below it never reach the persisted result, and the floor applies after resolution, so a claim another detector strengthened clears a threshold its first claim would have missed. The standard score each detector pays out (control flow 60, string body match 60, listing-only match 30, callback contract 75) now lives in one place, so tuning the scoring model is a single change, and the decisions behind it are recorded in ADR-0022 (issue #152, P3.5-1).
- **Type write-back into Ghidra: `--write-back` (P2.5-8).** `calxgloss typeinfer` can now apply its own surviving hypotheses back into the open program, in the order the program needs — **create the referenced type names first**, so no write names a type Ghidra cannot resolve, **then function prototypes**, merging the inferred parameter and return readings into each function's *existing* prototype (name, calling convention, and untouched slots ride back out verbatim, one write per function), **then local-variable types**. A missing type name becomes a one-byte placeholder the program can later flesh out, and an existing type is never recreated — a hand-worked program's real structs are safe. The pass is conservative by construction: a slot Ghidra already types concretely is **never overwritten** — only the `undefined` family narrows, and a `void` return is a decision, not a placeholder — records below a **confidence floor** (default 70, `--confidence-floor`) are skipped with the reason, call-site readings are skipped as site readings rather than program slots, and Rust-flavored integer widths (`u32`, `u64`) are written using Ghidra's C-parser spellings (`uint`, `ulonglong`). One refused write never aborts the run: every failure is collected and the pass ends with an **applied / skipped / failed report** naming each target and reason. The flag is off by default, works after a scan and with `--show` on a cached result, and the decisions behind it are recorded in ADR-0021 (issue #150, P2.5-8).
- **Type write-back seam: `TypeWriteSource` (P2.5-7).** `calxgloss-ghidra` gained the write side of its client seam: a `TypeWriteSource` trait beside `ScanSource` carrying the six type-writing calls the v6.0.0 bridge offers — **`set_function_prototype`** and **`set_local_variable_type`** (both addressing the function by address, as the bridge parses that parameter as an address and refuses a name), **`create_struct`** (fields by name and type, with an optional byte offset), **`create_enum`** (member name → value, explicit size), **`create_typedef`**, and **`add_struct_field`** — each payload shaped from the bridge's own request-body maps and every response still classified through the crate's error kinds, so a write the bridge refused as prose (`Structure with name 'X' already exists`, `Failed to set function prototype: …`) surfaces as a named `GhidraError::Reported` instead of a silent success, and the `Structure not found: X` sentinel on `add_struct_field` maps to `NotFound`. `GhidraClient` is the trait's **only implementer**: the read cache deliberately never wraps writes — the same function-tag precedent — so a type-write pass is handed the raw client and every write reaches the server. Nothing in the analysis pipeline drives the seam yet; the write-back pass and CLI land next (issue #149, P2.5-7).
- **Integer bit-pattern depth (P2.5-6).** The type inference scan now reads a parameter's integer width from more of the shapes a body carries it in, not just shifts and masks: a **comparison** (`param_1 == 0x100000000`), a **bitwise OR or XOR** (`param_1 | 0xff0000000`), or a **compound assignment** (`param_1 += 0x100000000`) beside a constant bounds the parameter's width the way a mask or shift count already did — a constant too wide for the default word widens the reading to `u64`, and the widest constant anywhere in the function's operations still pins it, whichever operation carries it. A comparison or arithmetic compound assignment counts only through a **non-zero constant**: `param_1 == 0` is the null-test spelling and `param_1 += 4` could advance a pointer, so neither reads a width on its own, and a parameter tested only against zero keeps no integer reading at all. Constants on either side of the operator count; non-constant operands, parameters behind casts, field operations, and the logical `&&`/`||` still bound nothing. The reading keeps the same record shape, the same confidence ladder (default word 55, pinned width 60), and the same family ordering — a string reading still beats a pointer reading, a pointer reading still beats an integer reading — so every record rides the existing conflict resolution, persistence, and prompt plumbing (issue #148, P2.5-6).
- **C++ mangling analysis (P2.5-5).** The type inference scan now reads the type contract that a name itself spells out — the reading no body usage can beat: a demangled qualified call like `Widget::Render(int,char *)(param_1, uVar2)` in a decompiled body types the call's arguments from the spelled parameter list, keyed by the callee's spelled name with the call line as evidence, and an **MSVC-mangled listing symbol** like `?copy@Widget@@QAGPADPAD@Z` decodes for calling convention (a member's implicit `this` at position zero, typed as the named class's pointer), argument count, rough argument types, and a non-`void` return — typed from the symbol itself, **even when the function's body never decompiles**, because the listing pass reads every symbol before the decompile attempt. Each reading lands under a new `mangling` method at confidence 80 — a symbol-borne fact, above the known-signature (75) and cross-function families and just below the vtable/COM dispatch evidence — so a mangling reading beats a weaker inline reading for the same parameter in the existing conflict resolution, and the records ride the existing persistence and prompt plumbing. The MSVC decoder covers the practical subset — member and static-member conventions, 64-bit `this`, simple integer/float/`bool`/`wchar_t` arguments, pointers with const/volatile storage, pointers to and by-value class types, nested class chains — and anything outside it (references, function pointers, enums, templates, operator spellings, name back-references) makes the whole name unparseable: **an unparseable name produces no records at all** rather than a half-decoded guess. A qualified name without a spelled parameter list says nothing, spelled lists are only placed when the argument count matches the decompiled parameters (plus one for an implicit `this`), and namespace noise (`std::`, `operator`) is never mistaken for a member contract (issue #147, P2.5-5).
- **Return-type inference from caller usage (P2.5-4).** The type inference scan now types what a function hands back — the reading no body can ever show about itself: a helper whose every caller assigns its result to a typed slot, feeds it to `strlen`, or dereferences it still decompiles as `undefined FUN_x(void)`, so the scan reads each function's **callers** instead. A call site contributes when the returned value sits in a shape that names a type: assigned to a local the scan's own locals pass typed in that caller (`local_8 = FUN_x();` where `local_8` stands `char *` lends the function that return type), passed at a position a known signature reads (`strlen(FUN_x());` types the result as the contract types that argument), or dereferenced / `->`-field-accessed (`*FUN_x()` says pointer, pointee unknown — a bare `void *`, never a guessed pointee). Each reading lands as a new `kind: "return"` record under the `return_usage` method at confidence 60 — the bottom of the ladder — keyed by the callee, so one function never keeps two return types: every caller's candidate competes in the existing conflict resolution, the strongest survives, ties go to the first-seen caller, and the record's evidence is that caller's decompiled line. Bare statement calls, comparisons, multiplications, casts around the call, untyped or non-local assignment targets, and results nested in a callee the database does not know say nothing. The pass rides the caller→callee pass's cached caller bodies — **zero extra Ghidra round-trips**, the scan still decompiles each function exactly once — and the records ride the existing persistence and prompt plumbing, rendering into the translator's type-info sections under the name `return` (issue #146, P2.5-4).
- **Local-variable type inference via assignment chains (P2.5-3).** The type inference scan now types the decompiler's stack slots, the record kind the vocabulary always defined but no detector ever emitted: after the inline detectors resolve, a local assigned a parameter with a surviving reading — `local_8 = param_1;` where `param_1` stands read as `char *` — takes that reading, a local assigned a known-signature routine's result — `local_10 = (char *)malloc(0x10);` — takes the contract's return type (`malloc` hands back `void *`, `strlen` a `size_t`), and a local assigned an already-typed local propagates the type **one hop**: `a = param; b = a; c = b` types `a` and `b` and stops, never chasing a chain to a fixpoint. Each reading lands under a new `assignment_chain` method at confidence 60 — the bottom of the ladder, since the assignment is direct body evidence but the type is only as good as its source — keyed by function and decompiled name, with the assignment line as evidence, so two different names in one function and the same name in two functions never conflict and one name assigned twice resolves to the strongest, first-seen record like every other target. Dereferences (`*puVar5 = …`), indexes, comparisons, compound assignments, control headers, and writes to parameters type nothing, and a cast around the source (`(char *)param_1`) still names the value. The pass reads the bodies the scan already holds — no extra Ghidra round-trips — and the records ride the existing conflict resolution, persistence, and prompt plumbing, so the decompiled bodies an operator reads and the translator's prompts now name their stack slots with real types (issue #145, P2.5-3).
- **Cross-function type propagation: caller to callee (P2.5-2).** The type inference scan now also types a function by what its callers hand it: after the inline detectors and the callee→caller pass, the scan asks Ghidra for each analyzed function's callers and reads the arguments at their call sites of it — a caller passing along one of its own typed parameters, a string literal (`"…"` is `char *`, `L"…"` a `wchar_t *`), or a known routine's result (the signature database gained return types: `malloc` hands back `void *`, `strlen` a `size_t`) — each lending the callee's own parameter a record under the `cross_function` method at confidence 65, the bottom of the cross-function band, so an inline vtable reading (85) or any inline reading on a tie still wins and a helper the body cannot type — a forwarder, a setter — reaches the translator's prompts typed from the contract its callers reveal. Numeric literals, casts, indexed or member operands, and identifiers the scan never typed say nothing about a parameter, and positions the callee's signature does not declare are never typed. Caller bodies are fetched at most once per scan: the listing's own bodies are reused, any other caller is decompiled once and cached — failures included, so a caller that will not decompile is asked for exactly once — and the analyzed function's own body is still decompiled exactly once (issue #144, P2.5-2).
- **Cross-function type propagation: callee to caller (P2.5-1).** The type inference scan now types a function's arguments by what the callee itself proves about its parameters: after the inline detectors run, a user-defined callee whose own body survives a parameter reading — `FUN_18004b210` standing `param_1` as `char *` because its body runs `strlen(param_1)` — lends that type to the bare-identifier arguments at every call site of it in the scanned program, each recorded as a call-site record with the call line as evidence under a new `cross_function` method, and the type climbs one hop further when the argument is the caller's own parameter, which gets its own parameter record. Literals, casts, and nested-call arguments produce nothing; a callee the scan never typed (an import, or a function whose body proved nothing) lends nothing; and where the caller's own body already read the same argument, the inline record wins the target — the call-site record survives beside it, the duplicate parameter record drops. Analysis is the minutes-long part, so it is tracked in `re/ghidra/analysis_cache.json` keyed by path and SHA-256: a program opened from the project whose bytes match a cached record skips re-analysis, while a fresh import is always analyzed; the cache degrades, never fails — corrupt or unwritable reads as cold and costs one re-analysis, never a broken command. A long analysis runs under a request timeout raised for it, and its progress is polled while it is in flight so the log shows function discovery climbing instead of one long silence. The dashboard sees it all: new `GhidraProjectCreated` and `GhidraProgramAnalyzed { dll, secs }` events flow over the existing WebSocket bridge (issue #116, G1-T6).

- **UDS port discovery + reconciliation (G1-T5)** — when the configured Ghidra port answers nothing, calxgloss now looks for a GhidraMCP server that is actually running before deciding to start one: the bridge's own runtime-socket directory (`$XDG_RUNTIME_DIR/ghidra-mcp`, falling back to `/run/user/<uid>/ghidra-mcp`) holds one registration per live Ghidra instance, and each reveals its real TCP port and open project. Dead registrations are ignored and never deleted, and a discovered server that passes the identity check is **attached to** instead of failing or spawning — the correction is logged ("configured X, discovered Y — attaching"), so a stale `ghidra.url` no longer blocks a command when a GUI Ghidra is open on another port. When a server does have to be started, it now picks the configured port when free, otherwise the bridge's default **8080** when free, and only then fails with the port-collision error naming both — it never binds over someone else's server, and the client follows whichever port was chosen. Discovery is Linux-only and read-only: calxgloss never kills or replaces a Ghidra it did not start, and an explicit URL that answers still wins untouched (issue #115, G1-T5).

- **Automatic headless Ghidra startup (G1-T4)** — every Ghidra command (`classify`, `translate`, `batch-translate`, `auto`, `auto-shim`) now finds its Ghidra server by itself instead of failing when none is running: if the configured port answers, it **attaches** to that server — a GUI Ghidra or a manually started headless one, which is never closed and never killed — and otherwise **starts a headless Ghidra server of its own**, using the bridge's own launch recipe, and shuts it down cleanly when the command ends (project closed, process killed, pid file removed). Starting one happens only when the doctor's install and extension checks pass (a failure names what is missing and where it goes) and only when the configured port is **free** — a port held by something else fails with a clear collision error naming the URL, never a bind over someone else's server, and a port answering as something other than GhidraMCP or an under-versioned plugin fails fast with the same named errors `doctor` gives. A started server appends its output to `headless.log` beside the run's project file, records its process id in `headless.pid`, runs with the bridge's program-selector requirement on (the incident fix's other half), and gets a ~90 s boot budget with a clean failure — naming the log — if the JVM dies mid-boot. No backwards compatibility: branches, refs, and workspaces from earlier runs are not migrated (issue #68).

No backwards compatibility (issue #69).

### Fixed

- **`auto` no longer panics on an explicitly named linker thunk** — when a batch's function list names a symbol the pipeline refuses as a linker import thunk (a `DelayLoad_*` symbol, say), the refusal is recorded **skipped**, not failed; but the skipped record was also delivered to the per-function completion callback as a success carrying no translated code, and the `auto` and `batch-translate` git-commit handlers assumed a success always carries code and unwrapped it — crashing the whole run mid-batch (the LaunchPad.exe panic). A refused unit never reaches the callback now: it was never attempted, so it has no code to write and no branch to clean up. Both CLI handlers additionally skip any unit with no translated code instead of unwrapping, so no future codeless-success can crash them either.
- **Scope controls treat one function as one entry however the binary is cased** — the skip and priority lists could hold two entries for the same (binary, function) pair when the operator spelled the binary name differently: the panel's add and remove operations compared the binary name exactly while the queue filter and panel readers compared it case-insensitively, so both spellings read as skipped/prioritized but removal only dropped the exact-cased entry. Every scope add, check, and remove now goes through one match rule: binary names match case-insensitively (Windows binary names are case-insensitive), function names match exactly (PE export and Ghidra symbol names are case-sensitive). A differently-cased add dedupes, and a differently-cased removal drops the entry. Fixes #107.
- **The live view's "needs calxgloss live" notice came back** — a plain `serve` answers `GET /api/progress/enhanced` with a static 404 so the live view can say honestly that it needs a running pipeline, but the API client had started surfacing the server's own error reason on failures and a static 404 carries HTML, not JSON, so the message fell back to the bare statusText ("Not Found"). The live view string-matched "404" in that message, missed, and showed the generic "request failed" empty state instead. The client now rides the HTTP status on the thrown error and the live view branches on `status === 404` — no message string-matching, so a server-supplied reason can never mask the status again. (Surfaced while consolidating the headless test helpers, issue #108.)
- **The LLM I/O view's Clear button now clears the log, not just the view** — Clear emptied the browser buffer while the persisted `re/analysis/llm_io/log.jsonl` kept every entry, so a reload (or re-entering the view) restored the history the operator had just cleared. The button now calls the new `POST /api/llm-io/clear` (shared routes, like its `GET` sibling), which deletes the log file and answers how many entries it dropped — idempotent, and a failed delete answers 500 rather than pretending the history is gone. If the server refuses, the view still clears but a toast says so, since the entries would return on the next reload.
- **The output-budget estimate was optimistic for code-heavy prompts** — `output_budget` sized the wire `max_tokens` as the window minus a chars/4 prompt estimate, but disassembly-and-template prompts tokenize denser (~3.4 chars/token measured): the EverQuest run's T2 prompt counted 3,561 real tokens against a 3,368 estimate, and the request overflowed the 172,000 window by ~200 tokens with a 400 on every retry. The estimate now assumes ~3 chars/token (keeping the 12.5% headroom), and a regression test pins the incident: the same prompt size must fit its real token count beside the cap.
- **Empty prompt sections no longer cost tokens** — the translation and escalation templates rendered every context section unconditionally, so a function with nothing to report still got a `## CALL GRAPH NEIGHBORS` header followed by "No call graph neighbors were available.", while `---` rules and template block-tag newlines padded every section with runs of blank lines. The escalate prompt alone carried fourteen such filler sections — pure prompt tokens carrying zero information, part of the context pressure behind the EverQuest run's 400s. Optional sections are now wrapped in a single conditional that drops the whole section when it has nothing to say, all `---` separators are gone, and every render passes through a blank-line normalizer so sections sit exactly one blank line apart. Tests that pinned the filler text now pin the section's absence.
- **The scratch PAL crate never compiled, failing every verification** — the embedded `stub_content.rs` template opened with `//!` module-doc lines, but the scratch `pal/src/lib.rs` splices it in with `include!`, and inner doc comments inside a macro expansion are rejected with E0753 ("can only appear before items"). Every translated function therefore failed compilation on scaffold code the LLM never wrote, and the retry loop burned attempts asking it to fix the verifier's own header. The template now uses plain `//` comments, and `ensure_pal_crate` compares the scratch file's *content* against the embedded template instead of mere existence — so an existing workspace's stale scaffold self-heals on the next run. A guard test pins that the template carries no `//!` lines, and a second test pins the self-heal.
- **Import thunks no longer ride the LLM** — a new built-in root pattern `^(DelayLoad_|_imp_|thunk_)` classifies delay-load stubs, IAT symbols, and Ghidra thunks as roots, so the batch pipeline stubs them deterministically instead of spending a translation unit (prompt + retries) on a one-instruction jump to the real API. The caller's translation reaches the API through the leaf/API mappings; the stub keeps the referenced symbol compiling. Surfaced while reading the EverQuest run's `DelayLoad_*` warnings — LaunchPad.exe alone is peppered with them.
- **An empty disassembly is now read as "no disassembly"** — the Ghidra bridge answers `disassemble_function` with a 200 and an empty body for functions that own no instructions (thunks and external imports have empty bodies, though the decompiler still follows them), which the client surfaced as `Ghidra reported an error: the server returned an empty response` and a `Could not read disassembly; reporting without it` warning on every `DelayLoad_*`-style thunk. The client now maps that response to an empty listing, the same shape the cross-reference endpoints already use for "no results".
- **Commits after Classifying staged nothing** — every classification record (and shim suggestion, translated source) failed to stage with git2's "repo path … should be relative": `commit`/`commit_to_main` passed the callers' workspace-joined absolute paths straight to `Index::add_path`, which only accepts repo-relative ones, so the post-classify commit landed empty while warning once per binary, and the translate/batch/auto commit failures were swallowed by `if let Ok(…)`. Both now normalize through a `repo_relative` helper that strips the workdir prefix — canonicalizing both sides on symlink or `..` mismatches — so absolute and relative paths stage alike.
- **Decompiler lines padded with trailing whitespace panicked the literal scanner** — `literal_at` indexed `line[i]` before checking bounds, while `literal_after_ws` and the bitpack detector's offset calls legitimately hand it an index at or past the line end, so a Ghidra line padded with spaces crashed the run with an index-out-of-bounds panic. The bounds check now comes first and the lookup answers `None`.
- **A clean start now creates the workspace git repo up front** — `live`/`auto` in a fresh folder left the dashboard popping "Not a Git repository" while the pipeline sat (silently, at the default log level) in the Ghidra preflight: `.git` was only created once translation actually started, deep after the preflight and classification. The workspace repo is now initialized at the top of the run (idempotent, honoring `--skip-git`), and the run prints a visible "Connecting to GhidraMCP…" line so the preflight no longer looks frozen. Fixes #123.
- **A warm run's activity heartbeat went silent** — the pipeline view's dashed sub-row under the processing binary (pass · function · "n of m") beat only on **live** decompiles, so once the Ghidra read cache had warmed, cached hits counted for nothing and the row rendered nothing under the `Working` badge. The heartbeat now counts *work items consumed*, not live round trips: a cached decompile beats just like a live one, and the pass's "n of m" stays honest warm or cold. Fixes #121.
- **Review actions can no longer silently disagree with git** — clicking Accept then Send Back fast on one unit let both actions read the unit's state at start, do their git work, and overwrite the unit's single action record — last write won. The dashboard could show SendBack while the code sat merged on main, and the pipeline might re-translate an accepted function. Each review action (accept, send-back, patch) now captures the unit's persisted action state at start and re-checks it before writing its own record: if a different action landed in the meantime, the action fails with a conflict error naming the state that won (HTTP 409) and leaves the record untouched, with an in-process lock making the re-check and the write atomic. Send-back and patch on an already-accepted unit are now refused outright — the code is merged and there is no un-merge path. Fixes #86.
- **A stalled browser tab no longer freezes live updates** — one hidden or background-throttled tab that stopped draining its WebSocket could block the broadcast loop on its full send buffer: every other tab's live view stalled with it, the server's own in-memory progress state waited in the same loop, and the upstream event channel overflowed and dropped events ("Lagged"), leaving rows stale until a reconnect. Delivery is now non-blocking — each message is handed to every client's buffer without ever waiting on a client — and a client whose buffer is full is disconnected instead; the browser reconnects and resyncs from a fresh snapshot like after any other drop. Fixes #85.
- **Double patch clicks no longer double the retry** — clicking "Request Patch" twice on the same unit computed the same next attempt twice, created the same v{N+1} branch twice, and spawned two background retry loops racing on one branch — double LLM cost and commits overwriting each other. The patch action now reads the unit's persisted action record first: if the next attempt already records a patch request, the response says `patch_already_in_progress` and nothing new is created — one branch, one record, one retry. A request after a previous patch attempt *finished* (the unit back in review at the new attempt) still starts a fresh attempt as before. Fixes #84.
- **Accepting a conflicting unit fails honestly** — accepting a unit whose branch can no longer merge cleanly onto main died deep in the merge and surfaced as an opaque internal error, and the web accept path could still record the unit as Accepted even though none of its code landed on main. The merge now checks for conflicts before committing anything: the reviewer is told exactly which files conflict, main is left untouched, the unit keeps its pre-accept status, and the accept record under `re/accepts/` says `conflicts:` instead of claiming a merge happened. Clean merges are unchanged — and the 3-way path, which previously failed at the tree-write step for every diverged branch, now actually produces the merge commit. Fixes #83.
- **Run logs survive a crash mid-save** — killing the process while a JSON artifact (token-usage log, fault log, experiment log, call graph, analysis cache, work-unit document) was being written could leave a half-written file where a valid document used to be; the next read failed to parse it, the logger logged "starting fresh", and the run's entire token/fault history was overwritten. Every persisted JSON document is now written atomically: the new document lands in a temp file beside the target and is renamed onto it, so a reader — or a crash — always sees either the previous complete document or the new one, never a truncated mix. Fixes #81.
- **Phantom-clean evidence scans when every decompile failed** — with several Ghidra CodeBrowser windows open the bridge can answer a scan's function listing from one program and its decompiles from another; every decompile then fails, and the evidence scans used to skip every function and finish "successfully", persisting an empty record under the target binary's name that was indistinguishable from a genuinely clean scan. The nine evidence scans now carry a skip-rate breaker: once more than half the function listing fails to decompile, the scan aborts with an error naming the counts ("Ghidra failed to decompile N of M functions — is the right program open?") and nothing is persisted. The detector now resolves candidates against the workspace's classified binaries — verbatim or by stem, any extension — and returns the inventory's spelling verbatim; an extension-less candidate matching no real binary resolves to nothing rather than a fabricated identity. Fixes #70.
- **Dashboard baseline test counts never showed** — the review queue's baseline columns, the CLI dashboard, and the quality summary's baseline pass rate all rendered `—` even when baseline artifacts existed on disk: the dashboard's baseline scan looked for `baseline.json` directly under each binary directory instead of the per-function subdirectory the test generator writes, and the unit-side lookup cut the unit key at the wrong path segment, so the two sides never joined. Baseline artifacts under `re/baseline/{file}/{func}/baseline.json` now attach to their units on the verbatim `{binary filename}/{function}` identity, keeping `foo.dll` and `foo.exe` workspaces distinct. Fixes #67.
- **Dashboard bounce and graph reshuffle during live runs** — every progress event kicked off a full git-backed dashboard rebuild: the status-card row was wiped and rebuilt (the server status card living inside it was removed and re-added every time), and the dependency graph's node order followed the builder's filesystem input order, so the graph view re-ran its layered layout with reshuffled binaries every few seconds. WS-triggered refreshes are now coalesced into one rebuild per short window, status cards and the server card update in place only when their values change, and the dashboard's dependency graph orders its nodes and edges deterministically — the layout stays put unless the data actually moved.
- **Crate-replacement classifications read back honestly** — the `classify` command serializes `Strategy` as an enum: `PalMapping`/`ReverseEngineer` land as bare strings, but `CrateReplacement` lands as a tagged object (`{"CrateReplacement": {"crate_name": "steamworks"}}`). Both readers of `re/classify/*.json` assumed a string: the pipeline tab hydrated those binaries with an empty strategy — rendering them "Unclassified" after a restart despite correct records on disk — and the dashboard's unit view failed the whole record parse, losing even the category. Both now read the variant name from either form, so steam_api64.dll and the v8 family keep their Crate Replacement classification across restarts.

## [0.2.0] — 2026-10-06

### Added

#### Output & pipeline

- **Crate-based output layout** — `translate` and `batch-translate` now produce `crates/<dll_stripped>/Cargo.toml` and one `src/<function>.rs` per function (DLL/EXE extension stripped, e.g. `EqGame.exe` → crate `EqGame`), with an auto-generated `mod.rs` registering every translated function.
- **Complexity-based prompt selection** — functions are classified by instruction count, branch density, call depth, and API-category diversity, and routed to a Minimal, Standard, Rich, or Detailed prompt with matching Ghidra context.
- **Failure-informed retry prompts** — every retry strategy injects a "PREVIOUS ATTEMPT HISTORY" section into the prompt when prior attempts failed, so the LLM can learn from specific past mistakes.
- **Per-attempt token usage logging** — every LLM call (initial, retry, and tier-escalated attempts) records token counts with DLL, function, attempt, strategy, context tier, and outcome to `re/analysis/token_usage.json`; the batch summary prints a total-tokens line.
- **Experiment logging** — each retry attempt is recorded to `re/analysis/prompt_strategy_log.json` with category, strategy, and outcome, and aggregate pass/fail stats can be computed from it.

#### Context tiers

- **Context tier selection** — five context tiers (`Signature`, `Disassembly`, `WithTests`, `ModuleContext`, `FullModule`) define how much context is sent to the LLM per function; the starting tier is chosen automatically from function complexity and API call count. Each tier has its own prompt, from a minimal signature-only prompt up to full-module context with neighboring functions, shared data structures, shim layer source, and PAL trait definitions.
- **Automatic context tier escalation** — a failed retry can bump the context tier to the next level and rebuild the prompt with escalated context, independently of strategy escalation.

#### Fault detection & analysis logging

- **Fault logging** — detected faults are persisted to `re/analysis/fault_log.json` with aggregate statistics.
- **Context-window detection** — LLM responses are checked against the model limit for truncation markers and oversized prompts are pre-checked; disassembly can be split into chunks for the LLM.
- **Hallucination detection** — generated code is cross-referenced against Ghidra symbols and the PAL catalogue; non-existent API references are logged and emitted as progress events.
- **Infinite-loop detection** — repeated identical (prompt, output) pairs across retries are detected before more tokens are wasted on a dead-end path.
- **Behavior-divergence detection** — code that passes baseline tests but fails generated edge-case inputs is flagged in the retry loop with confidence scoring and recovery advice.
- **Resource-exhaustion monitoring** — repeated failures and timeouts (OOM, swap thrash, HTTP 429/503/507) are tracked; the retry loop backs off, logs faults, and can suggest queueing work or switching models.

#### New analysis crates

All evidence results are saved as per-binary JSON documents under `re/analysis/<name>/<dll>.json`, carry shared scan provenance (binary name, finish timestamp, duration), and score findings with a shared 0–100 `Confidence` type.

- **`calxgloss-typesdb` — data structure recovery**: recovers named types from the Ghidra Type Manager, detects vtables (resolving method pointers and the MSVC RTTI chain to class and base-class names, flagging COM interfaces), and infers struct candidates from string literals.
- **`calxgloss-typeinfer` — type inference**: detects C++ `this` pointers from vtable dispatch, narrows parameter types from string-function usage and integer bit patterns, and propagates types from known signatures (`malloc`, `strlen`, `CreateFileW`, …); competing readings are resolved by confidence.
- **`calxgloss-algorithm` — algorithm recognition**: recognizes algorithm families (sorting, hashing, checksums, compression, …) from control-flow signatures, string markers, and callback contracts (e.g. a `qsort` compare function).
- **`calxgloss-memory` — memory lifecycle / RAII detection**: pairs allocations with releases (suggesting `Box<T>`/`Vec<T>`, or stack allocation for short-lived blocks), handle opens with closes (RAII guard suggestions), and reference-count bumps with drops (`Rc<T>`, narrowed to `Arc<T>` when shared across threads).
- **`calxgloss-sync` — concurrency detection**: pairs lock acquires with releases (`Mutex`/`RwLock`), detects interlocked/atomic calls (`AtomicU32`/`AtomicU64`), and thread spawns with or without joins (`std::thread::spawn` vs `tokio::spawn`).
- **`calxgloss-callback` — callback & function-pointer detection**: finds calls through function-pointer arrays, registration→callback pairs, and jump-table dispatches, suggesting `Vec<Box<dyn Fn(...)>>`, `Box<dyn Fn(...)>`, or `match`/dispatch tables.
- **`calxgloss-controlflow` — control-flow pattern recognition**: detects switch-shaped if-else chains, self-recursion (with tail-call detection), and state-machine patterns, suggesting `match`, loops, or `enum State`.
- **`calxgloss-stringctx` — string & configuration context**: classifies strings into nine categories (format strings, paths, error messages, …), maps strings to functions through body parsing and xrefs, and infers argument types from format specifiers.
- **`calxgloss-apidetect` — library & API identification**: identifies linked libraries from the import table and maps them to Rust crates (DirectX 9, SDL2, zlib, PNG, the C runtime, …), and summarizes which APIs each function reaches directly or through its callees.
- **`calxgloss-consts` — constant & enum recovery**: recovers bitflag groups from bitwise operations, enum candidates from contiguous switch cases, and repeated literals as named constants.
- **`calxgloss-serialize` — endianness & serialization detection**: detects byte-swap calls, bit-packing shift/mask chains, and magic-byte comparisons (PNG, gzip, ZIP), suggesting `byteorder` readers, field masking, or format decoders.

#### `calxgloss-ghidra`

- **New bridge capabilities** — auto-paged string, data-type, and data-item listings, struct layout and enum value lookups, raw memory reads, function tagging, and multi-program support (list open programs and switch which one queries run against).

#### `calxgloss-cli`

- **On-demand analysis commands** — `typesdb`, `typeinfer`, `algorithm`, `memory`, `sync`, `controlflow`, `callback`, `stringctx`, `apidetect`, `consts`, and `serialize` each run their scan against the program open in Ghidra and save the result to the matching `re/analysis/<name>/<dll>.json` cache the batch pipeline consumes. `--show` prints a cached result (counts, confidence, findings) without connecting to Ghidra; `--no-tag` keeps the vtable scan read-only.
- **`auto` subcommand** — detects project state and continues the workflow automatically: scans the target directory for DLLs, runs classification when records are missing, then batch-translates. Running with no subcommand is equivalent to `auto`. Supports `--target`, `--dlls`, `--all-functions`, `--classify-only`, `--skip-git`.
- **`init` subcommand** — creates a `calxgloss.toml` with a fully commented template of every `[ghidra]` and `[llm]` key.
- **`auto-shim` subcommand** — generates shim layers for all crate-replacement DLLs: API mappings (LLM) → source code → tests → verify → persist to `re/shims/<dll>/`, committed to git.
- **`dashboard` subcommand** — builds and renders a review dashboard from git branches and records, with `view`, `accept`, `reject`, and `accept-all` (dependency-ordered batch acceptance) and a `--follow` watch mode.
- **`serve` subcommand** — starts the web review UI HTTP server (port 3000 by default).
- **`live` subcommand** — runs batch translation and the web UI concurrently in one process, streaming progress over WebSocket.
- **`gc` subcommand** — archives stale unmerged translation branches to `refs/archive/…` instead of deleting them, with `--days` and `--dry-run`.
- **Config-driven directories** — `target_dir` and `workspace` can be set in `calxgloss.toml` or overridden by the global `--target-dir` / `--workspace` flags; `live` and `serve` use CWD unless explicitly overridden.
- **Incremental git commits during batch translation** — each function is committed and merged as soon as it succeeds, rather than deferring all git work to the end of the batch.
- **`classify` generates shim layer suggestions** — complexity estimates for crate-replacement DLLs are persisted to `re/shims/suggestions.json`.

#### Git & review workflow

- **Review records** — accepting a branch writes an acceptance record to `re/accepts/`, sending it back writes a rejection record to `re/rejections/`, and archiving renames a stale branch to `refs/archive/…` so it stays reachable.
- **Shim-layer dependency enforcement on branch creation** — branch creation can check that required shim layers (e.g. `d3d9.dll` → `re/shim/wgpu`) are already merged, in `Skip`/`Warn`/`Enforce` modes.
- **Dependency graph** — a DAG of DLL classifications → shim layers → function translations is built from classifications and call graph data, persisted to `re/analysis/dependency_graph.json`, and topologically ordered (level-aware) for batch operations.
- **Shim layer generation** — API mappings are generated by the LLM, shim source code (complete or skeletal) and per-mapping tests with mock call recorders are generated from the mapping table, and shim layers are verified in a sandboxed Cargo project.

#### Web review UI

- **Axum API server** (`server` feature) — dashboard, unit detail, dependency graph, dependency-sorted queue, line-by-line diff, Ghidra context, and health endpoints, plus accept / send-back / patch review actions wired into git and the translation pipeline (a patch request spawns a retry translation).
- **WebSocket progress streaming** — pipeline milestones, per-attempt status, and full LLM request/response events stream to the UI; a live "LLM I/O" tab shows the log.
- **Dependency-sorted review queue** — queue endpoints and the dashboard report dependency-ordered units with queue metadata and position; `Blocked` units are flagged.
- **Diff & Ghidra context viewers** — tabbed detail panel with line-by-line highlighted diffs against `main` and decompiler/disassembly context from on-disk analysis artifacts.
- **Interactive dependency graph** — layered layout with Bézier edges, hover tooltips, click-to-select with neighbor highlighting, click-to-detail, status dots, fit-to-view, wheel zoom toward cursor, and keyboard shortcuts.
- **Live progress panel** — per-DLL classification/strategy, in-progress translation with progress bar, and batch completion counts; completed functions mark their unit `Complete` in real time.
- **Stale branch cleanup** — a "Stale Branches" dashboard card and a "Branch Cleanup" view list unmerged branches past a staleness threshold and archive them from the UI.

#### `calxgloss-types`

- **Review dashboard data model** — work units, review statuses, dependency graph, status counts, and review actions shared across reports, web, and CLI, replacing the duplicate scaffolding in `calxgloss-web`.
- **Dependency-ordered queueing** — units carry processing levels (classification → shim → PAL → test → function → integration → fix), the dependency graph topologically sorts with level tie-breaking, and the dashboard auto-blocks units whose dependencies are in a failing state.
- **Typed progress events** — a serializable `ProgressEvent` enum (translation milestones, per-attempt completion, context tier selection, fault detections, LLM request/response) published over a broadcast channel for WebSocket transport.
- **Shim layer types** — API mappings, layers, complexity scores, and per-DLL shim suggestions with estimated complexity and confidence, produced from classification data without an LLM call.

### Changed

#### Vocabulary

- **Unified on *workspace*** — one directory, one name: `--repo-dir` is now `--workspace`, the config key `repo_dir` is now `workspace`, and `CALXGLOSS_REPO_DIR` is now `CALXGLOSS_WORKSPACE`. `translate`/`batch-translate` lost `--output-dir` (output always lands in the resolved workspace), and dead per-command `--repo` flags are gone.
- **Terminology corrections** — `ContextTier::Stub` → `Signature` ("stub" is reserved for mocks); FFI *stub* → FFI *binding* (the generated block calls the real DLL); `WorkUnitKind`/`WorkUnitLevel` → `WorkKind`/`WorkLevel`; `ReviewStatus::Merged` dropped (merging is the git effect of Accept, not a second verdict); the scratch PAL package renamed `calxgloss-pal` → `calxgloss-verify-pal`.
- **Confidence scales disambiguated** — evidence confidence (0–100, shared `Confidence` type), unit confidence (`unit_confidence`, 0.0–1.0), and fault-diagnosis confidence (`fault_confidence`, 0–10) now have distinct names.

#### Workspace layout

- **Reorganized `crates/` into the 5-context layout from `GLOSSARY-MAP.md`** — `crates/pipeline/`, `crates/evidence/`, `crates/integrations/`, `crates/interface/`, and `crates/shared/`, with the meta-crate re-exporting every library crate except `calxgloss-web`.

#### GhidraMCP 6.x migration

- **Migrated `calxgloss-ghidra` to the bethington GhidraMCP bridge** (v6.0.0, replacing the deprecated LaurieWired extension): snake_case endpoint surface, JSON response and error support, and name-based decompilation resolved through `search_functions`.

#### Pipeline & prompts

- **Evidence pre-analysis in batch translation** — `batch_translate` and `batch_translate_from_callgraph` run each evidence scan (type database, type inference, algorithm, memory, sync, callback, control flow, string context, API, constants, serialization) at the start of a batch when its cache file is missing; a missing workspace, unreachable Ghidra server, or failed save only logs a warning and the batch proceeds.
- **Analysis context in prompts** — the escalate prompt (and, for control flow, the ModuleContext and FullModule translation tiers) reads the persisted evidence caches and renders sections for recognized algorithms, memory lifecycle, concurrency, callbacks, control flow, strings, APIs, and constants; a missing or corrupt cache degrades to no context rather than failing the prompt.
- **Type and data-structure context from persisted caches** — the previously stubbed prompt context extractors now load the type inference and type database caches and keep the records tied to the target function.
- **Translation attempts record their context tier**, enabling post-hoc analysis of which context scope yields the best pass rates.
- **Boxed pipeline futures** — the retry loop's futures are boxed so downstream `Send` checks stop at the boundary instead of overflowing the compiler's trait-evaluation recursion limit.
- **`classify_dlls` reads PE headers** for accurate per-DLL export/import counts instead of the stale counts from whichever program happens to be open in Ghidra.
- **Classification records persisted to disk** — `classify` writes `re/classify/{dll}.json` and commits to `main`; later `auto` runs skip re-classification.

### Fixed

- **Wrapped decompiler signatures parse** — Ghidra's multi-line signature lines failed to parse, so every engine that scans all functions silently skipped those functions (~41 of eqmain.dll's 4,358). Signatures are now joined until the parameter list or body begins. Fixes #54.
- **Dashboard dependency edges (issue #10)** — the builder now wires the shim→function dependency edge the branch-creation policy already checks, so a sent-back shim cascades `Blocked` to everything translating on top of it; the classify edge's DLL matching and shim unit classification were also corrected. The `Blocked` cascade no longer leaves `StatusCounts` stale.
- **Review verdict durability (issue #9)** — the dashboard builder now reads send-back and patch-request records, so `SendBack`/`PatchRequested` survive rebuilds and failing roots can cascade `Blocked`. Patch records written before this change read unchanged.
- **`read_all_patch_records` walked the wrong tree depth** — it never found records at `re/patches/{dll}/{function}/vN.json`, leaving `PendingReview` unreachable in built dashboards.
- **Review actions 500'd on slashed unit ids** — accept/send-back/patch failed at the audit-trail write because nested parent directories under `re/actions/` were not created.
- **Default allocator names missed Ghidra's underscore-form `operator_new`/`operator_delete`** — the live 6.x decompiler writes the underscore form in function bodies, so whole-name matching never fired and allocation findings were missed. The default sets now carry both spellings. Fixes #6.
- **`println_content` blanked lines carrying multi-byte characters** — the report-line padding helper compared byte length against the column width while truncation counted characters, printing some short lines empty. It now counts visible characters.
- **Axum 0.8 route syntax** — routers used the legacy `:id` capture syntax that panicked on startup; all routes now use `{id}`.
- **Static file serving** — assets resolved against the process CWD instead of the crate directory, and the fallback extractor was incompatible with `fallback_service`, so JS and CSS returned 404.
- **Live units 404'd in the unit detail endpoint** — the endpoint now consults the live progress state and creates synthetic in-progress units.
- **LLM request/response log rendered HTML-entity-encoded** — content now renders as raw text with minimal escaping, so JSON and code display correctly.
- **`showDetail` body scope** — the error handler could not reference `body`; the declaration moved outside the `try/catch`.
- **`merge_to_main` stale main reference** — a cached ref handle caused merged branch file changes to be lost on hard reset.
- **Empty cross-reference responses** — a 200 with empty body from GhidraMCP (no callers/callees) is now treated as a valid empty result instead of an error.
- **Trims leading/trailing whitespace** from disassembly and decompiler output before sending to the LLM, keeping prompts cleaner and avoiding wasted tokens.
