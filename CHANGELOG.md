## [Unreleased]

### Added

#### Scan tracer (P53)

- **Every pre-batch evidence scan gets a named row in the live view, from emit to panel (P53.1, issue #428)** — the scan phase reports every registered scan to the progress stream: a started event when it spawns the scan and a completed event when the join lands, naming the wall-clock seconds from spawn. The completed event carries the finding count where the row names a single one. The type-database row files named types, vtables, and inferred structs separately, so it reports no count at all, and a cached hit or failed scan reports none either — the event leaves the findings field out, never a zero. The web progress store keeps one record per scan name for the binary whose pass is in flight: running from the started event, settled by the completed event, replaced when the same scan re-runs, and cleared when scan traffic or a batch naming the next binary opens a new pass. `GET /api/progress/enhanced` serves the records in scan-name order. The live view grows an evidence-scan panel with no reload needed: a running scan names itself beside a ticking clock, a finished scan shows its elapsed seconds and its finding count or the words `no single count`, and before the first started event the panel says the scan phase has not started rather than implying a count. Scan names ride the registry's own table, so a newly registered scan appears in the panel with no edit to the panel or the pair test. Cold and warm passes both emit the pairs, following the warm-replay convention of issue #121. The new events stay batch-level: they name no unit and move no unit phase.

- **A failed scan and an unreported finding count read honestly on the live scan panel (P53.2, issue #429)** — a scan whose evidence engine fails ends with its own completed event, marked failed. The event carries the failure's own words, and the finding count stays unknown — never a zero. A scan task that crashes inside the concurrent window is caught and reported the same way, while its sibling scans keep running to their own completed events undisturbed. The served payload and the live view carry that reading end to end: a failed row shows a failed chip beside its error text, a count that was never reported shows the words `findings: unknown` rather than a number, and a failed row reads apart from a completed one at a glance. One failing or crashing scan leaves every other scan's started/completed pair intact.

- **The worklist tick line shows Kuna's current function beside the in-flight pass, cold call-graph build included (P53.3, issue #430)** — the live progress payload grows the working pass's latest heartbeat beside its scan records. The record names the pass, the function Kuna is decompiling, and the position in the pass's work list. No new event exists, and no new heartbeat is added. The payload carries the same `BatchProgress` heartbeat the pipeline binary row already shows, beating once per unique function. The live view's scan panel draws the record as one tick line beside the running scan: `evidence scans · FUN_1800412a0 · 1,200/7,267`. Each later heartbeat moves the function and the position on that line, with no page reload. The line names whatever pass is working, so the cold call-graph build shows the same line under the call-graph pass name. The silent windows between scan completions and the first unit stop being silent. A pass with no per-item granularity shows its name alone: the unknown position parts stay out of the payload and off the line, never a fabricated `0/7,267`. A batch summary or the next binary's pass start clears the record, exactly as it clears the scan rows.

#### Conformance verdict (P26)

- **The web review surfaces render the one conformance verdict, and the unit detail renders its obligation entry (P26.8, issue #424)** — the queue view now shows each binary's *conformance verdict* and its disposition tallies above the item list, and an empty queue never hides the honest verdict. The unit detail shows the unit's own *obligation entry*: the attempt it speaks for, the owner digest, the required case kinds, the disposition standing at the read, and the receipt citation — and where the reviewer's skip or park record stands for the unit, the read seam shows that record's disposition beside its reason, exactly as the per-binary row tallies it. Both readings ride the shared model: the dashboard build runs one ledger read and one live-record join, the web server copies the fields into its payloads, and the browser only turns JSON into words — no surface computes a second derivation, so the two can never disagree. Older payloads still read: a unit document that predates the obligation field, a binary with no filed ledger, a ledger that names no entry for the unit, and a payload with no conformance rows all still render, and each surface spells the *unknown* reading out — "never a clean run", "never shown as zero obligations" — never a zero and never a closed obligation. The standing rule keeps its pins at this seam too: a filed verdict leaves every unit's review status exactly as it was, writes no review action record, merges no branch, and blocks no Accept. ADR-0060 closes the honesty lineage that ADR-0053 opened: the ledger is a record that never acts, review stays the only door into verified, no disposition ever aggregates into a pass, and every build re-derives the verdict instead of storing one.

- **A green claim must prove what it says: the cited receipt stamps the kinds of try it covered, and an exe binary waits on its scenario verdict (P26.5, issue #421)** — the conformance read now closes a claimed-green obligation only on evidence it can prove from filed bytes. The **verification receipt** states the case kinds its suite actually exercised: the verify engine collects each baseline case's declared kind onto the receipt's face, the Markdown twin prints the same list, and the stamp never guesses — a case that declared no kind adds nothing, a run that never compiled covers nothing, and a receipt filed before the field existed reads as covering nothing, never as covering everything. At the close check, every kind the ledger entry requires must stand among the kinds the cited receipt stamps; a green run that never tried a required class — no malformed input, say — keeps the obligation open and names the missing kinds as the first broken link. For an exe binary, unit evidence alone never closes an obligation: the scenario lane is what shows the translated unit actually runs and behaves. The read looks for a **scenario verdict** filed under `re/scenarios/verdicts/`, named for the binary and the scenario, claiming complete equivalence on its face — and it re-derives that document's stamped digest from the filed bytes before trusting any of it, so a verdict edited after filing claims nothing at all. Without such a verdict the row reads *incomplete* and names the scenario verdict lane as the open link: an absent verdict reads as its own honest negative rather than an invented cause, and the FFI gate never closes an entry on its own. Injected-fault pins at the dashboard-build seam hold each refusal: a citation naming another unit's receipt, a suite missing a required kind, an old receipt that stamps no kinds, a verdict claiming only partial equivalence, a stray document filed under the wrong name, and a verdict whose bytes no longer match its stamped digest — each keeps the row short of *complete* and names what broke. The same seam pins the way through: settled and dismissed unknown records stay out of the gate's refusal, and a fully closed exe row with a filed complete-equivalence verdict reads *complete*.

- **Every unverified unit says why at the dashboard build: the read seam joins the ledger with the reviewer's live records (P26.4, issue #420)** — the conformance read now joins the filed obligation ledger with the reviewer's live records: the skip set, the classification records and their overrides, the unit override records, the review-action records, and branch state. A unit the reviewer's skip set names reads *skipped*, and its provenance names `re/review/skips.json`. A binary whose in-force classification is Do Not Translate parks every unit under it, and the classification's own reason rides beside the disposition — however green each unit's claim looks. An operator classification override releases those obligations outright: once the in-force category is no longer Do Not Translate, nothing parks the units, and the same evidence closes them. A reviewer override record at `re/analysis/unit_overrides.json` overrides a unit's system judgment at the read, so that unit tallies *overridden* and never counts as verified, even over a fully-evidenced green claim. A branch merged into main with no standing Accept review action reads *un-reviewed*: review, not the merge, is the only door into verified, and the unit tallies in its own count. Every disposition holds its obligation open and blocks a *complete* verdict on its own, tallied apart from the verified in the model, the JSON, and the terminal sentence. Where no live record speaks for a unit, the ledger's own filed disposition stands, and its provenance says so plainly. The precedence at the read: classification park first, then the reviewer skip, then the reviewer override, then the entry's recorded disposition, and last the claim's own evidence walk. The layer still stores nothing and touches nothing. The join shares the same skip set, parked classifications, and override handle that the review surfaces already read, rather than keeping a second copy to drift.

- **The dashboard answers, for every binary the obligation gate ran, whether the restitch actually closed end to end (P26.3, issue #419)** — on each build the dashboard derives one *conformance verdict* per target binary, prints it in its own section, and carries the same rows in the shared JSON model. A binary reads *complete* only when every filed obligation walks back through checked evidence. The attempt branch stands, its tip is still the commit the entry pinned, and the cited receipt pair is committed there and seals to the cited digest. The pair speaks for this exact unit and attempt, its verdict is *passed*, an Accept review action stands, and the branch is merged into main. The verdict carries the ledger's closure digest beside it. Anything still open reads *incomplete*. The row names the first obligation whose chain broke — function, attempt, and the link that gave way — and it names a blocking unknown that shut the gate. *Skipped*, *parked*, *overridden*, *un-reviewed*, and *no-baseline* obligations get their own tallies, held apart from the verified. A ledger never filed, an empty roster, tampered or replaced ledger bytes, or a receipt citation no branch can resolve reads *unknown* with its cause named at the read: *no ledger filed*, *digest mismatch*, *no obligations filed*, *unresolvable receipt citation*. The dashboard build itself survives the bad input, and a tampered document's input error is printed where the operator sees it. Every new model field reads *unknown*, never a pass and never a silent zero, when an older document lacks it. The verdict is never stored. Each build recomputes it from the repository, so a document tampered between builds changes the next build's answer. The verdict layer decides nothing: it writes no branch, no Accept action, and no review status. Only translated units' binaries get a row — shim and classification branches are not target binaries.

#### Baseline case kinds (P26)

- **Baseline cases now state which kind of try they are: an ordinary try, an error-path try, or a malformed try (P26.2, issue #418)** — every case the test generator produces carries its case kind from the moment it is born. The generator's intent is recorded, not guessed later. Values derived from the declared signature ask the unit for its normal job. A value the body's own comparison guards named, and every probe built from a recorded branch, aims at an error path and is stamped as such. No ordinary malformed-try producer exists in the harness yet, and it does not pretend otherwise: the roster stays closed, and a later ticket adds that producer together with its kind. A baseline document filed before kinds existed reads back with the kind absent, and nothing invents one on its behalf. So a later check that requires certain kinds of try fails closed against an old suite instead of letting it quietly pass for one it never exercised.

#### Obligation ledger (P26)

- **The done claim grows its document: per-unit obligations, closed rosters, and a seal a reader re-derives (P26.1, issue #417)** — one obligation ledger files per target binary at `re/obligations/<binary identity>.json`, beside the unknown ledgers and keyed by the binary's name exactly as it is on disk. Each entry names one obligation: the unit's function and attempt, an owner that pins a green claim to the exact content it was made about, the kinds of try the unit's baseline suite must cover, a verifier-receipt citation wherever the unit claims green, and a standing from a closed roster of honest facts. A claimed-green entry with no cited receipt is not a valid record. Invented kinds and invented standings refuse at the door, and no free-text status exists anywhere. The document says which binary it speaks for and when it was filed; a document missing either is refused, not read. The ledger seals itself with a closure digest over its own content. The same records written in another order seal to the same digest, and any content edit seals a different one, so a reader who never saw the writer proves the seal from the filed bytes alone — a tampered or misfiled ledger is caught, never read as clean. Unchanged records refiled at a later batch keep their seal, so successive batches diff by digest to see exactly what moved. A missing ledger reads as recomputable-missing; corrupt, tampered, or replaced bytes fail loudly. Nothing files a ledger yet: the shape lands ahead of its owners.

#### Verification receipts (P25)

- **The verification-receipt vocabulary: the record, its content digest, and the `re/verification` route (P25.1, issue #410)** — the durable shape every verifier will file: the **verification receipt** names the verified unit (binary identity, function, 1-based attempt, retry strategy, attempt path), the gate that judged it (compile-only vs compile-and-baseline-test), the baseline suite it was earned against (by digest, never by copy), per-dimension counts keyed by dimension name so P23's mined-input and P24's scenario dimensions join additively with no record rewrite, the timings of each leg and the whole run, the closed verdict set — passed / tests-failed / compile-failed / harness-error — so a harness fault is never mistaken for a unit verdict, and the record's own **content digest**: sha256 over the document's JSON with the digest field blanked, the same fold the *scenario verdict* carries, so a reader of filed bytes alone re-derives the citation P26's ledger will hold a verified unit by. It files per unit per attempt at `re/verification/<binary identity>/<function>/attempt-<n>.json`, so a v1 verdict and its v2 fix stand one name apart in one directory and diff side by side across attempt branches; filed receipts are never edited in place. Nothing files receipts yet at this point — the vocabulary lands before the writers, the track's prefactor.

- **Every verify run files its digest-paired receipt pair, and the verify command prints the citation (P25.2, issue #411)** — the *verifier owns its own receipt*: every `calxgloss-verify` run files a **verification receipt** pair under the record convention beside `re/baseline/` — the JSON authority plus its human-readable Markdown twin at `re/verification/<binary identity>/<function>/attempt-<n>.json`/`.md` — **paired by content digest**: the Markdown carries the JSON's own digest, and a reader holding only the pair re-derives the digest over the JSON's filed bytes; edit one file and the pairing fails loudly. Every run files, pass or fail: `passed`, `tests-failed`, and `compile-failed` each leave their record with the matching verdict, and a `tests-failed` verdict never rests on counts alone — the diverged baseline cases are named by position on both sides of the pair. The record states the gate as actually invoked — a compile-failed run or a zero-case suite never claims the full baseline-test gate — and names the **baseline-suite digest**: sha256 over the canonical encoding of the case suite actually fed in, with the baseline file's location riding the fold when one existed (relative to the record tree, never machine-specific), and an empty suite filing its explicit digest, never a missing field. The dimension map mirrors the returned result's facts exactly: a case whose value matched while its observed route diverged reads as a values pass and a trace fail, each dimension counting only what it was qualified to assess (ADR-0057's honesty rule). The engine hands the filed document back beside the result as a `VerificationRun`, so commit sites (#413) can stage the pair onto the attempt branch without re-reading the record tree; the retry ladder records its attempt number and strategy (the prompt shape earns its own name in #412), and a filed pair is never edited in place — the next attempt writes its own beside the earlier verdict, byte-identical. The standalone `verify` command files the pair, prints its content digest — the handle a green claim cites — and commits nothing. The Markdown rendering is the record's own fold: it ships inside `calxgloss-types` beside the JSON so the document can never render a story its facts don't tell (the renderer cannot live in `calxgloss-reports` as the spec first sketched — reports depend on the translator, which depends on verify, so verify could not call it — and the review surface keeps its contract through a re-export with a pin test). Pins: the compile-backed primary seam drives the real verifier against a real scratch project and runner — a passing run's pair with dimension counts mirroring the returned result, digest pairing proven by re-derivation and broken on purpose by tampering, a tests-failed pair naming its cases, a trace divergence with a matching value splitting the dimension counts, a compile-failed run assessing nothing on a compile-only gate, an empty suite's explicit digest, a filed baseline file's location riding the fold, attempts keyed one name apart with the earlier pair byte-identical — plus a process-level CLI e2e proving the command files, prints, and commits nothing, and a record-seam pin for the fold and the rendering.

- **The attempt-branch commit stages the verified pass's receipt pair (P25.4, issue #413)** — the branch checkout now answers "what stood behind this commit?" with no pipeline running. `calxgloss-git` grows the one helper that resolves a unit's *verification receipt* pair: `GitManager::receipt_pair_paths` names the JSON authority and its Markdown twin, repo-relative, under the standing `re/verification/<binary identity>/<function>/attempt-<n>` route — no commit site re-derives the file names. The `translate`, `batch-translate`, and `auto` commands stage the pair into the attempt-branch commits they already make, all three sites through one shared staging helper, the batch and auto sites citing the ladder's winning attempt: the last pass the verify gate cleared, whose verdict the ladder's `compiled` and test counts already carry (P25.3, #412). Staging is pair-or-nothing and existence-gated: a pair the gate actually filed rides the commit as filed bytes, and an absent pair changes the commit not at all — the green claim stays uncitable, visibly, and nothing is fabricated. The committed JSON stays stable-ordered — `binary` before `attempt`, `verdict` before `failed_cases` before `digest`, never alphabetical — so `git diff` between attempt branches reads the record cleanly. Pins: a temp-repo commit test files a real persisted receipt pair and asserts both members land in the commit tree with the staged JSON byte-identical to the filed bytes in declaration order; the absent-pair pin proves the commit carries only the code, nothing invented; and the CLI seam pins the committed file list — code plus pair, or code alone — not helper internals, with commit messages byte-for-byte unchanged.

- **The web patch-retry commit stages the pair, closing the four commit sites (P25.5, issue #414)** — the last of the commit sites the P25 spec names: the web's patch-retry action now stages the verified pass's **verification receipt** pair into the same attempt-branch commit it already makes, beside the translated code, citing the retry ladder's winning attempt — the last attempt the verify gate cleared — the pattern the `translate`, `batch-translate`, and `auto` commands set (P25.4, #413). Staging stays pair-or-nothing and existence-gated: a pair the gate actually filed rides the commit as filed bytes, and an absent pair changes the commit not at all — the green claim stays uncitable, visibly, and nothing is fabricated. The patch record now names the very commit that carries the code and its pair: the attempt branch no longer grows a trailing no-op commit whose contents could drift from what the record vouches for. With the web site staged, all four sites — `translate`, `batch-translate`, `auto`, and patch-retry — carry the pair, and the claim that a pass's commit message was its only durable trace is retired.

- **The harness-error honesty rule: a broken harness files its pair, and an unwritable pair files an admitted unknown (P25.6, issue #415)** — the honesty edge of the receipt fold, at the verifier's persisting seam. A run whose own toolchain breaks — a scaffold, cargo, or runner that could not even be run — now files its **verification receipt** pair verdicted **harness-error**: no baseline case assessed, no case named, the compile-only command doctrine saying plainly that no baseline leg ran through a runner (the same breadth doctrine a compile-failed pair keeps), and the seam answering with the harness failure itself — never a `VerificationResult`, because a unit that was never judged has no verdict to hand out. Infrastructure failure never reads as a unit failure and never reads as a pass: the old fallback text that turned an unstartable test runner into a quiet zero-test run is gone. And a pair that cannot be written files an **admitted unknown** instead of vanishing as a log line: the roster grows the blocking **receipt-unfiled** kind, paired with a new **verify-run origin** keyed by the run's own attempt slot, and its question names the unit, the attempt, and the pair path that never landed, with the reason the filing failed riding the question. The record lands in the binary's own unknown ledger through the shared derivation and revision doctrine — filing twice is one record — and reads back through the standing admitted-unknown route the review surfaces already use; the pipeline's residue carry that keeps capture-origin records now carries verify-run-origin ones, so a later batch filing never erases an admitted unknown one broken run left behind. A run whose pair cannot land keeps its earned verdict — honestly degraded, the gap admitted out loud in the record tree — and if even the unknown cannot be filed, both failures chain into one loud error; a twin that fails to land retracts the half-filed authority, so a key never stands with half a pair. Pins: the compile-backed seam proves a harness-broken run files its harness-error pair digest-paired with no unit verdict leaving the seam, and that a pair key held open by a directory files exactly one blocking admitted unknown naming the run while the run's verdict stands; a record seam pins the unknown's id, severity, attempt-slot key, and idempotent re-filing through the existing read route; and the pipeline's roster sweep gains the kind's producer on the real path — the sweep holds the attempt-1 pair key open, the walk's own filing fails at the first attempt, the verifier admits the gap itself, and the ledger carries one `receipt_unfiled` record through the batch's later filings, pairing one-for-one against the declared roster.

- **The verify harness calls the unit under test by its own name, and testgen files every generated case positionally, so a pipeline-driven attempt can honestly earn a `passed` (issue #416)** — #414's deferred web pin lands with it. testgen used to spell generated inputs as named objects while the verify harness probed that shape, called a toy stand-in instead of the unit, and let the receipt rebuild a values pass from test-pass counts — the suite and the unit never spoke one callable shape, so no pipeline-driven translate could honestly pass its own baseline. testgen now files inputs positionally: a zero-parameter unit gets a `null` input, and every other unit a JSON array of argument values in declared parameter order; the record-and-replay fold's canonical dedup key now reads that vector spelling directly, beside the named spelling its mined rows still carry. The generic three-slot filler only pads when no signature parsed at all: a unit whose signature parsed carries only cases its own calling shape can answer, so a padded arity can never break a correct unit's scratch build. The generated runner calls the function the verify request names: a null input calls it with no arguments, and an array calls it with one coerced argument per element, in order — numbers that do not fit the unit's declared parameter are refused rather than truncated, and bools, chars, strings, pointers, and optional inputs arrive in the shape the unit asked for. An input the unit cannot take fails its own case, naming the input and the unit, instead of silently calling nothing. A unit that panics fails its case with the panic carried, and a unit that crashes the runner with a fatal signal — the segfault a dereferenced null produces — is a failed test whose return was never observed, never a broken harness. The values dimension now states what it actually compared: a case with no expected return leaves its value verdict unassessed (ADR-0057), and a pass on a suite of unassessed values reads as exactly that. A run whose test project produced no result lines names its own cause instead of guessing: a test-project build failure verdicts `compile_failed` with the compiler's own errors, while a scaffold or runner that could not run still files its `harness-error` pair under the #415 rule. The web patch-retry commit completes #414's deferred half: after a verified pass, the attempt-branch commit carries the committed attempt's receipt pair beside the translated file, in one commit, and the patch record cites that very commit.

#### Scenario-capture baseline (P24)

- **The scenario lane opens: a declared scenario contract files as one owned document per target binary (P24, issue #402)** — declaring is authoring, not running: the new `scenario declare --binary <exe> --scenario <name>` command validates a **scenario contract** — working dir, explicit env (`--env KEY=VALUE`), argv (`--arg`), scripted interactions (`--input-at MS:TEXT`, `--secret-at MS:TEXT`, `--resize-at MS:COLSxROWS`, `--signal-at MS:interrupt|break`), terminal geometry, observation paths (`--observe`, refused when a path is absolute or climbs with `..` out of the run dir), idle window and max run duration with their absurd bound refused rather than waited on, output cap, finalization grace, and versioned normalization (`--normalize-version`, `--normalize-literal FROM=TO`, `--normalize-port`) — and files it in the record tree's new owner directory as `re/scenarios/<binary identity>.json`: exactly one document per target binary with exactly one owner (interface; pipeline and testgen only read it), several scenarios per binary coexisting as named entries. A malformed declaration is an input error refused naming the offending field — `working_dir` that does not resolve, an `observation_paths` entry escaping the run dir, an absurd `idle_timeout_ms`/`max_run_ms`/`finalization_grace_ms`/`max_output_bytes` — and nothing files on a refusal, so no bogus contract waits downstream; re-declaring a scenario name replaces its contract outright, keeping exactly one current contract per name. **Sensitive scripted inputs never persist their text**: `--secret-at` files a byte-count placeholder, and the CLI pin proves the declared secret appears nowhere in the filed document's raw bytes. The shared records land with the vocabulary: the contract, the thin **scenario capture** (optional block per dimension — terminal, interaction, exit, filesystem, process — with the exit disposition from the closed set exited/timeout/idle_timeout/cancelled/failed), and the **scenario verdict** carrying one closed per-dimension verdict — assessed pass / assessed fail / unassessed. The honesty rule every record obeys: absent fields read *unassessed* — silence is readable, never a pass and never a fail by the same absent-field rule ADR-0053 established for unknowns. The pipeline glossary names the *scenario contract* and fixes the collision: a scenario *run* is one child execution, never the run-wide *Run*. Pins: pure record tests pin the absent-reads-unassessed rule, the closed wire sets, the placeholder's storage form, contract round-trip, validation naming each field, and replace-by-name coexistence; a family of CLI e2e pins walks `scenario declare` end to end at the handle-entry seam — filed document at the documented record-tree path with its binary envelope, all four interaction kinds and both observation paths landed, the secret absent from the raw filed bytes, coexistence and outright replacement across three runs, every malformed shape refused naming its field or flag with nothing filed. `scenario declare` is exempt from the `target_dir` preflight — a contract can be declared before the program exists.

- **The fixture console EXE joins the fixture crate beside the fixture DLLs: stdin-reading, file-writing, declared exit codes (P24, issue #403)** — a cross-compiled console program (`fixtures/fixture_console.c` → `fixture_console.exe`, same mingw-w64 rules as the DLL fixtures: a missing toolchain says so by name) gives the scenario lane a known program to run for real. Its behavior is scriptable from the outside on one line per interaction: `echo <text>` lands verbatim in stdout, `write <path> <text>` files under the run dir and acknowledges, `delete <path>` names `deleted` or `missing`, `exit <code>` ends the run right now, and an unrecognised line is `refused:` and never fatal; at EOF the run ends on the code declared by `--exit-code N` on argv — a malformed declaration is refused loudly on stderr rather than silently falling back to 0 — so both declaration routes let a rigged comparison force a named divergence. stdout is unbuffered so acknowledgments land in observation order while the run lives. Its identity constants are exposed the way the DLL's are — the file name, the identity literals `calxgloss-fixture-console-v1` and the ready line a reviewer names the target by, and the console subsystem — so later scenario slices name the fixture by identity, never by a build path; loading the EXE validates its PE identity with named errors (x86-64, a console exe not a DLL, the console subsystem, literals present), so a broken fixture says which element broke. Nothing scenario-specific lives in the fixture itself — it is plain console behavior a scenario can rig against.

- **First scenario capture: one command runs a declared contract against the original EXE and files the capture (P24, issue #404)** — `scenario capture --binary <exe> --scenario <name>` takes the declared contract out for a real run against the target binary standing in the target dir and files what the run was observed to do: the first **scenario capture**, readable at its documented record-tree location `re/scenarios/captures/<binary identity>-<scenario key>.json`, with exactly one current capture per scenario name — a re-capture replaces the previous document outright, never versioned, never appended. The run stands behind a host terminal exactly as an operator would drive it, and finalization rides the **ownership token**: the launched process's identity is bound at launch and the contract's finalization grace runs SIGTERM first, SIGKILL only after the bounded window — never a bare-PID kill. A missing Wine fails the capture by name through the standing preflight line — before any process exists to hang — and a capture before any declaration is refused toward `scenario declare`; either refusal files nothing. The capture holds the exit disposition from the closed set (exited / timeout / idle_timeout / cancelled / failed) with the run's exit code when a code exists, terminal output chunks under the contract's cap carrying an explicit truncation mark the moment the run outgrows it — a capped capture states its cap, in the document and in the printed summary, and never claims more than it saw — and every interaction delivered while the run stood is acknowledged at its declared offset (a sensitive byte-count placeholder stays undelivered and unacknowledged until the credential slices arrive). The declared observation paths classify across the run as created / deleted / modified / unchanged, each named side carrying its size, whole-file sha256, and 4 KiB block digests, so a partial write shows exactly which blocks moved and **files are compared by content, never by existence**. The capture stamps its pairing: the sha256 of the very program bytes it ran and the Wine version that ran them — the **pairing rule** says a re-capture pairs for comparison only against identical program bytes, and a digest mismatch is stated out loud, naming both digests before the replacement files, never silent. The pipeline glossary names the *scenario capture* and the *pairing rule*: a capture is bounded evidence, not a claim.

- **Hung runs named by their windows, and the process dimension grows real data: finalization outcomes and sampled process samples (P24, issue #405)** — the two windows a *scenario contract* declares are now proven behavior, not declarations: a fixture that falls silent ends `idle_timeout` at the idle window and a fixture that keeps talking ends `timeout` at the max run duration, each naming its disposition in the **scenario capture**, neither stalling. Finalization reaches the process only through the **ownership token**, and the capture names how it went: the owned process signaled — SIGTERM first, the declared grace to end on its own, SIGKILL only past it — or the process had already exited, or the **token refused**: a pid that answers to a different identity than its launch bound is signaled not at all, and the record says so by name (`stale_identity_untouched`) — pinned as behavior against a live stranger pid, not prose. A run that ended on its own leaves the outcome absent: nothing was finalized, and it reads *unassessed* by the honesty rule. ### Added

#### Evidence scans

- **Branch inventory, end to end (P12.5/#224, issues #258–#261)** — the `controlflow` scan now records every branch site in each function body: guards, loop exits, else arms, and switch arms. Each site gets one record carrying the condition text, the parameters it involves, the operator and immediate when the predicate is readable, the kind of thing the branch guards (early return, error path, loop exit, else arm, switch arm), a confidence, and the evidence line. A reading that names the operator and its immediate scores highest. A shape-only reading (compound condition, unreadable predicate) claims only that the branch exists and never names an operator or immediate. A truncated or malformed body records only what is visible, and a body with no readable branch records nothing. The records persist as the `branch_site` finding kind — documents written before the kind existed still load unchanged — and the `controlflow` report names the kind in its breakdown. They reach the LLM through the CONTROL FLOW sections the module-context and escalate prompts already have, so a retry after a divergence sees the same branch context as the first attempt. They also feed test generation: the translator takes the branch inventory from the same persisted control-flow document it already loads for the prompt, with no second load and no new artifact path. A unit whose document carries branch-site records therefore gets a baseline suite that exercises the guards, error paths, loop exits, and switch arms the decompiled body reveals, with expected values still captured from the original binary through the existing baseline run. Each record yields one baseline case: an equality guard yields its equality value; a relational guard yields the immediate ±1, so the pair straddles a loop-exit boundary either way; a guard against zero, and a shape-only or operator-only reading, yield a null/zero probe; a switch arm yields its case value, and a named constant that is not a literal degrades to a null/zero probe rather than inventing a value. The probe lands on the parameter the condition names — the declared name or the decompiler's positional spelling — and the parameters the condition does not involve hold typical values. A probe outside a parameter's declared width and signedness drops that case instead of producing an input the Wine harness cannot encode. Branch cases dedup against the existing boundary suite and against each other, and a per-function cap of 40 drops the lowest-confidence branch cases first, never a boundary case. With an empty inventory the prompt section and the baseline suite are exactly what they were before, and a missing or corrupt control-flow document degrades to no section and today's suite while the run proceeds.

- **Known-library function identification (P14/#227, issues #262–#267)** — a new `libmatch` scan names the CRT routines statically linked into a binary, so a `memcpy` stops being a translation unit. Before matching, each decompiled body is normalized: the decompiler's Ghidra-shaped variable spellings, register temporaries, and volatile addresses become wildcards, while calls, operators, constants, string literals, and control-flow keywords stay literal — a match claims the body's *shape*, never its bytes. The built-in set carries what a typical statically linked MSVC binary holds: the `memcpy` copy loop and the `strlen` NUL scan, `memset`, `memcmp`, `strcmp`, and `strcpy`; the allocator wrappers as the set's deliberately sloppier entries — `operator new` as a `malloc` call with a null test, `operator delete` as a guarded `free`, each claiming a confidence of 50 rather than the standard body-evidence score because any thin allocation helper reads those shapes; and the red-black-tree idioms of the STL associative containers, keyed on the MSVC node fields that survive normalization (a rotation's child rehang, and a search descent that walks `_Left`/`_Right` while testing `_Isnil`). Every entry is hand-authored against the normalization contract, with the shapes that must be present and the shapes that must be absent keeping the look-alike loops apart: a guarded copy reads as a `memmove` shape and goes unmatched rather than misnamed, and the `strlen` entry requires the `while (*VAR != '\0')` spelling so compare and copy loops, which test a loaded byte instead of the dereferenced pointer, no longer read as a length scan — the guarded-copy `memmove` shape is left for the operator's own file to claim. A finding names the symbol, its family (CRT or STL), the evidence lines that carried the match, and a confidence, and where two signatures claim one function the strongest claim wins (ADR-0022). Matches propagate over the bodies the scan already keeps, with no extra decompiles. The carry-over confidence floor — 80 on the evidence scale, following the `libmatch` Skip-floor precedent — is stated in one place: every resolved pairing is recorded regardless of the floor, and only the downstream carry-over consumer applies it. The payoff lands in the queue: a new-version function that pairs at or above the floor to an old-version function whose translation is *accepted* — a merged `re/{binary}/{function}...` branch, the review overlay's Accepted classification (ADR-0003) — gets its first attempt seeded from that accepted code instead of asking the LLM cold. The seed is a standard attempt branch under the new function name, pre-populated with the merged `translated.rs`, and the seeded unit then rides the normal pipeline: baseline capture re-run from the new binary through the existing Wine path, and full verification against the new bytes (ADR-0016's carry-over bet: the translation carries, the ground truth does not). Nothing a seed touches carries a Verified mark — the deterministic verification is the verdict. Provenance survives into the record: every seeded result names the old function and the attempt branch its code came from, and the new branch's commit says "seeded from {old} attempt {n} (paired, {conf}% confidence)". The staleness gate guards the seeds whole: a pairing document that does not name the binary whose current bytes are being translated and hash those bytes as its `new_bytes_sha256` seeds nothing, because a stale document describes a different version situation and seeding from it would be guesswork. The one-branch-one-seed rule lets an accepted translation seed at most one new function, the strongest pairing claim winning the branch, so two new functions never claim one merged translation. Below-floor pairings persist but seed nothing, and those functions queue fresh exactly as before. Seeds are collected from the pairing documents the trigger leaves in `re/analysis/bdiff/` during the same pre-batch scan step, and the accepted-code lookup goes through an injected port implemented outside the translator, which stays git-free. No port, no documents, unreadable documents, and functions without an accepted twin all degrade to "no seed": a fresh queue, never a failed run. Before any of that spends anything, `calxgloss bdiff --binary <name>` lets an engineer review the version change. It loads the pairing documents for that binary identity and lists every old↔new pair with the old name, the new name, the confidence colored on the shared bands the other reports use, and the match family that carried it, beside the functions paired on neither side — old-only and new-only listings, each side its own listing minus the paired names, in scan order — in the standard persisted-document report shape. Its breakdown line names every match family the document can carry with counts (`name_identity`, `normalized_body`, `call_topology` in ladder order), and a family with no records stays off the line. The live document is the one that names the binary and hashes the target directory's current bytes as its `new_bytes_sha256`; a document naming a since-replaced current version is never printed as live. A missing or stale document fails the run naming the gap — the stale pair's hashes beside the current hash, and how a fresh document appears — never an empty success. The command is pure report: no scan runs, no engine read (ADR-0026 untouched), no write-back (ADR-0020), no LLM, and its closing line reminds the operator that the run's carry-over seeds only from pairings at or above the carry-over floor. This track adds no web or dashboard surface.

#### Pipeline control & runs

- **Detect and park .NET managed assemblies (#235)** — the classification pass now reads each binary's COM descriptor (PE data directory 14) during the PE parse it already performs. A managed assembly becomes the strategy switch's new `.NET Managed` category with a new **Do Not Translate** strategy, and its classification reason documents that we do not yet decompile .NET programs (ADR-0044). Precedence is operator classification override, then the PE marker, then name heuristics, and the `known_runtime` flag stays reserved for runtime libraries. Every consumer reflects the fact: the binaries list shows the category and strategy, and the review queue gives a parked binary's units a new **Do Not Translate** review status. That status is visible in the full queue view, excluded from active counts and from next-work serving, sorted after skipped units, immune to the auto-blocking cascade and to manual skip and unskip, and stable across dashboard rebuilds; the parking reason surfaces in the unit's known gaps. `translate`, `batch-translate`, and `auto` refuse a parked binary before loading the analysis engine or contacting the LLM, and the refusal names the gap, the signal, and the classification-override escape hatch — an override pointing the category away from `.NET Managed` releases the binary as fully translatable.

- **Configurable per-request LLM timeout (`[llm] timeout_secs`)** — the LLM client's HTTP timeout was hardcoded at 300 seconds, so a slow local model on modest hardware lost every completion that took longer than five minutes to the client aborting mid-generation. The timeout now follows the layered configuration like every other `[llm]` key: `timeout_secs` in `calxgloss.toml`, `CALXGLOSS_LLM_TIMEOUT_SECS`, and `--timeout-secs`, defaulting to the same 300 seconds (5 minutes), attributed by source in `calxgloss config`, and applied by `translate`, `batch-translate`, `auto`, and `auto-shim`. The wait covers the whole exchange — connect, send, generation, and body read — so raising it is the fix for timeouts on machines that simply answer slowly.

- **Focus slot — "translate this next" (#284)** — an operator can put one binary next in line with a single press. `POST /api/pipeline/binaries/{binary}/focus` works only in live mode and follows the pause pair's honesty rules: 503 with no scope handle, 409 naming the server's own reason for an undiscovered binary, and last press wins. It places one discovered binary in a single focus slot. The live worklist moves the focused binary to the front of the queue at the next binary boundary, re-publishes the plan with it there, and consumes the slot — honored once, never again. The served pipeline table also hoists a pending focus, so re-fetching `GET /api/pipeline` shows the new plan order before the loop reaches the boundary. The slot is persisted in the scope record, so a re-opened handle honors it after a restart, using the case-insensitive match rule from issue #107.

- **One translation toggle per pipeline row (#285)** — every non-PAL pipeline row now carries exactly one translation button beside Configure and Classify. It reads Pause only while the pipeline is working that binary and the binary is not held (a held row reads as held), and Start Translation in every other case — never two translation buttons on one row, and no row-level Resume. The button drives a new per-binary endpoint, `POST /api/pipeline/binaries/{binary}/start` (live only; 503 without a scope handle or live run control, 409 naming the server's own reason for an undiscovered binary). The server composes the swap so it cannot half-apply from a flaky client: the pressed binary is resumed and focused at the front of the queue plan, whatever is in flight is paused through the per-binary pause path with unit-boundary semantics and completed work kept, a run-level pause is released, and a session that has only classified so far begins translating with the pressed binary first. The row button never calls the run-level start endpoint. A press the run cannot honor is refused, never a silent no-op: a stale row whose pass this run already completed gets a 409 naming the reason and pointing at the row's Configure, because re-running a finished pass is restart's job, and a terminal run is refused with the state machine's own message. The success response names both halves of the swap, and `binary_pause_changed` events re-render every connected client: the plan reorders and the previous leader shows Paused with no page reload.

### Changed

- **Wide argument lists on the prompting and run path collapsed into bundles (issue #268)** — the escalate and module-context prompt builders took one list per evidence engine across the prompting boundary, up to 21 same-typed positional parameters where a transposition compiles silently, and the CLI run entry points took 14–20 positional parameters each. Every new evidence engine therefore meant touching every wide signature between the retry helpers and the templates, plus every call site. The seam now carries bundles instead. One evidence bundle, defined in the prompting crate beside the finding types it holds, feeds the escalate template constructors, both escalate prompt builders, and the module-context and full-module prompt-data constructors, and lower context tiers pass partial bundles; the translator's retry helpers gather it in one pass over the filed analysis documents and fill the call-graph lists from the live scan source on top. The run entry points (`auto`, `live`, and the per-binary pass) take run identity, options, and the cheaply-cloneable control handles as bundles too, and the compile-fix, test-fix, and edge-case-fix builders, the shim pipeline, and failure recording take their shared inputs as single records. Rendered prompts are byte-identical: the bundles only carry input, and no persisted artifact format changed.

- **Decompiler-noise stripping at the decompile read exit grows to the full /GS canary family (spec #232, issues #271–#273)** — a statically linked MSVC binary dresses nearly every function in stack-guard code that carries no meaning for translation and only dilutes the pseudo-C a scan or the LLM reads. The noise filter at the seam's `decompile` read exit now strips the whole canary family. Standalone calls to `__security_init_cookie`, `__security_check_cookie`, and `__report_gsfailure` — lines consisting solely of the call — are stripped at both analysis read exits. The epilogue half: an `if` comparing the saved cookie local against the cookie global, with nothing but the `__report_gsfailure` call inside its block, comes back from the `decompile` read with the wrapper, the comparison, and the failure call gone as one shape, and the function's real statements byte-identical around them. That check runs before the named-guard-call pass, because the failure call inside the `if` is what anchors the shape. The gate is deliberately conservative and strips only the complete idiom: a condition carrying a comparison against a cookie-global spelling (`__security_cookie`, `stack_cookie_guard`, or a `DAT_`-shaped unnamed global), a block holding exactly one standalone guard-runtime call, and no `else` attached to the wrapper on either side. A lone comparison, an empty or stuffed wrapper block, a condition without a cookie global, a hollowed `if` the named-call pass leaves behind, and idiom text spelled inside strings or comments all claim nothing and pass through. The prologue half closes the family: a line that is exactly one assignment storing the cookie global XOR'd with a stack-slot address into a local — `local_8 = DAT_18004a040 ^ (ulonglong)&stack0x00000008;` — comes back gone along with its line break, and a cookie local the strips leave unreferenced loses its declaration line with them. A full prologue-plus-epilogue canary body therefore comes back with the whole idiom gone. This recognizer runs after the other two, because whether the saved local is left unreferenced is only knowable once they are done, and its declaration sweep stays strictly inside the body's declaration block — the run of bare declarations the decompiler opens right after the body's brace — so a local any remaining statement still names keeps its declaration byte-for-byte. The conservative gate holds on the save statement itself: the assignment must be the line's whole content with exactly two operands, a cookie-global read (either operand order, behind any cast) and a stack-slot address (`&stack0x` plus hex). A lone XOR, a cookie copy without the XOR, a cookie XOR'd against a constant instead of a stack-slot address, a store into a global or through a pointer, a compound assignment, a three-operand XOR, and a save sharing its line with a comment or any other text all claim nothing and pass through byte-for-byte. SEH/EH frames, `try`/`catch`-shaped bodies, and landing pads are never part of a match — that is the error-handling scan's territory — and since the canary check is now stripped even from SEH functions' epilogues, the error-handling scan's own canary false-fire gate becomes redundant insurance. The never-empties rule guards the combined strips: a body made entirely of guard code passes through whole rather than coming back empty. The scan read cache keeps storing the engine's raw text whole (ADR-0043) — the filter runs on read, so deleting the cache recovers byte-identical unfiltered behavior — and the signature line passes through byte-for-byte. The filter is always on: no toggle, no CLI surface, no findings, artifact, or schema changes, and no extra engine reads. Each strip logs a debug line naming the function and the noise family (`guard-call`, `epilogue-cookie-check`, `prologue-cookie-save`), and a new noise family joins as one more recognizer in the filter's single home module, the seam untouched.

### Fixed

- **An import thunk named after its own import was translated as if it recursed (issue #269)** — a binary's one-instruction veneer for an API (`jmp [__imp_SetCursor]` → `user32!SetCursor`) carries the API's own name in the symbol table, so the decompiler renders its tail-jump as a call to that name and the function reads as infinite recursion (`SetCursor(); return;`) while matching none of the name-based thunk patterns — and the LLM would faithfully turn the apparent recursion into a Rust function that calls itself. The translator now reads the body shape instead of the name: a function whose whole body is one unconditional call to its own name — in either engine's spelling, comment slugs and return-type casts included — is refused as a skipped root on the explicit and batch paths and in pre-built requests, before any LLM token is spent, and the refusal names the shape as the reason. A genuinely recursive function, whose body carries a base case around the self-call, is not this shape and still translates.

- **A stripped 32-bit PE listed only a couple dozen functions (issue #270)** — the Kuna load went straight from bootstrap into the analysis commit without the options step, so the commit installed only what the loader itself knows: the entry point, the TLS callbacks, and the code pointers the base relocations name. On a 64-bit image that is mostly harmless, because the `.pdata` exception table recovers nearly every function, but a stripped 32-bit PE carries no `.pdata` and no symbol table: `LaunchPad.exe`, a statically linked MSVC GUI launcher, listed 17 functions where the image holds thousands, and every scan and the whole translation queue saw only those 17. The load now arms Kuna's own driver-default discovery bundle before the commit, exactly as `kuna decompile-all` does: `listing on` (the recursive call-graph walk) on every image, plus `funcstart_patterns on` and `aif on` (the prologue-pattern sweep and the aggressive instruction finder) on a non-x86-64 image, where the cheap x86-64 oracles are inert. `LaunchPad.exe` now lists 7,573 functions, and x86-64 keeps the aggressive pair off so the cheap path stays cheap and never over-produces.

- **The `typeinfer` scan spun forever on a large stripped 32-bit image (the 2026-10-20 `LaunchPad.exe` incident)** — the calling-convention corroboration pass checked every per-function convention record against every kept disassembly listing, and answered each check by re-splitting and re-parsing the whole listing, so the pass cost grew as functions × records × listing size. On 64-bit fixtures this stayed invisible: Microsoft x64 never spells a `ret N` epilogue, so epilogue records barely exist. A statically linked 32-bit MSVC image hands nearly every function a `ret N` record, so `LaunchPad.exe`'s 7,267 functions meant billions of row parses and tens of minutes of 100% CPU silence mid-scan, which read as a hung run. The pass now reads each kept listing exactly once and groups its call rows by the callee name they name, so every check becomes a lookup. The output is unchanged: bumps in record order, one call-site view per (caller, callee) pair in listing order, evidenced by the first site in row order.

### Added

#### Analysis engine

- **Kuna analysis engine (epic X5/#203, issues #205–#211)** — a new analysis engine loads a target binary **in-process** through the Kuna console engine, pinned to Kuna `v1.878`, with the x86 SLEIGH specs compiled at build time and embedded in the binary. There is no Ghidra install, server, or port involved. Engine selection is a global `--engine <ghidra|kuna>` flag plus the `[analysis] engine` config key (environment variable `CALXGLOSS_ANALYSIS_ENGINE`); the default stays `ghidra`, and a run uses exactly one engine. Under `kuna` every scan read is answered — function listing, decompiled pseudo-C, imports and exports, image base, strings, cross-references, callers, type-library listings, structure layouts, enum members, data items, and raw memory reads — and consumers read Kuna's warning, name, and disassembly dialects. Type write-back compiles to Kuna `--assert` directives held beside the scan record at `re/kuna/<binary>.kuna` and replayed on every load. Scan records carry engine provenance: engine name, release tag, and pinned commit. Kuna runs beat the Ghidra passes they replace. Kuna's per-function watchdogs are calxgloss configuration: `[analysis] max_fn_instructions`, `max_fn_seconds`, and `max_fn_memory_mib` fail one oversized function by name, and the `DecompileBudgetExceeded` failure names the knob to raise and the `--engine ghidra` fallback, instead of hanging or exhausting the machine.

#### Evidence scans

- **Calling-convention detection (P12.6, #226, issues #245–#251)** — the type-inference scan now detects each function's calling convention, and its consumers use the answer. Readings come from the convention letter in MSVC-mangled listing symbols, the `@N` decoration on import names, and machine listings: callee `ret N` epilogues and caller stack cleanup for 32-bit, and the Microsoft-x64 call shape (shadow space plus `RCX`/`RDX`/`R8`/`R9`) for 64-bit. A cross-function pass raises a reading agreed by epilogue, decoration, and caller cleanup above any single channel, and each calling function gets a record of the callee's convention at its call site. The `typeinfer` report names conventions and the channel that read them. The module-context and escalate prompts gained a CALLING CONVENTION section. Signature synthesis spells the detected convention into the synthesized signature — `__cdecl`, `__stdcall`, `__fastcall`, `__thiscall`; Microsoft x64 spells none — so the generated FFI binding, and the shim signatures rendered from the same string, call the original with the detected convention instead of the default.

- **Global-state analysis (P13, closes #225, issues #252–#257)** — a new scan records which program globals each function reads and writes: the global's name, the access kind, the statement that carried it, and a confidence band, with a derived per-function purity summary. It persists per binary at `re/analysis/globalstate/{binary}.json` and runs as one of the pre-batch evidence scans. A shared-globals index rolls the records up into one entry per global naming its reader and writer functions. The CLI gained a `globalstate --binary <name> [--show]` report. The module-context and escalate prompts gained a GLOBAL STATE section that spells the target function's own globals and steers the translation to give each global a home in a threaded struct rather than a Rust `static`. The concurrency scan's data-race pairing now consumes the same global readings, so race findings and the global-state document name the same accesses by construction. The translation orderer consumes the persisted index as state-sharing edges: within a priority tier, the unit that first defines a global enters the queue before the units that reuse it, and an empty or missing index leaves the existing dependency order exactly intact. Generated baseline tests now carry the function's persisted globals as expectations, with the typed `GlobalRead`/`GlobalWrite` side-effect kinds and the global name riding the expectation's detail string, so a verification failure reports the expected side effects by named kind instead of an opaque `Other(...)` note; test documents written before the kinds existed still load.

- **Serialization analysis deepening (P11.5, issues #198–#201)** — the `serialize` scan now reads the message-integrity and format story, not just scattered per-call hints. `cross_field_validation` findings report the checksum and length checks a parser runs against its own input. `serialization_format` findings compose a function's byte-swap and bit-pack readings into one ordered layout claim with a `byteorder`-style reader suggestion. `protocol_message` findings identify well-known network magics (IPv4, ARP, IPv6, VLAN) only when corroborated by network-order swaps or cross-field validation — a bare magic sniff stays a plain magic finding. One `endianness_map` finding per scan coalesces the binary's byte-swap calls by width into a wire-order claim: network-order names imply `be`, and direction-neutral builtins claim nothing. All of it rides the persisted JSON, the `serialize` report, and the escalate prompt's SERIALIZATION section.

- **Constant recovery deepening (P10.5, issues #190–#195)** — the `consts` scan reads constants the way the code does. Repeated literals beside a named identifier gain context-derived names (`const SIZE_0x280: u32 = 0x280;`). Composite bitwise masks decompose when every set bit was independently sighted in the body. Per-function bitflag groups that share bits merge transitively into one program-level `flag_family` record suggesting a single `bitflags!` struct. Known protocol and format magics and sentinels (PNG, GIF, JPEG, ZIP, gzip, ELF, PE, Mach-O, `0xDEADBEEF`, `0xCAFEBABE`, …) are recognized by name even when seen exactly once. Color-shaped literals group into one palette finding per binary. And `calxgloss consts` now writes a reviewable Rust source file beside the persisted JSON — `bitflags!` blocks, enums, and named constants rendered from the findings, byte-identical across scans of one program.

- **API detection deepening (P9.5, issues #184–#188)** — `apidetect` findings now carry the API category its library mapping names, using the PAL's vocabulary (`Win32Core`, `DirectX`, `SDL2`, `POSIX`, …), and crate suggestions render with feature flags (`flate2[zlib]`, `image[png]`). A `platform_divergence` finding flags binaries that import both Win32 and POSIX or C-runtime stdio, and suggests cfg-gated translation. `com_interface` findings recognize the COM component model — runtime imports, the IUnknown-shape trio, and interface-decorated names — and suggest a trait per recovered interface. The scan also writes two derived artifacts beside the cached JSON: a Cargo.toml-style dependency manifest at `re/analysis/apidetect/{binary}.toml` (every suggested crate once, features inlined, no versions claimed) and an FFI bindings file at `re/analysis/apidetect/{binary}.rs` declaring only the imports no crate replaces.

- **String context deepening (P8.5, issues #181–#182)** — `stringctx` now spots the language machinery a binary leaves in its strings — whole-string language names, locale codes, and non-ASCII user-facing text — as one `localization` finding per function suggesting a language enum with the localized strings in a table. It also ties strings across call boundaries: a `cross_function` finding lands when one scanned function hands a literal or a resolved `DAT_` string to another function through a call, suggesting the receiving parameter translate as a string type.

- **Control-flow analysis deepening (P7.5, issues #176–#179)** — built on the per-body control-flow graph foundation (#175), `controlflow` now reports `loop` findings — counted, conditional, do-while, and goto-driven loops, with the count and maximum nesting depth per function — and `branch_density` classification (dispatch-table candidate versus sequential scan), and it adds `mutual_recursion` findings, one per call cycle of length 2 or more, derived from the bodies the scan already holds. The recursion reading deepens: self-calls nested in loops flag a depth multiplier, and tail calls spread over lines or nested in a block read as tail calls through the graph.

- **Callback & function-pointer analysis deepening (P6.5, issues #170–#173)** — `callback` now spots the plugin boundary: `LoadLibrary`/`GetProcAddress` or `dlopen`/`dlsym` pairs, plugin entry-point names, and the host API table handed to an entry point, suggesting `Box<dyn Plugin>`. It reconstructs callback `chain` findings across functions — a callback registered in one function and called by name in another, or a table registered and called through. It rebuilds `event_system` architecture — two or more registrations to one name plus a visible dispatch site — suggesting the observer pattern. And it fills real closure contracts into callback suggestions from the persisted type-inference document, so a suggestion reads `Box<dyn Fn(i32) -> bool>` instead of `Box<dyn Fn(...)>`.

- **Concurrency analysis deepening (P5.5, issues #164–#168)** — `sync` now detects thread-local storage — the Win32 `TlsAlloc`/`TlsGetValue` family and the POSIX `pthread_key_*` family — suggesting `thread_local!`; raw futex calls (`futex` and `syscall(SYS_futex, …)`), suggesting `std::sync::Mutex`/`Condvar` instead of transliterated syscalls; `lock_order` conflicts, where two functions acquire the same two locks in opposite orders; and `data_race` pairs, where one function stores into a program global that another reads with no lock either side respects — one lock object held over every access suppresses the claim.

- **Memory lifecycle analysis deepening (P4.5, issues #158–#162)** — the `memory` scan now follows a block across the whole call boundary. `cross_function` findings pair an allocation in one function with a callee's release of the parameter it received. `ownership` findings report blocks handed to a callee or returned whole (`Box<T>`). `leak` findings report allocations never released and never allowed to escape. An `Rc<T>` upgrade lands when a callee stores the pointer it was handed into a global or a struct field. And paired handles spelled with a real type in the body get named `Drop` suggestions (`impl Drop for HANDLE`).

- **Algorithm recognition deepening (P3.5, issues #152–#156)** — the `algorithm` scan now resolves competing claims to one report per algorithm with the strongest evidence, and it gained a configurable minimum-confidence floor. `--patterns <file>` teaches it new control-flow signatures, string signatures, callback contracts, and correlation relationships from one JSON document: the file replaces the built-in sets whole, and entries may carry their own confidence. `cross_function` correlation hints recognize the algorithms living between functions — `divide_and_conquer`, or a `qsort` host whose named comparator actually compares its arguments. The per-function pass runs with bounded concurrency, at most eight decompiles in flight, and the skip-rate breaker still aborts a wrong-program scan.

- **Type inference deepening (P2.5, issues #143–#150)** — the `typeinfer` scan types far more of a program. Types propagate across call boundaries in both directions: a callee's own parameter readings lend types to the bare-identifier arguments at its call sites, and callers' typed arguments, string literals, and known-routine results lend types to the callee's parameters. Locals are typed through assignment chains, and return types are inferred from how callers use the result. C++ mangling is decoded: demangled qualified calls type their arguments, and MSVC-mangled listing symbols yield a calling convention, an argument count and rough types, and a return type even when the function's body never decompiles. Integer widths are bounded by comparisons, bitwise OR/XOR, and compound assignments beside wide constants. `--write-back` applies the scan's surviving hypotheses back into the open program — referenced type names created first, then function prototypes, then local-variable types — never overwriting a slot the program already types concretely, skipping records below `--confidence-floor` (default 70), and ending with an applied/skipped/failed report naming each target and reason.

- **Type database recovery deepening (P1.5, issues #137–#141)** — the `typesdb` scan now recovers the type tree, not just flat records. String-inferred struct candidates link to RTTI-confirmed vtables and take their demangled class names. Candidates split across a hub function merge on shared referencing functions. Struct fields whose type names match recovered types link into nested subtrees. STL/MFC types (`basic_string`/`CString`, `vector`, the `map`/`set` family, smart pointers) are flagged with their family so the translator maps them onto `String`/`Vec`/`BTreeMap` instead of hand-rolling layouts. And `re/analysis/typesdb/{binary}.rs` carries the recovered types as `#[repr(C)]` declarations with explicit padding, regenerated after every scan.

- **The scan read cache lives at `re/cache/` (ADR-0042/0043)** — the cache directory went from `re/ghidra-cache/` to `re/decomp-cache/` and now to `re/cache/`, joining the record of effort's other plain names. The config key, the environment variable (`CALXGLOSS_LLM_CONTEXT_WINDOW`), and the flag (`--context-window`) are renamed to match the meaning, and each request's output cap is derived from the window minus a pessimistic prompt estimate. There is no backwards compatibility: a workspace still writing `max_tokens` fails to parse with the full key listing.

- **Binary identity is the verbatim filename, carried as a type (#68, #69)** — a target binary's identity is now its filename exactly as spelled, extension included (`game_logic.dll`), used unchanged in branch names, unit keys, artifact directories, classification records, and API payloads. This replaces the branch-drops-the-extension convention, which forced every consumer to guess which spelling a string followed. Identity and unit key now travel as their own types with one shared branch-grammar parser, and the CLI follows: `--binary`/`--binaries` replace `--dll`/`--dlls`. There is no backwards compatibility.

- **Batch pipeline reads go through the cached scan source (#105)** — one cached source per target binary now feeds all eleven evidence scans, the call-graph build, and the retry/escalation context helpers. A second batch over the same workspace with unchanged binary bytes replays every engine read from cache at zero live calls, and each function is decompiled at most once per cold batch across all the scans. Cache trouble degrades to live reads.

- **All eleven scan engines read through one shared seam (#100–#102)** — the engines' near-identical local copies of the read-source trait are gone; the shared `ScanSource` is re-exported by every engine crate, so the read cache implements it once for all of them.

- **Run-telemetry logs are bounded (#82)** — the token-usage, fault, and prompt-strategy logs keep at most the 10,000 newest entries. Aggregate totals still cover the whole run, while per-attempt detail covers only the retained window.

- **Pseudo-C text scanning now lives in one shared module** — the call-site walking, argument splitting, parenthesis matching, literal skipping, and cast stripping that every evidence crate restated is now one configured implementation, so a scanner fix lands once.

- **The pipeline table was reworked** — rows lay out as fixed aligned columns with a header (Binary, Total, Translated, In progress, Queued, Failed, Tokens, Success, Classification, Actions), long names ellipsize, and one Classification column carries the state (PAL trait, Shim → crate, Full RE, Unclassified). A new `BatchStarted` event marks the binary being prepared as **Working** before any function-level progress exists.

### Fixed

- **Kuna's function listing no longer hands consumers an ambiguous import name (issue #216)** — the #215 decompile warning came back over a 32-bit MSVC binary: a name with two executable entries — a thunk veneer per referencing object file plus the IAT slot — was listed but refused decompilation and translation, because the engine's name lookup refuses to guess between two executable candidates. The listing now keeps an entry only when the engine's own resolution settles on it, bounded to the names the enumeration spells more than once.

- **Multi-byte characters in decompiled bodies panicked the scanners' byte walks** — a non-ASCII character outside a string literal (a `ﾟ` in a comment) crashed the recursion call-site scan and the `consts` tokenizer by slicing at a non-char boundary. Both now match at the byte level, which cannot panic.

- **`auto` panicked on an explicitly named linker thunk** — a unit refused as a thunk was recorded skipped but also delivered to the per-function completion callback as a codeless success, and the git-commit handlers assumed a success always carries code and unwrapped it, crashing the run mid-batch. Refused units never reach the callback, and the handlers now skip results with no code.

- **Scope controls treated one function as two entries when the binary was cased differently (Fixes #107)** — adds, checks, and removals now share one match rule: binary names match case-insensitively, function names exactly.

- **The live view's "needs calxgloss live" notice was replaced by a generic error (issue #108)** — the client now reads the HTTP status from the error it throws, and the live view branches on the 404, instead of matching a message string the server may overwrite.

- **The LLM I/O view's Clear button cleared only the browser buffer** — a new `POST /api/llm-io/clear` deletes the persisted log and answers how many entries it dropped. If the server refuses, the view says so instead of pretending the history is gone.

- **The output-budget estimate was optimistic for code-heavy prompts** — disassembly-and-template prompts tokenize at ~3.4 characters per token, not ~4, so the EverQuest run's prompts overflowed the context window with a 400 on every retry. The estimate now assumes ~3 characters per token with the same headroom.

- **Empty prompt sections cost tokens** — the templates rendered "nothing available" filler headers and separator rules for every absent section, fourteen filler sections on the escalate prompt alone. Optional sections now render only when they have content, and every render passes through a blank-line normalizer.

- **The scratch PAL crate never compiled, failing every verification** — `//!` module-doc lines in the embedded template are rejected (E0753) inside the `include!` expansion, so every translated function failed on scaffold code the LLM never wrote and the retry loop burned attempts fixing the verifier's own header. The template now uses plain comments, and an existing workspace's stale scaffold fixes itself on the next run.

- **Import thunks no longer go to the LLM** — a built-in root pattern (`^(DelayLoad_|_imp_|thunk_)`) classifies delay-load stubs, IAT symbols, and thunks as roots, so they get a deterministic stub instead of a full translation unit spent on a one-instruction jump.

- **An empty disassembly is now read as "no disassembly"** — the bridge answered 200 with an empty body for functions that own no instructions (thunks and external imports), which the client surfaced as an error and a warning on every such function. It now maps to an empty listing.

- **Commits after Classifying staged nothing** — absolute workspace-joined paths reached the git staging call, which only accepts repo-relative paths, so every classification record commit landed empty. Paths are now normalized to repo-relative form, and commit failures that used to be swallowed now surface.

- **Decompiler lines padded with trailing whitespace panicked the literal scanner** — an index-out-of-bounds on lines ending in spaces. The bounds check now comes first and the lookup answers `None`.

- **A clean start now creates the workspace git repo up front (Fixes #123)** — a fresh folder left the dashboard popping "Not a Git repository" while the run sat silently in the preflight. The repo is initialized at the top of the run, and the preflight prints a visible connecting line.

- **A warm run's activity heartbeat went silent (Fixes #121)** — the pass heartbeat counted only live engine round trips, so once the read cache had warmed, the pipeline row rendered nothing under the Working badge. The heartbeat now counts work items consumed, warm or cold.

- **Review actions can no longer silently disagree with git (Fixes #86)** — fast Accept-then-Send-Back clicks raced on the unit's single action record. Each action re-checks the persisted state before writing and fails with a 409 naming the state that won, and send-back or patch on an already-merged unit is refused outright.

- **A stalled browser tab no longer freezes live updates (Fixes #85)** — one hidden or throttled tab that stopped draining its WebSocket blocked the broadcast loop for every other client and overflowed the event channel. Delivery is now non-blocking, and a client whose buffer fills is disconnected and resyncs.

- **Double patch clicks no longer double the retry (Fixes #84)** — a second "Request Patch" created the same next attempt twice and spawned two retry loops racing on one branch. A patch already in flight answers `patch_already_in_progress` and creates nothing.

- **Accepting a conflicting unit fails honestly (Fixes #83)** — the merge now checks for conflicts before committing anything, names the conflicting files, leaves main and the unit's status untouched, and the accept record says `conflicts:` instead of claiming a merge happened.

- **Run logs survive a crash mid-save (Fixes #81)** — killing the process mid-write could leave a half-written JSON artifact that the next run read as corrupt and overwrote. Every persisted document now lands atomically (temp file plus rename), so a reader always sees the previous or the new document whole.

- **Phantom-clean evidence scans when every decompile failed (Fixes #71)** — a wrong-program scan skipped every function and finished "successfully", persisting an empty record indistinguishable from a clean one. The evidence scans now abort once more than half the listing fails to decompile, naming the counts, and persist nothing.

- **Function-name hints never invent a `.dll` (Fixes #70)** — the call graph's function-to-binary detector appended `.dll` to every extension-less name, so hints from an `.exe` target never resolved. Candidates now resolve against the workspace's classified binaries, and an unmatched candidate resolves to nothing.

- **Dashboard baseline test counts never showed (Fixes #67)** — the baseline scan looked at the wrong directory level and the unit-side lookup cut the key at the wrong segment, so the two sides never joined. Baseline artifacts now attach on the verbatim `{binary}/{function}` identity.

- **Dashboard bounce and graph reshuffle during live runs** — every progress event rebuilt the status cards and re-ran the dependency graph's layout in filesystem order. WebSocket refreshes are now coalesced, cards update in place only when their values change, and graph nodes and edges order deterministically.

- **Crate-replacement classifications read back honestly** — the strategy's tagged-object form broke both readers of the classification records, rendering those binaries "Unclassified" after a restart. Both forms are now read.

- **Empty pipeline table after restarting a live run** — rows were derived only from the current process's event stream, so a restart over prior work showed "No binaries discovered yet". Classifications now load from the persisted `re/classify` artifacts, with live events still taking precedence.

- **Debug builds panicked on char literals in decompiled bodies** — a `']'` literal underflowed the argument splitter's nesting counter. Char literals are now skipped when matching parentheses and splitting arguments, and the counter saturates on malformed input.

- **Stale cached UI assets** — static files were served with no cache headers, so browsers mixed old CSS/JS with new. Responses now carry an ETag with `no-cache` revalidation.

- **Recent activity cycled and claimed "just now"** — units were stamped with the build clock and the list followed filesystem order. Accepted units now carry their commit time, and the list is ordered newest-first.

- **Live progress events applied out of order (issue #65)** — one task per event raced for the progress-state lock, so updates could land reordered or dropped. Events now flow through a single ordered consumer.

- **The retry loop accepted non-compiling first attempts (issue #64)** — success ignored the `compiled` flag, so a first attempt that failed to compile counted as successful and no retry strategy ever ran. Success now requires compilation plus all tests passing.

- **Fast-forward merge logs once (issue #87)** — the double debug line per merge is gone.

### Refactored

- **The pre-batch scan phase fans out (#234, issues #236–#241)** — the eleven evidence scans now run through one shared preamble, so the CLI and web batch paths can no longer drift apart, each scan as an owned job under one phase-scoped heartbeat, with a completion latch ordering the one real dependency: callback detection awaits the type-inference document. The scans run four at a time over the shared scan read cache — measured on a real target: the cold scan phase of a 4,076-function binary went 142.7 s → 113.9 s. Every function is still decompiled exactly once across the whole phase, and the persisted documents are byte-identical to the sequential schedule.

- **Frontend split into ES modules** — the single `app.js` is now one module per view plus shared fetch and format helpers, loaded natively by the browser with no build step.

### Documentation

It names all eleven evidence-scan methodologies plus the call graph, saying what each detects, the Rust shape it suggests, and the prompt section its findings render into, and its batch-flow, progress-event, filesystem-layout, web-endpoint, and retry/escalation sections were corrected.

## [0.2.0] — 2026-10-06

### Added

#### Output & pipeline

- **Crate-based output layout** — `translate` and `batch-translate` now write a Rust crate per DLL: `crates/<dll_stripped>/Cargo.toml`, one `src/<function>.rs` per function, and an auto-generated `mod.rs` that registers every translated function. The DLL or EXE extension is stripped from the crate name (e.g. `EqGame.exe` → crate `EqGame`).
- **Complexity-based prompt selection** — the tool classifies each function by instruction count, branch density, call depth, and API-category diversity. It then sends the function to a Minimal, Standard, Rich, or Detailed prompt, with matching Ghidra context.
- **Failure-informed retry prompts** — when earlier attempts failed, every retry strategy adds a "PREVIOUS ATTEMPT HISTORY" section to the prompt, so the LLM can see and avoid the earlier mistakes.
- **Per-attempt token usage logging** — every LLM call records its token counts to `re/analysis/token_usage.json`. This covers initial, retry, and tier-escalated attempts, each with its DLL, function, attempt, strategy, context tier, and outcome. The batch summary prints a total-tokens line.
- **Experiment logging** — each retry attempt is recorded to `re/analysis/prompt_strategy_log.json` with its category, strategy, and outcome, so aggregate pass/fail statistics can be computed from that file.

#### Context tiers

- **Context tier selection** — five context tiers (`Signature`, `Disassembly`, `WithTests`, `ModuleContext`, `FullModule`) control how much context the LLM receives for one function. The starting tier is chosen automatically from function complexity and API call count. Each tier has its own prompt, from a minimal signature-only prompt up to full-module context with neighboring functions, shared data structures, shim layer source, and PAL trait definitions.
- **Automatic context tier escalation** — after a failed attempt, a retry can step the context tier up one level and rebuild the prompt with the larger context. This works independently of retry-strategy escalation.

#### Fault detection & analysis logging

- **Fault logging** — detected faults are saved to `re/analysis/fault_log.json` with aggregate statistics.
- **Context-window detection** — the tool checks LLM responses against the model limit for truncation markers, and it checks oversized prompts before sending them. Disassembly can be split into chunks for the LLM.
- **Hallucination detection** — generated code is checked against Ghidra symbols and the PAL catalogue. References to APIs that do not exist are logged and emitted as progress events.
- **Infinite-loop detection** — when the same (prompt, output) pair repeats across retries, the run detects it before more tokens are spent on the dead end.
- **Behavior-divergence detection** — code that passes baseline tests but fails generated edge-case inputs is flagged in the retry loop, with confidence scoring and recovery advice.
- **Resource-exhaustion monitoring** — repeated failures and timeouts (OOM, swap thrash, HTTP 429/503/507) are tracked. The retry loop backs off, records faults, and can suggest queueing work or switching models.

#### New analysis crates

Each scan saves its results as a per-binary JSON document under `re/analysis/<name>/<dll>.json`. Every document carries scan provenance shared by all scans (binary name, finish timestamp, duration), and every finding is scored with the shared 0–100 `Confidence` type.

- **`calxgloss-typesdb` — data structure recovery**: recovers named types from the Ghidra Type Manager. It detects vtables — resolving method pointers and following the MSVC RTTI chain to class and base-class names, and flagging COM interfaces — and it infers struct candidates from string literals.
- **`calxgloss-typeinfer` — type inference**: detects C++ `this` pointers from vtable dispatch, narrows parameter types from string-function usage and integer bit patterns, and propagates types from known signatures (`malloc`, `strlen`, `CreateFileW`, …). Competing readings are resolved by confidence.
- **`calxgloss-algorithm` — algorithm recognition**: recognizes algorithm families (sorting, hashing, checksums, compression, …) from control-flow signatures, string markers, and callback contracts (e.g. a `qsort` compare function).
- **`calxgloss-memory` — memory lifecycle / RAII detection**: pairs allocations with releases (suggesting `Box<T>`/`Vec<T>`, or stack allocation for short-lived blocks), handle opens with closes (RAII guard suggestions), and reference-count bumps with drops (`Rc<T>`, narrowed to `Arc<T>` when shared across threads).
- **`calxgloss-sync` — concurrency detection**: pairs lock acquires with releases (`Mutex`/`RwLock`), detects interlocked/atomic calls (`AtomicU32`/`AtomicU64`), and detects thread spawns with or without joins (`std::thread::spawn` vs `tokio::spawn`).
- **`calxgloss-callback` — callback & function-pointer detection**: finds calls through function-pointer arrays, registration→callback pairs, and jump-table dispatches, and suggests `Vec<Box<dyn Fn(...)>>`, `Box<dyn Fn(...)>`, or `match`/dispatch tables.
- **`calxgloss-controlflow` — control-flow pattern recognition**: detects switch-shaped if-else chains, self-recursion (with tail-call detection), and state-machine patterns, and suggests `match`, loops, or `enum State`.
- **`calxgloss-stringctx` — string & configuration context**: classifies strings into nine categories (format strings, paths, error messages, …), maps strings to functions through body parsing and xrefs, and infers argument types from format specifiers.
- **`calxgloss-apidetect` — library & API identification**: identifies linked libraries from the import table and maps them to Rust crates (DirectX 9, SDL2, zlib, PNG, the C runtime, …). For each function it summarizes which APIs the function reaches directly and which through its callees.
- **`calxgloss-consts` — constant & enum recovery**: recovers bitflag groups from bitwise operations, enum candidates from contiguous switch cases, and repeated literals as named constants.
- **`calxgloss-serialize` — endianness & serialization detection**: detects byte-swap calls, bit-packing shift/mask chains, and magic-byte comparisons (PNG, gzip, ZIP), and suggests `byteorder` readers, field masking, or format decoders.

- **Review dashboard data model** — work units, review statuses, the dependency graph, status counts, and review actions are now one set of records shared by the reports, web, and CLI, replacing the duplicate scaffolding in `calxgloss-web`.
- **Dependency-ordered queueing** — units carry a processing level (classification → shim → PAL → test → function → integration → fix). The dependency graph sorts them topologically, breaking ties by level, and the dashboard automatically blocks units whose dependencies are in a failing state.
- **Typed progress events** — progress reports travel as typed, serializable events: translation milestones, per-attempt completion, context tier selection, fault detections, and LLM request/response. They are published on a broadcast channel so they can reach the web UI over a WebSocket.
- **Shim layer records** — shared records describe API mappings, shim layers, and complexity scores, plus per-DLL shim suggestions with estimated complexity and confidence. These are computed from classification data, without an LLM call.

### Changed

#### Vocabulary

- **Unified on *workspace*** — one directory, one name: the `--repo-dir` flag is now `--workspace`, the config key `repo_dir` is now `workspace`, and the environment variable `CALXGLOSS_REPO_DIR` is now `CALXGLOSS_WORKSPACE`. `translate` and `batch-translate` no longer take `--output-dir` — output always lands in the resolved workspace — and the dead per-command `--repo` flags are gone.
- **Terminology corrections** — `ContextTier::Stub` is renamed `Signature`, because "stub" is reserved for mocks. An FFI *stub* is now called an FFI *binding*: the generated block calls the real DLL. `WorkUnitKind`/`WorkUnitLevel` are renamed `WorkKind`/`WorkLevel`. `ReviewStatus::Merged` is dropped: merging is the git effect of Accept, not a second verdict. The scratch PAL package is renamed `calxgloss-pal` → `calxgloss-verify-pal`.
- **Confidence scales disambiguated** — the three confidence values now have separate names: evidence confidence (0–100, the shared `Confidence` type), unit confidence (`unit_confidence`, 0.0–1.0), and fault-diagnosis confidence (`fault_confidence`, 0–10).

#### Workspace layout

- **Reorganized `crates/` into the 5-context layout from `GLOSSARY-MAP.md`** — the crate tree now has `crates/pipeline/`, `crates/evidence/`, `crates/integrations/`, `crates/interface/`, and `crates/shared/`. The meta-crate re-exports every library crate except `calxgloss-web`.

#### GhidraMCP 6.x migration

- **Migrated `calxgloss-ghidra` to the bethington GhidraMCP bridge** (v6.0.0, replacing the deprecated LaurieWired extension) — the client now speaks the bridge's snake_case endpoints, handles JSON responses and JSON errors, and resolves decompilation by function name through `search_functions`.

#### Pipeline & prompts

- **Evidence pre-analysis in batch translation** — `batch_translate` and `batch_translate_from_callgraph` now run each evidence scan (type database, type inference, algorithm, memory, sync, callback, control flow, string context, API, constants, serialization) at the start of a batch whenever its cache file is missing. A missing workspace, an unreachable Ghidra server, or a failed save only logs a warning; the batch proceeds.
- **Analysis context in prompts** — the escalate prompt, and for control flow also the ModuleContext and FullModule translation tiers, now read the persisted evidence caches and render sections for recognized algorithms, memory lifecycle, concurrency, callbacks, control flow, strings, APIs, and constants. A missing or corrupt cache means no context for that section, not a failed prompt.
- **Type and data-structure context from persisted caches** — the prompt context extractors that were previously stubbed now load the type inference and type database caches, and keep the records tied to the target function.
- **Translation attempts record their context tier**, so operators can later see which context scope yields the best pass rates.
- **`classify_dlls` reads PE headers** for accurate per-DLL export/import counts, instead of the stale counts from whichever program happens to be open in Ghidra.
- **Classification records persisted to disk** — `classify` now writes `re/classify/{dll}.json` and commits it to `main`; later `auto` runs skip re-classification.

### Fixed

- **Wrapped decompiler signatures parse** — Ghidra sometimes writes one function signature across several lines, and those lines failed to parse. Every scan that reads the whole function listing silently skipped those functions — about 41 of eqmain.dll's 4,358. Signature lines are now joined until the parameter list or body begins. Fixes #54.
- **Dashboard dependency edges (issue #10)** — the dashboard builder now records the shim→function dependency edge that the branch-creation policy already enforces, so a sent-back shim cascades `Blocked` to everything translating on top of it. The builder also matched the classify edge to the wrong DLL and classified shim units wrongly; both are corrected. The `Blocked` cascade no longer leaves `StatusCounts` stale.
- **Review verdict durability (issue #9)** — the dashboard builder now reads send-back and patch-request records, so `SendBack` and `PatchRequested` verdicts survive a dashboard rebuild and failing roots can cascade `Blocked`. Patch records written before this change read unchanged.
- **Patch records were never found** — the patch-record reader walked the wrong tree depth, so it never found records at `re/patches/{dll}/{function}/vN.json`, and `PendingReview` was unreachable in built dashboards. The walk depth is corrected.
- **Review actions 500'd on slashed unit ids** — accept, send-back, and patch requests failed when writing the audit trail for unit ids containing `/`, because the nested parent directories under `re/actions/` were not created. They are now created.
- **Default allocator names missed Ghidra's underscore-form `operator_new`/`operator_delete`** — the live 6.x decompiler writes the underscore form in function bodies, so whole-name matching never fired and allocation findings were missed. The default sets now carry both spellings. Fixes #6.
- **Report lines blanked on multi-byte characters** — the report-line padding helper compared byte length against the column width while truncation counted characters, printing some short lines empty. It now counts visible characters.
- **Web server panicked at startup (Axum 0.8)** — the routers used the legacy `:id` capture syntax, which Axum 0.8 rejects at startup. All routes now use the `{id}` syntax.
- **Static file serving** — JS and CSS returned 404: assets resolved against the process CWD instead of the crate directory, and the fallback handler was set up wrong. Both are fixed.
- **Live units 404'd in the unit detail endpoint** — a function still translating in this run had no stored unit to look up. The endpoint now consults the live progress state and creates a synthetic in-progress unit.
- **LLM request/response log rendered HTML-entity-encoded** — content now renders as raw text with minimal escaping, so JSON and code display correctly.
- **Unit detail error handler crashed** — when the detail view failed, its error handler could not reference the code body it meant to report, because the declaration was inside the `try/catch`. The declaration moved outside it.
- **Merged branch changes lost on hard reset** — the merge kept a cached reference to `main` that had gone stale, so a hard reset undid the merged branch's file changes. The cached reference is gone.
- **Empty cross-reference responses** — GhidraMCP answers 200 with an empty body when a function has no callers/callees. The client treated that as an error; it is now treated as a valid empty result.
- **Trims leading/trailing whitespace** from disassembly and decompiler output before sending to the LLM, keeping prompts cleaner and avoiding wasted tokens.

### Removed

- **Left sidebar dependency graph in the web UI** — the collapsible sidebar panel holding a small dependency graph, and its toggle button, are gone; the full graph view covers it.

### Refactored

- **Module splits across the workspace** — oversized files were split into focused modules: the CLI binary, the Ghidra/LLM/testgen clients, the prompt templates and builders, the reports dashboard, the translator pipeline, the verification crate, the git manager, the analyzer, config, the dashboard types, the PAL crate, and the web handlers.

## [0.1.0] — 2025-09-27

### Added

#### `calxgloss-translator`
- **Batch translation** (`batch-translate` CLI subcommand) — translates multiple functions from a single DLL in one invocation. It enumerates all exported functions with `--all-functions` or takes a comma-separated list with `--functions`. Every function gets a pass/fail report, and the summary shows success and failure counts with the pass rate. `--skip-git` runs the batch without touching git. Each successful function is automatically committed and merged to a git branch.
- **Full translation pipeline** — an end-to-end workflow: GhidraMCP → analysis → test generation → LLM → Rust code. It also translates directly from pre-collected data and estimates parameters from decompiler output.
- **Retry logic** — on failure, the translator escalates its retry strategy (CompileFix / TestFix / Escalate), with dedicated compile-fix and test-fix prompts.

#### `calxgloss-ghidra`
- **GhidraMCP HTTP client** — keeps a session against the GhidraMCP bridge and answers DLL queries (list, info, imports, exports) and function queries (disassembly, decompiler output, call graph, full analysis), with tracing logs throughout.

#### `calxgloss-llm`
- **Local LLM client** (Ollama/vLLM compatible) — sends non-streaming and SSE streaming completions through the OpenAI-compatible `chat/completions` API, strips code fences from replies, and carries tracing logs.

#### `calxgloss-prompts`
- **Prompt templates built with the Askama template engine** — translation prompts covering disassembly, decompiler output, Windows API mappings, and baseline tests, plus compile-fix and test-fix prompts.

#### `calxgloss-pal`
- **Platform abstraction layer** with a full Windows API → Rust equivalent mapping table: 100+ mappings across 10 categories (Win32 Core, GDI, DirectX, Win32 GUI, Audio, COM, Win32 Networking, Win32 Registry, VB6 Runtime).

#### `calxgloss-analysis`
- **DLL classification, call graph analysis, and Windows API tagging** — classification heuristics with lookup tables for 70+ Windows OS DLLs, 15 Microsoft SDK DLLs (→ wgpu/tiny-skia/skrifa), and 40 known third-party DLLs (→ fmod-rs/cpal/mlua/pyo3/flate2/vb6runtime etc.). A classified DLL takes one of the `PalMapping` / `CrateReplacement` / `ReverseEngineer` strategies. The analysis also scans disassembly for dynamically-loaded APIs.

#### `calxgloss-testgen`
- **Test generation** — generates FFI bindings with comprehensive Windows type parsing (60+ type mappings, calling conventions, pointer handling). Test inputs are generated with signature-based and disassembly-driven edge case detection. A baseline runner compiles and runs the tests in a temporary Cargo project, and baseline results save/load as JSON at `re/baseline/{dll}/{function}/baseline.json`.

#### `calxgloss-verify`
- **Sandboxed verification** — scaffolds a temporary Cargo project, runs `cargo check`, and verifies behavior against baseline tests. It generates the test harness and parses `cargo test` output, and provides PAL stub types for graphics, audio, filesystem, window, and thread abstractions.

#### `calxgloss-git`
- **Git automation for the translation workflow** — names branches `re/{dll}/{function}v{N}`, performs fast-forward and 3-way merges, writes patch record JSON files for failed translations, and provides branch, commit, merge, and revert operations.

#### `calxgloss-reports`
- **Terminal report formatting** — colored ANSI output for translation, verification, and classification reports, with pass-rate color-coding and batch summaries that mark each function with a checkmark or cross.

#### `calxgloss-web`
- **Web UI data models and an axum API router scaffold** behind the `server` feature flag, including a dependency-sorted review queue with status counts.

#### `calxgloss` (meta-lib)
- **Meta-lib** re-exporting all workspace crates.

#### `calxgloss-config`
- **Configuration crate** — loads settings from file, environment, and flags in that precedence order, validates each section, exposes typed settings, and reports the paths it searched when a value is missing.

#### `calxgloss-types`
- **Shared data structures**, organized by module: DLL analysis, function metadata, test cases, translation, verification, and Git automation.

#### `calxgloss-cli`
- **Full CLI binary** — `clap`-based `classify`, `translate`, and `verify` subcommands run the full pipeline (Ghidra → analysis → test generation → LLM prompt → code → write → verify → git branch/commit/merge → report), with configurable retries, LLM config, and `tracing-subscriber` logging.

#### Infrastructure
- **Project scaffolding** — 14 workspace crates and a workspace-root `Cargo.toml` with shared dependencies.
