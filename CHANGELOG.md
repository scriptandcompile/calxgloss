### Added

#### Unknown records

- **(P21, issue #376)** The derived dashboard now carries each unit's open-unknown state the way it carries parking reasons, so the web unit detail, the review queue with its per-binary tallies, and the terminal dashboard all read the same state from the same model — and an absent or unreadable ledger reads as *unknown*, never as zero. The model stores no copy of the ledger/resolution join: the builder joins records to resolutions per unit during derivation — records scoped to the unit by their recorded function, functionless records riding only functionless units — and the unit's seat gains `unknowns`: the open records in ledger order with kind, severity, question and required evidence, a severity tally across Blocking/Material/Notable, and settled resolve/dismiss counts alongside. The ledger's three readings (no document, the records key absent, an explicit empty set) and the resolution ledger's absent-versus-empty stay distinct all the way onto the wire, where an absent field means unknown. Honesty at the edges: a corrupt ledger or resolutions document degrades every affected unit to unknown with a warning rather than filing a zero or failing the build. On the surfaces: the terminal queue gains an Unk column (`?` for unknown) and the unit view an Open Unknowns block showing each record's severity, kind, question, evidence and revision; the web review queue rides per entry as a chip colored by worst open severity, `?` when the ledger's state is unknown; the unit detail grows an Open Unknowns section under Known Gaps listing each record with its question, severity and required evidence, resolved/dismissed shown as settled counts distinct from the open list; and the binaries rollup and per-binary function tables gain Unk columns where `null` means unknown rather than none. No new surface machinery — the review surface grew fields on the derived model only, and the reviewer's resolve/dismiss/reopen from #374 stay API-only until dedicated action UI lands. Pins: the builder joins open records onto the carrying unit with severity counts and scopes other functions' records away, degrades absent, keyless, corrupt and empty ledgers per their distinct readings, keeps settled records off the open list with their counts, and poisons a binary tally as soon as any of its functions is unknown; the wire carries no `unknowns` key for an unknown unit while the known-and-none unit serializes its empty list, keeping the readings distinct at the JSON edge; the web fold mirrors the terminal poison rule.

- **The ladder files its own pruned escalate and refused tier steps as standing questions (P21, issue #372)** — the third unknown-record producer, turning P20's pruning evidence from a silent skip's beside-note into the ladder's own admitted gaps: every escalate rung the walk prunes on a re-asked family the held report declares `unavailable` files one `retry_pruned` record per blocked family, and every context-tier step it refuses on the same rule files one `tier_refused` record. Filing happens at the decision itself, inside the two prune arms, and changes nothing about it — the attempt walk, the `Pruned: escalate would re-ask …` hint, and the tier-hold hint all stay byte-unchanged, the walk never reads a record back, and the ladder keeps owning which prompt runs (feedback into strategy is P27's). The two kinds keep the shared mapping pins: declared `unavailable` lands at `blocking`, the same honest criterion the seam's own unavailable family already answers to, spelled for the decision the admission blocked. A pruned escalate's record is built on that family's own admission line — the bare status word the fallback when it gave no reason — its origin a `retry_decision` naming the family the pruned rung would have re-asked, and its source slot that family id, so a later escalate rung pruned on the same family re-derives one standing question, never a second opinion; the refused tier step takes exactly one record whoever many families held it, its origin naming the tier the ladder refused to step onto and its question joining every blocked family's admission in exactly the wording the tier-hold hint uses. The carrier is the run itself: the loop hands its residue up on the `RetryResult` — the only carrier a tier refusal has, since a refused step adds no attempt record — and the pipeline folds it into the same per-binary accumulator as seam and coverage residue, deduplicated by id; a ladder with nothing pruned hands up nothing and opens no ledger. Re-deriving the same decision across attempts, batches, and runs lands the same id with revisions and first-seens untouched, and the two filing functions in the ladder-residue module are these kinds' only write sites, recognized by the shared roster checker — the full pairing sweep stays the roster ticket (#375). Pins: canned-report walks over the capped and uncapped climbs assert the recorded attempt walks and prune hints byte-unchanged beside the new records, the same run repeated lands each id once at revision 1, and the loop's policy-only budget pin stays green — the arms only call the producer module's filing functions, though it sits at its 600-line ceiling now, so future loop growth must argue the budget. Kuna declares its full roster answerable, so no ladder run prunes today and every fixture walk and byte-identity pin stands untouched.
- **The batch files the analysis seam's unavailable families as standing questions for the units that would re-ask them (P21, issue #371)** — the second unknown-record producer, where P20's held capability report and P21's record vocabulary meet: every question family the batch's held report declares `unavailable`, and that this unit's retry posture would actually re-ask of the seam, files one `analysis_family` record against that unit. Filing happens at the unit's entry into the retry wrapper — before its first attempt, covering both batch paths — because it is the unit's posture, never its outcome, that the admission bears on; the ladder's steering reads (operator caps, reviewer-forced strategy, the held report itself) settle once ahead of the filing, so filing and ladder walk one and the same posture. Posture is the ladder the loop is configured to walk: it re-asks P20's own re-asked roster — `function-inventory` and `decompilation` — exactly when the unit has more than one attempt and the ladder can step onto an escalate rung, either through `escalate_on_failure` or a first strategy forced straight onto escalate; a ladder that never escalates asks the seam nothing beyond its first attempt and files nothing. The mapping keeps the shared pins: declared `unavailable` lands at `blocking` — the answer could never have arrived at all — and the question is built on the entry's own admission line, the bare status word the fallback when it gave no reason, exactly as `FamilyCapability::admission` spells it. The required evidence names the family that could not answer, the origin carries that family, and the source slot is the seam's own family id, so the shared derivation repeats the same id across attempts, batches, and runs. Four rules keep the filing honest in both directions: an answerable family derives nothing; a family the report never declared — which reads *unknown* — derives nothing in both directions, absence never producing a gap record and a produced record never resting on an absent declaration; a family outside the unit's re-asked roster derives nothing against that unit, however honestly the report admitted it; and this derivation is the kind's only write site — no new analysis happens here, only families the engine itself admitted it cannot answer become records. Seam residue accumulates into the same per-binary set as coverage residue, deduplicated by id — the same gap re-derived is one question, not a second opinion — and a seam that admitted nothing opens nothing: the coverage fold keeps sole ownership of filing a ledger nobody's producers contradicted. The shared roster checker recognizes this write site, so `analysis_family` pairs with a producer; the full pairing of every kind is the roster-sweep ticket. Kuna declares its full roster answerable, so no fixture batch files a seam record today and every landed ledger, prompt render, and byte-identity pin stands untouched.
- **Open unknowns render into the escalate and module prompts through the evidence bundle (P21, issue #370)** — a filed ledger finally speaks to the model: the analysis's own admitted questions ride the per-unit evidence fold as one more projection row, and one shared section include renders them into exactly the bundle-fed readers — the escalate rung, the module-context tier, and the full-module tier. The `unknown ledger` row loads `re/unknowns/<binary identity>.json` joined with the reviewer's resolutions document before any selection, so a resolved or dismissed record folds away at the read and a reopened one rides back in; only records naming this unit's function and reading open reach the prompt, and a record about the binary itself never enters a unit's prompt. The join never feeds coverage residue from the ledger — the ledger is what the batch already admitted, and residue from it would let the ledger inflate itself. The ledger document's three read states keep their doctrine through the row: no document and a document without its records key read as missing (the field stays empty, and no render reads absence as zero gaps), an explicitly empty list reads as known-and-none, and a corrupt ledger or a corrupt resolutions document degrades exactly like every other row's corrupt document — the gather never fails. The include owns the render bound in P19's five-plus-count discipline: the first five open records in ledger order quote their question and required evidence verbatim, the remainder folds into one `(+N more open questions not listed)` line, and a unit with forty open gaps keeps the section bounded. An empty or absent ledger contributes literally nothing — every affected template renders byte-for-byte what it rendered before any ledger was filed, pinned by the heading suites — and the section's wording is verbatim-pinned by the prompts section suite, which registers the row in the named-row roster so a forgotten registration fails CI. The section states the admitted gaps and the evidence that would settle them; it never prescribes a strategy, and the ladder keeps owning which prompt runs. Pins: render tests over the section's bound in all three readers, settle/dismiss/reopen folds at the gather, the absent/empty/unusable ledger never failing the fold, the escalate adapter's end-to-end prompt, and a fixture ledger staged before a whole ladder run — the recorded LLM-request prompts, exactly what the web LLM I/O log stores, quote each open question once, never a settled one, and carry the count line at rungs 4, 7, 8, and 9 while the non-bundle rungs carry no section at all.
- **The batch files the gaps its own evidence reads admitted — the first unknown-record producer (P21, issue #369)** — P19's coverage stamps and P21's record vocabulary meet at the pipeline's projection read seam: while a batch's per-unit evidence fold reads each filed document, every facet that document stamps `partial` or `unavailable` becomes one `coverage_facet` unknown record, and the batch files the per-binary ledger at `re/unknowns/<binary identity>.json`. No new analysis: only gaps the engines already admitted on disk become records, and this derivation is the kind's only write site. The shared severity pins are spelled — `partial` lands at `material` (a facet that fell short by its own admission is that level's honest criterion), `unavailable` at `blocking` (the establishing evidence never arrived) — while `complete` and `unexamined` facets, and documents carrying no coverage record at all (pre-P19 documents, whose absence reads as unknown), derive nothing: absence never produces a gap record. Each record's question is built on the facet's own limitation line, falling back to the bare status word exactly as `ScanCoverage::admission` does; its required evidence names the facet and the document that fell short; its origin carries that pair, and its source slot `{document}#{facet}` makes the same facet admitted short by two documents two gaps. Records are function-scoped and derive their ids through the shared rule, so the same re-admission lands the same id. The derived set is accumulated in scan order — the known-library document read outside the seam first, then the folded rows in table order, each document in its coverage record's own facet order — deduplicated by id, and filed at each unit's end through the shared filing merge: a re-run lands the same ids with revisions and first-seens untouched, a revision bumps only when a persisted field actually changed on disk, and the document is replaced outright — always the current derived set, never an append log. A batch whose folds never read a document files nothing: the ledger's absence keeps reading as unknown, and filing an empty set nobody looked at would be the dishonest known-and-none. The reviewer's resolutions document feeds the merge's reopen marks and is never touched by the write — a corrupt one reads as no marks and never stops a batch — while the pipeline's own landed ledger is different: an unreadable one fails the write loudly rather than guess past the document it replaces. The shared roster checker recognizes this write site's pairing; the full sweep across every producer is the roster ticket (#375).

- **The shared unknown-record vocabulary lands with deterministic ids, a merge rule, and review pins (P21, issue #368)** — the foundation of the unknowns track: nothing files a record and no screen shows one yet; this ticket builds the shapes every later ticket speaks through. An unknown record states one fact a run noticed — a facet, analysis family, or export that fell short — with where it was noticed (binary, function, kind) and what was in force at that moment (the declared version, the export, the analysis run), plus two admission lines: what was learned and what it cost. Its identity is derived, never assigned: the same subject and the same in-force snapshot always produce the same id, and no id component comes from free text, so a reworded admission is the same unknown — the same id, and any reviewer decision already attached to it stays attached — while a different facet, family, or export is a different unknown with a different id. Six kinds are declared in code (`coverage_facet`, `analysis_family`, `baseline_never_run`, `export_uncovered`, `retry_pruned`, `tier_refused`) and the severity set is closed at three levels, with `blocking` meaning the establishing evidence never arrived at all — the only level that blocks a done claim. A shared roster checker names, from the declaration side, the same three faults the derivation side has always named: a kind missing a declaration, a declaration nothing derives, and a faulting subject listed twice. Two documents carry the vocabulary into storage per binary. The ledger document keeps its records in derivation order, each record carrying its derived id — the join key reviewer resolutions bind to — and carries a filing envelope: a document without its envelope is not a filed ledger, it is an unreadable one. The resolutions document belongs to reviewers and stores one entry per record id: the disposition (`resolved` or `dismissed`), a required bounded reason, the record revision the decision was written against, and the instant it was written. Filing is a merge rule with four clauses: re-derived records keep their first filing instant and bump nothing, a refresh that changes no persisted field bumps the revision zero times, a slot that stopped deriving disappears from the ledger's current face while its resolution stays durable, and a reopen adds exactly one ledger revision when nothing else has moved since the reviewer acted — so review actions never rewrite the ledger themselves, and nothing is ever deleted from or rewritten in the ledger document after filing. Reading the ledger keeps three states apart, exactly as coverage doctrine demands: no document at all, a document whose records key was never written, and a document carrying an explicitly empty records list, the first two unknown and the last known-and-none; a malformed document stays a parse failure, never an empty one. Writes against a record whose revision has moved fail as the standing "changed underneath" conflict, naming the state actually landed, and only a fresh attempt can proceed. Two writers can never clobber each other: re-filing merges through the rule without touching reviewer entries, and two reviewers' decisions on different records coexist in one document.

#### Seam capability report

- **The analysis engine now says which questions it can answer (P20, issue #354)** — the seam now carries a capability report beside its provenance: one entry per query family — `function-inventory`, `decompilation`, `disassembly`, `strings`, `caller-edges`, `xrefs`, `type-database`, `data-items`, `imports`, `exports`, `image-base`, `memory-reads` — saying whether the analysis engine can answer that family right now. A family it cannot answer carries one bounded reason line; it is the report's only free-text slot. A family absent from a declared report, or a source that declares no report at all, reads as `unknown` — never answerable, never unavailable — and `unknown` is a word no analysis engine can write about itself. Kuna declares its full roster honestly today: every family answerable, nothing admitted. The report is live session state — nothing new persists into scan documents or cache keys, whose admitted scan coverage stays the persisted half — and the scan read cache and the pipeline's scan source pass the report through unchanged: a cache never changes capabilities, it only caches answers. The prompt, the retry ladder, and the run reports start reading the report in the entries below (issues #355–#357).

- **Prompts admit the query families the analysis engine cannot answer (P20, issues #355, #357)** — the translator reads the seam's capability report exactly once per batch, beside opening the batch's cached scan source, and holds it for the whole batch; reading the report costs no additional analysis-engine read. The escalated prompt's imported-APIs section reads the `imports` family from that held copy. When the seam declares `imports` `unavailable`, that section opens a one-line `Analysis engine:` admission beside its entries — a heading and the line when the surface filed nothing, never a bare silence and never an invented answer (issue #355). The same admission now covers every query family that feeds a prompt section — `decompilation`, `disassembly`, `strings`, `caller-edges`, `xrefs`, `type-database`, and `data-items` on top of `imports` (issue #357): an unavailable family adds exactly one bounded `Analysis engine:` line to each prompt section it feeds, beside the entries that section filed, with heading plus line when it filed nothing. A section fed by several unavailable families opens its heading once and carries each family's own line in roster order, never a merged admission. The escalate, module-context, full-module, rich, and detailed prompt templates all read the held report, and the `module_context` and `full_module` context tiers fold it in the same way the escalate retry strategy does. Answerable and undeclared families render byte-for-byte what they rendered before the seam spoke, empty evidence bundle included. The families that feed no prompt section — `function-inventory`, `exports`, `image-base`, `memory-reads` — stop at the seam declaration: they never print a prompt line. Kuna declares every family answerable, so no production prompt changes today. The scan command's run report grows the matching `Seam:` line after its report, only for families the opened seam itself admitted unavailable; since the real Kuna seam declares every family answerable, today's run reports print no `Seam:` line, and the difference between a run report and a `--show` report stays exactly the one run-path-only exemption recorded in ADR-0054.

- **The retry ladder prunes retries that would re-ask what the analysis engine cannot answer (P20, issue #356)** — an escalate retry, and a context-tier step onto `module_context` or `full_module`, re-ask the seam for the neighbor listings and function bodies it just failed to answer — the families `function-inventory` and `decompilation` — so those retries can only re-produce the empty context that made the retry necessary. Before spending an attempt, the ladder now consults the capability report it already holds, and that decision costs no additional analysis-engine read. When the report declares either re-asked family `unavailable`, the escalate retry is pruned: the attempt record carries the ladder's own `pruned_escalate` label and one line in the seam's own admission wording — `Pruned: escalate would re-ask decompilation — unavailable — <the engine's reason>` — that line then appears in every following fix prompt's failure history beside the unit's other hints, and the ladder rotates to a retry strategy that can close the unit. A tier step never steps onto a module context tier in the same situation: the unit's context stays at the last tier the analysis engine answers, and the attempt record carries the matching `Pruned: tier escalation to module_context would re-ask …` hint. Neither case is ever a silent skip. The rule works in both directions: only a declared `unavailable` prunes; an answerable family admits nothing to prune; a family the report never declared reads `unknown` and blocks nothing; and a family outside the re-asked pair never blocks a retry. Kuna declares every family answerable, so today's production retry ladders are untouched.

#### Engine-identity cache key

- **The scan read cache names the analysis engine build that filed it, so an engine swap can never replay stale answers (P20, issue #358)** — until now the cache manifest guarded against engine changes only with a hand-bumped version integer: every change to what the analysis engine answers asked a contributor to remember to raise `CACHE_FORMAT_VERSION`, and a forgotten bump silently kept replaying the old analysis engine's scan documents. The manifest now records the identity of the engine build that filed it — the seam's own provenance stamp: engine name, pinned release, and pinned source revision, spelled `name@version@fingerprint` — and a mismatch forces cold reads automatically, with no version integer involved: a manifest filed under one engine identity and opened under another is not a surviving scan, and bumping the pinned engine crate moves the identity on its own. A manifest written before this field existed — raw bytes carrying no identity at all — loads without error, reads its identity as `unknown`, which no real engine identity can ever match, and goes cold; never hot, never an error. The pipeline's version pairing now refuses a sibling scan document filed under a different engine identity, so a batch never pairs answers the opened analysis engine did not produce. The version integer keeps its job, narrowed to the record-shape gate it always was: `CACHE_FORMAT_VERSION` stays at 4. The cache layout, binary-hash keying, safe filenames, gitignore ensuring, and the `--refresh-cache` hatch are untouched.

#### Seam-capability track close-out

- **The seam-capability track closes with its end-to-end checks (P20, issue #359)** — the final ticket of track #353: no new behavior, only the standing checks that keep the whole track's rules in force in one pass. The declared families and the seam's own query methods are paired against each other through the real pipeline's scan source: every query method claimed by exactly one declared family, every declared family carried by the read exactly once, and an orphan in either direction fails, naming every offender at once. Any future track — P28's masked byte search, P29's def-use primitive — that grows the seam without growing the roster, the declaration, and the read in the same change fails in one pass, naming itself. Today's real Kuna seam declares every family answerable, so today's run reports print no `Seam:` line anywhere, and the difference between a run report and a `--show` report stays exactly the one run-path-only exemption ADR-0054 recorded — nothing else. The two admission doctrines share one wording but keep their own frames: a coverage record and a capability entry that spell the same sentence about the same kind of falling-short produce byte-identical admission text by design, while the frames keep the lines apart — `Coverage:` beside `Analysis engine:` in prompts, the family name and the `Seam:` label in run reports — so the two kinds of admission never merge into one line and never borrow each other's frame. When the pinned Kuna build changes, every scan directory filed under the previous build's identity goes cold at once and is re-filed naming the build that answers now, while a directory filed under the current identity survives every check untouched — the refusal is the bump itself, not a hand-raised number. The review UI needed nothing new, and that stands as a decision, not an omission: it renders filed documents, and the capability report is live session state with no filed half to display. ADR-0055 records both doctrines — the analysis engine declares its own answer surface, checked one-for-one against the seam's query methods and the real pipeline's read, and the engine build's identity, not a hand-bumped integer, keys the scan read cache — amending the engine-drift narrative written in ADR-0042 and ADR-0043. With this, P20 is landed on the roadmap and P21 is unblocked.

#### Admitted scan coverage

- **The apidetect scan admits its delay-import blind spot end to end (P19, issue #346)** — the coverage record shaped in issue #345 now speaks everywhere an apidetect artifact is read. A scan's coverage record states, facet by facet, how much that scan could read; this ticket puts the record to work, and the tickets below give the same voice to the other evidence engines. The apidetect evidence engine stamps its record inside its own scan: the `import-table` and `api-usage` facets examined, `delay-imports` never examined. An API document's record fills the prompt bundle's coverage field exactly once per document, while missing, corrupt, or pre-P19 documents fill nothing, keeping their old renders byte-identical. The shared libraries-apis prompt section appends exactly one bounded admission line — `Coverage: partial — delay imports unexamined`, wording owned once by the shared coverage type — whenever the record admits falling short, and the line renders even when no findings were filed, so an empty list from a partial scan never reads like the silence of a complete one. The `apidetect` run report and its `--show` report print the same admission line beside their counts, byte-identically to each other. The command's name, flags, and existing report wording are untouched. These rules repeat across the track and are not restated below: missing, corrupt, and pre-P19 documents fill no coverage field and keep old renders byte-identical; each prompt section whose record admits falling short appends exactly one bounded `Coverage:` line and nothing under complete coverage; each scan's run report and `--show` report print the same admission line beside their counts; and no command's name, flag, or existing report wording changes.

- **The libmatch and floatsimd evidence engines speak their limits out loud (P19, issue #347)** — the admitted-semantics track's third ticket, closing out issues #345–#347. The libmatch matcher has always concluded "same body shape, so same library function" from decompiled bodies alone: no signature carries version authority, but nothing said so. Every match record the evidence engine files now carries a per-finding admission note — `Signature match, version unknown` — stated beside the rule that admits it, old records without the note still load, and the shared libmatch prompt section renders the note beside each finding's evidence. The floatsimd scanner's silence used to be ambiguous: a function with no floating-point call might have been examined and clean, or never examined at all. So its scan, which already counts its skipped bodies, now names what it never reached — its document-level coverage record marks the `function-bodies` facet `partial` and names the unreached functions when a pass skipped any — and the shared floatsimd prompt section appends the same bounded `Coverage: partial — …` line the apidetect section renders. A complete record's silence reads as examined-and-clean; a partial record's never reads that way. Both evidence engines stamp coverage inside their own scans, fill the prompt bundle's coverage field exactly once per document through the read seam, and print the admission line in their run reports beside their counts, byte-identically to their `--show` reports; the commands' names, flags, and existing report wording are untouched.

- **The typesdb and consts scans state what they could not read (P19, issue #348)** — the track's fourth ticket. A `typesdb` scan over a target that yields no vtable evidence — a stripped release build, a non-MSVC binary — used to file a database whose vtable section was simply empty, byte-identical to a program with no classes. Now the scan names its single `vtables` facet `unavailable`, with its reason ("no vtable evidence on this target"), inside its own document, and a scan that found tables stamps `complete` — so zero recorded vtables reads as a property of the target. The shared data-structures prompt section appends exactly one bounded `Coverage:` admission line beside its entries whenever the record admits falling short, and adds nothing under complete coverage; unlike the constants sections, an empty structures list opens no section to qualify — structures the scan never recovered near this function establish nothing either way. The `consts` scan now names the regions it read: its `function-bodies` facet goes `partial` with a limitation line naming the function bodies the decompiler never produced — bounded at five names, the remainder folded into a count — and its `data-objects` facet goes `partial`, naming the data-object memory windows that never arrived. An object the scan read and claimed no table for stays unmentioned: that gap is the object's shape, not the scan's border. The one constants scan feeds two evidence surfaces, so the constants section and the data-tables section each carry the same one admission line; over a region-limited scan an empty constants section still renders its heading beside the line, letting an escalate retry tell "this binary has no constants" from "the constants scan examined little and filed almost nothing". The `typesdb` and `consts` run and `--show` reports print the limitation lines beside their count breakdowns only when there is something to admit, byte-identically to each other, and a line too wide for one report row breaks at its facet boundaries instead of mid-word; names, flags, and existing report wording stay as they were.

- **The global-state, error-handling, and callback scans admit the bodies they never reached (P19, issue #350)** — the track's sixth ticket, covering the last three evidence engines the track's problem statement named, with the same rule as issue #349 for their `function-bodies` facet: `complete` when the decompiler produced every body, `partial` with a limitation line naming the never-reached bodies, bounded at five names and a count. - **Branch inventory, end to end (P12.5/#224, issues #258–#261)** — the `controlflow` scan now records every branch site in each function body: guards, loop exits, else arms, and switch arms. Each qualifying object claims one `DataTable` finding carrying the symbol, address, element type, entry count, and values inline up to 512 with a truncation flag while the count stays whole, the referencing functions from `xrefs_to`, the evidence lines that carried the reads, and a `const NAME: [T; N];` suggestion. A bare `DAT_*`/`switchD_*` label takes its mechanical uppercase form; a meaningful label names its table verbatim. The stride is settled by agreement, not guesswork, with the same care as candidate selection. First come the widths the bytes decode cleanly at — a width must divide the length into at least two entries that are nonzero and not all equal, so a fill or a gapped run is not a table — and the widths implied by the reads' bounds guards then narrow that set. An object viable at exactly one width decodes as that element type. Where several widths are viable, the type the analysis engine applies to the object resolves it — that is authoritative — unless the bytes contradict the listing: an array count that does not fit the length, an applied type whose own decode is incoherent, or a guard naming another width claims nothing rather than a guess. With no applied type, the guard-implied widths narrow the viable set and only a single surviving width claims. An object incoherent at every stride, a fill, a gapped run, and a mix of magnitudes claim nothing at any tier. Confidence comes out by family instead of one anchor: an applied type the bytes confirm is the top tier at 90, a clean decode corroborated by an indexed body read or a guard-named stride is 70, a clean decode whose object carries cross-references but no kept read is 50, and a decode nothing references at all is 30 — visible in the record's confidence, evidence, and report breakdown. Float elements join the record: an f32 or f64 table names its element type and carries its entries as raw bit patterns, readable only at that width when the integer readings are incoherent. The coherence rule that keeps them honest is a bounded band with a magnitude spread no wider than an order of magnitude across the entries — an entry outside the band, a wild exponent, or a table that jumps orders of magnitude is noise, not a table. The reading also refuses the objects that only look like constant arrays. A kept body that writes through a table's symbol — a plain assignment (`DAT_x = 0;`), a store through an index into it (`DAT_x[i] = v;`), or a store routed through it another way (`*(int *)(&DAT_x)[i] = 3;`, `*(int *)(DAT_x + 4) = 0;`) — disqualifies the object outright, because a written global is mutable global state, the global-state track's territory, never a `const` array. Comparisons, reads through casts of the symbol, and string literals naming it are not writes, and the check watches only the bodies the scan actually keeps as evidence. An object whose every entry resolves to the function the listing names claims nothing even when its bytes decode cleanly under a sizing guard: that is a dispatch table, and the callback scan's jump-table reading owns it outright. The same goes for an object with only some entries resolving — a half-decoded mix whose pointer interpretation belongs to the types track, not a const array of numbers that are really addresses. The veto is resolution, not magnitude: a large value that no listed function starts at stays an ordinary scalar and lands with the table. The reading rides the seam's existing reads — `data_items`, `read_memory`, `xrefs_to` — adds no new ones, and keeps no bodies past the walk. It appends after the color palette in data-listing order and lands under the new `data_table` finding kind: documents written before the kind existed still load finding-for-finding unchanged, each referencing function's lookup surfaces the table, and the `consts` report names the kind in its breakdown. The generated constants file grows a data-table pass: each `DataTable` finding becomes a `pub const NAME: [T; N] = [ … ];` declaration spelling the record's element type, entry count, and decoded entries, named by the label's Rust form and sharing the file's whole-file collision machinery — a name an earlier declaration already holds gains the next free `_2`, `_3` suffix in render order, so a context name and a table label colliding on one spelling still get distinct, stable declarations. Tables render sorted by address, twelve entries to a line, integers in hex as the file spells every other value, and a float table's raw bit patterns re-spelled as the shortest literals that read back as the same float, a stray non-finite pattern spelling the type's `NAN`/`INFINITY`/`NEG_INFINITY` path so the emitted array is valid Rust whatever the record holds. A truncated value list gets a comment stating the full entry count above a declaration whose length matches the entries actually spelled — the render never pretends a prefix is the whole table — and two renders of one document are byte-identical. The first attempt also sees the tables: the module-context prompt grows a DATA TABLES section between PARAMETER DIRECTIONS and the external-function rules naming every `DataTable` finding whose referencing functions name the target — table symbol, element type and entry count spelled as the Rust array type (`const [T; N]`), and the confidence behind the claim — loaded through the evidence gather that already reads the per-binary `consts` document once and splits it into constant hints and data-table hints. The escalate prompt's existing CONSTANTS section picks the tables up automatically, each entry naming its element type and count. A function touching no table renders no section and pays no tokens, and a missing, corrupt, or failed `consts` document degrades to no section at all — never a failed prompt.

A body naming one of the compiler's exception-handler thunks — `__except_handler3` or `__except_handler4`, with the MSVC-decorated `__` spelling admitted and the `_except_handler4_common` runtime routine, or a name merely embedded in a longer identifier, refused — claims a `named_handler` finding at band 70 carrying the thunk name as its evidence. The shape rules are the false-positive floor: BOOL-shaped `return 0`/`return 1`, ordinary small-integer comparisons, and out-of-band values — the C++ eh code `0xE06D7363` the raise finding loves among them — claim nothing, though a raise finding still stands with its code quiet. Arguments of other calls, indexed addresses, and dereferenced loads are never sites, a literal inside a string or comment never counts, and a returned expression that is itself a comparison (`return (hr == 0xc0000022);`) hands back a 0/1 rather than the code, so its literal sits honestly at the guard band. Codes also travel along the call map, so a caller's contract is inherited rather than guessed. Only codes travel, because a callee's spelled frame, `RaiseException` claim, named handler, or cleanup shape names how the callee handles failure, not what its caller faces. The reading adds no engine reads: the call edges come off the same kept bodies, and each callee's code set comes from re-running its reading over text the scan already holds. The section steers the Rust mapping finding by finding: idiom bullets lead with the scan's own suggestion — an exception-mapped error type for a spelled frame, early returns plus RAII or scope guards for a cleanup ladder — naming the target idiom, the confidence band, and the deciding body line; a `raise_exception` finding appends the code it raises; failure-code bullets spell the code and its site; and inherited-code bullets name the callee the contract rode in on. - **Binary-version diffing, end to end (P18/#233, issues #294–#300)** — a new `bdiff` pass pairs two versions of one binary. It takes the old scan and the new scan as snapshots in memory — function listings, exports, kept bodies — and writes one confidence-scored pairing document saying which new-version function *is* the old one, so the queue can tell "same function, new address" from "changed function" from "genuinely new function". The shared rule arrives first: the body normalization the `libmatch` scan already applies before matching becomes the project-wide meaning of "same body shape", so the diff track consumes the shipped rule instead of carrying its own normalizer — one shared rule with one owner — and the shipped scan's behavior is untouched. The pairing ladder opens with name identity. An exported name present in both versions, or a demangled name matching exactly — the `::` chains, spelled parameter lists, and demangled `operator.` spellings the decompiler itself writes — pairs at 95 on the evidence scale. A lone signal claims nothing (ADR-0038), so equal addresses pair nothing on their own, and neither does a matching `FUN_…` spelling: that spelling is itself an address. Functions that merely *moved* across a version update — renamed `FUN_…` spellings, shifted addresses, identical bytes — pair through the `normalized_body` family using the shared normalizer. Both versions' kept bodies go through it: byte-equal normalized shapes pair at 90; a body that is not byte-equal is diffed line by line over the normalized sequence and scores on its structural-diff ratio, counting every changed, added, or removed line as one edit, landing between the carry-over floor and the byte-equal 90 — a ten-line body whose update rewrote one statement pairs at 89; a pair sharing less than 60% of its normalized lines is a clearly different body and pairs nothing; and a blank kept body — a failed decompile listing nothing — pairs nothing, because blank-on-blank byte-equality proves nothing and a lone structural coincidence claims nothing. Body-family records carry the normalized-body diff as their evidence: a summary line naming the edit count and similarity ("normalized body diff: 1 of 10 lines differ (90% similar)"), then the first few edits quoted in body order as `changed:`, `added:`, or `removed:` lines with the remainder named. A byte-equal pair says so beside its line count. An engineer can therefore audit why two functions were called one function without re-deriving the pass. Functions whose bodies changed too much to pair by shape, but whose *neighbors* in the call graph already paired, pair through the `call_topology` family. Each snapshot yields a call map derived purely from the bodies that snapshot itself carries: every whole identifier token that is one of the snapshot's own listed function names reads as a call or a handed callback (ADR-0024's token rule, no engine read), and a self-mention records no edge, so a pair can never corroborate or propagate itself. An unpaired function claims its first agreeing partner once at least two distinct paired neighbors agree in the same direction. Two exported callers agreeing on a renamed callee pair at 70 on the evidence scale, deliberately below the 80 carry-over floor: topology on its own earns persistence, and the carry-over consumer still applies the floor. Claims enter the pair set immediately and the pass iterates to a fixed point, so a chain of renamed functions pairs through neighbors that converged themselves. The walk follows old scan order and takes first agreeing partners, so one fixed point diffs clean (ADR-0028's positional rule again), and a lone paired neighbor is a lone signal that claims nothing (ADR-0038). Topology records name every paired neighbor they stood on, quoting the first few and naming the remainder. Two independent families reading one pair beat either single reading, so a body-family pair that topology also agrees on gains a 5-point bump: a byte-equal body pair corroborated through two paired callers rises to name identity's 95 and never past it. The record keeps the `normalized_body` family — a corroboration is not a competing claim — and adds its paired-neighbor evidence lines beside the body diff that won. Pairings resolve one-to-one throughout: each function pairs at most once per side, the best score wins (ADR-0022), and a tie keeps the first seen in scan order (ADR-0028's precedent), so two documents of one version pair diff cleanly. Every record names both spellings, its family, its confidence, and its evidence lines. The pass is pure text and structure over documents: no new seam reads, no engine reads (ADR-0026 untouched), no program mutation (ADR-0020), no LLM. It persists one document per (binary identity, old bytes, new bytes) through the shared JSON store at `re/analysis/bdiff/<binary>-<old-sha256>-<new-sha256>.json` — a new file, so every previously persisted analysis artifact loads unchanged. The key is the hash triple and the document itself names both hashes, so a stale document from a since-replaced version is detectable rather than silently trusted, and the file's presence is the reuse-the-document check. The run's scan step pulls the trigger: when the live binary's warm scan cache sits beside a surviving cache directory from an earlier version — the scan cache keys on identity plus SHA-256 of the file bytes (ADR-0043), so the previous version's directory stays put when the bytes change — the pre-batch scan step pairs the two right after the scan pass closes and persists the document, so both batch entry points, with and without a call graph, pair the same way. A sibling directory counts as a scan only when it reads back whole at the current cache format version, its manifest naming that directory's own hash and its function listing present; a cold or unusable sibling was never warmed and stands for nothing read and nothing written. The sibling walk sorts its hashes so one workspace's runs compute and log the same documents in the same order. The trigger reads only the two directories' cached scan documents — function listing, export listing, and kept bodies — through the read-only surviving-scan reads of the seam, which keeps the trigger in the pipeline without making the analysis-engine adapter depend on the diff crate: zero engine reads, zero program mutation, milliseconds. The pairing itself is the shipped pass, unchanged. Reuse: a later run of the same version loads the persisted document for the live pair and never recomputes, and reuse requires the document itself to name the live binary and the live (old, new) hash pair — a renamed or since-replaced document is detected as stale, warned once, and recomputed rather than silently trusted, exactly the detectability the store promised. A binary that has never changed version has no sibling directory, nothing is persisted, and the queue behaves byte-identically to before. The trigger degrades and never fails a run: an unreadable binary, an absent cache, an unreadable document, or a failed save logs and the batch proceeds. Pairings stay pairwise, so longer version chains ride successive pairwise documents. The carry-over confidence floor — 80 on the evidence scale, following the `libmatch` Skip-floor precedent — is stated in one place: every resolved pairing is recorded regardless of the floor, and only the downstream carry-over consumer applies it. The payoff lands in the queue: a new-version function that pairs at or above the floor to an old-version function whose translation is *accepted* — a merged `re/{binary}/{function}...` branch, the review overlay's Accepted classification (ADR-0003) — gets its first attempt seeded from that accepted code instead of asking the LLM cold. The seed is a standard attempt branch under the new function name, pre-populated with the merged `translated.rs`, and the seeded unit then rides the normal pipeline: baseline capture re-run from the new binary through the existing Wine path, and full verification against the new bytes (ADR-0016's carry-over bet: the translation carries, the ground truth does not). Nothing a seed touches carries a Verified mark — the deterministic verification is the verdict. Provenance survives into the record: every seeded result names the old function and the attempt branch its code came from, and the new branch's commit says "seeded from {old} attempt {n} (paired, {conf}% confidence)". The staleness gate guards the seeds whole: a pairing document that does not name the binary whose current bytes are being translated and hash those bytes as its `new_bytes_sha256` seeds nothing, because a stale document describes a different version situation and seeding from it would be guesswork. The one-branch-one-seed rule lets an accepted translation seed at most one new function, the strongest pairing claim winning the branch, so two new functions never claim one merged translation. Below-floor pairings persist but seed nothing, and those functions queue fresh exactly as before. Seeds are collected from the pairing documents the trigger leaves in `re/analysis/bdiff/` during the same pre-batch scan step, and the accepted-code lookup goes through an injected port implemented outside the translator, which stays git-free. No port, no documents, unreadable documents, and functions without an accepted twin all degrade to "no seed": a fresh queue, never a failed run. Before any of that spends anything, `calxgloss bdiff --binary <name>` lets an engineer review the version change. It loads the pairing documents for that binary identity and lists every old↔new pair with the old name, the new name, the confidence colored on the shared bands the other reports use, and the match family that carried it, beside the functions paired on neither side — old-only and new-only listings, each side its own listing minus the paired names, in scan order — in the standard persisted-document report shape. Its breakdown line names every match family the document can carry with counts (`name_identity`, `normalized_body`, `call_topology` in ladder order), and a family with no records stays off the line. The live document is the one that names the binary and hashes the target directory's current bytes as its `new_bytes_sha256`; a document naming a since-replaced current version is never printed as live. A missing or stale document fails the run naming the gap — the stale pair's hashes beside the current hash, and how a fresh document appears — never an empty success. The command is pure report: no scan runs, no engine read (ADR-0026 untouched), no write-back (ADR-0020), no LLM, and its closing line reminds the operator that the run's carry-over seeds only from pairings at or above the carry-over floor. This track adds no web or dashboard surface.

- **Wide argument lists on the prompting and run path collapsed into bundles (issue #268)** — the escalate and module-context prompt builders took one list per evidence engine across the prompting boundary, up to 21 same-typed positional parameters where a transposition compiles silently, and the CLI run entry points took 14–20 positional parameters each. Every new evidence engine therefore meant touching every wide signature between the retry helpers and the templates, plus every call site. The seam now carries bundles instead. One evidence bundle, defined in the prompting crate beside the finding types it holds, feeds the escalate template constructors, both escalate prompt builders, and the module-context and full-module prompt-data constructors, and lower context tiers pass partial bundles; the translator's retry helpers gather it in one pass over the filed analysis documents and fill the call-graph lists from the live scan source on top. The run entry points (`auto`, `live`, and the per-binary pass) take run identity, options, and the cheaply-cloneable control handles as bundles too, and the compile-fix, test-fix, and edge-case-fix builders, the shim pipeline, and failure recording take their shared inputs as single records. Rendered prompts are byte-identical: the bundles only carry input, and no persisted artifact format changed.

- **Decompiler-noise stripping at the decompile read exit grows to the full /GS canary family (spec #232, issues #271–#273)** — a statically linked MSVC binary dresses nearly every function in stack-guard code that carries no meaning for translation and only dilutes the pseudo-C a scan or the LLM reads. The noise filter at the seam's `decompile` read exit now strips the whole canary family. Standalone calls to `__security_init_cookie`, `__security_check_cookie`, and `__report_gsfailure` — lines consisting solely of the call — are stripped at both analysis read exits. The epilogue half: an `if` comparing the saved cookie local against the cookie global, with nothing but the `__report_gsfailure` call inside its block, comes back from the `decompile` read with the wrapper, the comparison, and the failure call gone as one shape, and the function's real statements byte-identical around them. That check runs before the named-guard-call pass, because the failure call inside the `if` is what anchors the shape. The gate is deliberately conservative and strips only the complete idiom: a condition carrying a comparison against a cookie-global spelling (`__security_cookie`, `stack_cookie_guard`, or a `DAT_`-shaped unnamed global), a block holding exactly one standalone guard-runtime call, and no `else` attached to the wrapper on either side. A lone comparison, an empty or stuffed wrapper block, a condition without a cookie global, a hollowed `if` the named-call pass leaves behind, and idiom text spelled inside strings or comments all claim nothing and pass through. The prologue half closes the family: a line that is exactly one assignment storing the cookie global XOR'd with a stack-slot address into a local — `local_8 = DAT_18004a040 ^ (ulonglong)&stack0x00000008;` — comes back gone along with its line break, and a cookie local the strips leave unreferenced loses its declaration line with them. A full prologue-plus-epilogue canary body therefore comes back with the whole idiom gone. This recognizer runs after the other two, because whether the saved local is left unreferenced is only knowable once they are done, and its declaration sweep stays strictly inside the body's declaration block — the run of bare declarations the decompiler opens right after the body's brace — so a local any remaining statement still names keeps its declaration byte-for-byte. The conservative gate holds on the save statement itself: the assignment must be the line's whole content with exactly two operands, a cookie-global read (either operand order, behind any cast) and a stack-slot address (`&stack0x` plus hex). A lone XOR, a cookie copy without the XOR, a cookie XOR'd against a constant instead of a stack-slot address, a store into a global or through a pointer, a compound assignment, a three-operand XOR, and a save sharing its line with a comment or any other text all claim nothing and pass through byte-for-byte. SEH/EH frames, `try`/`catch`-shaped bodies, and landing pads are never part of a match — that is the error-handling scan's territory — and since the canary check is now stripped even from SEH functions' epilogues, the error-handling scan's own canary false-fire gate becomes redundant insurance. The never-empties rule guards the combined strips: a body made entirely of guard code passes through whole rather than coming back empty. The scan read cache keeps storing the engine's raw text whole (ADR-0043) — the filter runs on read, so deleting the cache recovers byte-identical unfiltered behavior — and the signature line passes through byte-for-byte. The filter is always on: no toggle, no CLI surface, no findings, artifact, or schema changes, and no extra engine reads. Each strip logs a debug line naming the function and the noise family (`guard-call`, `epilogue-cookie-check`, `prologue-cookie-save`), and a new noise family joins as one more recognizer in the filter's single home module, the seam untouched.

### Fixed

- **An import thunk named after its own import was translated as if it recursed (issue #269)** — a binary's one-instruction veneer for an API (`jmp [__imp_SetCursor]` → `user32!SetCursor`) carries the API's own name in the symbol table, so the decompiler renders its tail-jump as a call to that name and the function reads as infinite recursion (`SetCursor(); return;`) while matching none of the name-based thunk patterns — and the LLM would faithfully turn the apparent recursion into a Rust function that calls itself. The translator now reads the body shape instead of the name: a function whose whole body is one unconditional call to its own name — in either engine's spelling, comment slugs and return-type casts included — is refused as a skipped root on the explicit and batch paths and in pre-built requests, before any LLM token is spent, and the refusal names the shape as the reason. A genuinely recursive function, whose body carries a base case around the self-call, is not this shape and still translates.

- **A stripped 32-bit PE listed only a couple dozen functions (issue #270)** — the Kuna load went straight from bootstrap into the analysis commit without the options step, so the commit installed only what the loader itself knows: the entry point, the TLS callbacks, and the code pointers the base relocations name. On a 64-bit image that is mostly harmless, because the `.pdata` exception table recovers nearly every function, but a stripped 32-bit PE carries no `.pdata` and no symbol table: `LaunchPad.exe`, a statically linked MSVC GUI launcher, listed 17 functions where the image holds thousands, and every scan and the whole translation queue saw only those 17. The load now arms Kuna's own driver-default discovery bundle before the commit, exactly as `kuna decompile-all` does: `listing on` (the recursive call-graph walk) on every image, plus `funcstart_patterns on` and `aif on` (the prologue-pattern sweep and the aggressive instruction finder) on a non-x86-64 image, where the cheap x86-64 oracles are inert. `LaunchPad.exe` now lists 7,573 functions, and x86-64 keeps the aggressive pair off so the cheap path stays cheap and never over-produces.

- **The `typeinfer` scan spun forever on a large stripped 32-bit image (the 2026-10-20 `LaunchPad.exe` incident)** — the calling-convention corroboration pass checked every per-function convention record against every kept disassembly listing, and answered each check by re-splitting and re-parsing the whole listing, so the pass cost grew as functions × records × listing size. On 64-bit fixtures this stayed invisible: Microsoft x64 never spells a `ret N` epilogue, so epilogue records barely exist. A statically linked 32-bit MSVC image hands nearly every function a `ret N` record, so `LaunchPad.exe`'s 7,267 functions meant billions of row parses and tens of minutes of 100% CPU silence mid-scan, which read as a hung run. The pass now reads each kept listing exactly once and groups its call rows by the callee name they name, so every check becomes a lookup. The output is unchanged: bumps in record order, one call-site view per (caller, callee) pair in listing order, evidenced by the first site in row order.

## [0.3.0] — 2026-10-19

### Added

#### Analysis engine

- **Kuna analysis engine (epic X5/#203, issues #205–#211)** — a new analysis engine loads a target binary **in-process** through the Kuna console engine, pinned to Kuna `v1.878`, with the x86 SLEIGH specs compiled at build time and embedded in the binary. There is no Ghidra install, server, or port involved. Engine selection is a global `--engine <ghidra|kuna>` flag plus the `[analysis] engine` config key (environment variable `CALXGLOSS_ANALYSIS_ENGINE`); the default stays `ghidra`, and a run uses exactly one engine. Under `kuna` every scan read is answered — function listing, decompiled pseudo-C, imports and exports, image base, strings, cross-references, callers, type-library listings, structure layouts, enum members, data items, and raw memory reads — and consumers read Kuna's warning, name, and disassembly dialects. Type write-back compiles to Kuna `--assert` directives held beside the scan record at `re/kuna/<binary>.kuna` and replayed on every load. Scan records carry engine provenance: engine name, release tag, and pinned commit. Kuna runs beat the Ghidra passes they replace. Kuna's per-function watchdogs are calxgloss configuration: `[analysis] max_fn_instructions`, `max_fn_seconds`, and `max_fn_memory_mib` fail one oversized function by name, and the `DecompileBudgetExceeded` failure names the knob to raise and the `--engine ghidra` fallback, instead of hanging or exhausting the machine.

#### Evidence scans

- **Calling-convention detection (P12.6, #226, issues #245–#251)** — the type-inference scan now detects each function's calling convention, and its consumers use the answer. Readings come from the convention letter in MSVC-mangled listing symbols, the `@N` decoration on import names, and machine listings: callee `ret N` epilogues and caller stack cleanup for 32-bit, and the Microsoft-x64 call shape (shadow space plus `RCX`/`RDX`/`R8`/`R9`) for 64-bit. A cross-function pass raises a reading agreed by epilogue, decoration, and caller cleanup above any single channel, and each calling function gets a record of the callee's convention at its call site. The `typeinfer` report names conventions and the channel that read them. The module-context and escalate prompts gained a CALLING CONVENTION section. Signature synthesis spells the detected convention into the synthesized signature — `__cdecl`, `__stdcall`, `__fastcall`, `__thiscall`; Microsoft x64 spells none — so the generated FFI binding, and the shim signatures rendered from the same string, call the original with the detected convention instead of the default.

- **Global-state analysis (P13, closes #225, issues #252–#257)** — a new scan records which program globals each function reads and writes: the global's name, the access kind, the statement that carried it, and a confidence band, with a derived per-function purity summary. It persists per binary at `re/analysis/globalstate/{binary}.json` and runs as one of the pre-batch evidence scans. A shared-globals index rolls the records up into one entry per global naming its reader and writer functions. The CLI gained a `globalstate --binary <name> [--show]` report. The module-context and escalate prompts gained a GLOBAL STATE section that spells the target function's own globals and steers the translation to give each global a home in a threaded struct rather than a Rust `static`. The concurrency scan's data-race pairing now consumes the same global readings, so race findings and the global-state document name the same accesses by construction. The translation orderer consumes the persisted index as state-sharing edges: within a priority tier, the unit that first defines a global enters the queue before the units that reuse it, and an empty or missing index leaves the existing dependency order exactly intact. Generated baseline tests now carry the function's persisted globals as expectations, with the typed `GlobalRead`/`GlobalWrite` side-effect kinds and the global name riding the expectation's detail string, so a verification failure reports the expected side effects by named kind instead of an opaque `Other(...)` note; test documents written before the kinds existed still load.

- **Serialization analysis deepening (P11.5, issues #198–#201)** — the `serialize` scan now reads the message-integrity and format story, not just scattered per-call hints. `cross_field_validation` findings report the checksum and length checks a parser runs against its own input. `serialization_format` findings compose a function's byte-swap and bit-pack readings into one ordered layout claim with a `byteorder`-style reader suggestion. `protocol_message` findings identify well-known network magics (IPv4, ARP, IPv6, VLAN) only when corroborated by network-order swaps or cross-field validation — a bare magic sniff stays a plain magic finding. One `endianness_map` finding per scan coalesces the binary's byte-swap calls by width into a wire-order claim: network-order names imply `be`, and direction-neutral builtins claim nothing. All of it rides the persisted JSON, the `serialize` report, and the escalate prompt's SERIALIZATION section.

- **Constant recovery deepening (P10.5, issues #190–#195)** — the `consts` scan reads constants the way the code does. Repeated literals beside a named identifier gain context-derived names (`const SIZE_0x280: u32 = 0x280;`). Composite bitwise masks decompose when every set bit was independently sighted in the body. Per-function bitflag groups that share bits merge transitively into one program-level `flag_family` record suggesting a single `bitflags!` struct. Known protocol and format magics and sentinels (PNG, GIF, JPEG, ZIP, gzip, ELF, PE, Mach-O, `0xDEADBEEF`, `0xCAFEBABE`, …) are recognized by name even when seen exactly once. Color-shaped literals group into one palette finding per binary. And `calxgloss consts` now writes a reviewable Rust source file beside the persisted JSON — `bitflags!` blocks, enums, and named constants rendered from the findings, byte-identical across scans of one program.

- **API detection deepening (P9.5, issues #184–#188)** — `apidetect` findings now carry the API category its library mapping names, using the PAL's vocabulary (`Win32Core`, `DirectX`, `SDL2`, `POSIX`, …), and crate suggestions render with feature flags (`flate2[zlib]`, `image[png]`). A `platform_divergence` finding flags binaries that import both Win32 and POSIX or C-runtime stdio, and suggests cfg-gated translation. `com_interface` findings recognize the COM component model — runtime imports, the IUnknown-shape trio, and interface-decorated names — and suggest a trait per recovered interface. The scan also writes two derived artifacts beside the cached JSON: a Cargo.toml-style dependency manifest at `re/analysis/apidetect/{binary}.toml` (every suggested crate once, features inlined, no versions claimed) and an FFI bindings file at `re/analysis/apidetect/{binary}.rs` declaring only the imports no crate replaces.

- **String context deepening (P8.5, issues #181–#182)** — `stringctx` now spots the language machinery a binary leaves in its strings — whole-string language names, locale codes, and non-ASCII user-facing text — as one `localization` finding per function suggesting a language enum with the localized strings in a table. It also ties strings across call boundaries: a `cross_function` finding lands when one scanned function hands a literal or a resolved `DAT_` string to another function through a call, suggesting the receiving parameter translate as a string type.

- **Control-flow analysis deepening (P7.5, issues #176–#179)** — built on the per-body control-flow graph foundation (#175), `controlflow` now reports `loop` findings — counted, conditional, do-while, and goto-driven loops, with the count and maximum nesting depth per function — and `branch_density` classification (dispatch-table candidate versus sequential scan), and it adds `mutual_recursion` findings, one per call cycle of length 2 or more, derived from the bodies the scan already holds. The recursion reading deepens: self-calls nested in loops flag a depth multiplier, and tail calls spread over lines or nested in a block read as tail calls through the graph.

- **Callback & function-pointer analysis deepening (P6.5, issues #170–#173)** — `callback` now spots the plugin boundary: `LoadLibrary`/`GetProcAddress` or `dlopen`/`dlsym` pairs, plugin entry-point names, and the host API table handed to an entry point, suggesting `Box<dyn Plugin>`. It reconstructs callback `chain` findings across functions — a callback registered in one function and called by name in another, or a table registered and called through. It rebuilds `event_system` architecture — two or more registrations to one name plus a visible dispatch site — suggesting the observer pattern. And it fills real closure contracts into callback suggestions from the persisted type-inference document, so a suggestion reads `Box<dyn Fn(i32) -> bool>` instead of `Box<dyn Fn(...)>`.

- **Concurrency analysis deepening (P5.5, issues #164–#168)** — `sync` now detects thread-local storage — the Win32 `TlsAlloc`/`TlsGetValue` family and the POSIX `pthread_key_*` family — suggesting `thread_local!`; raw futex calls (`futex` and `syscall(SYS_futex, …)`), suggesting `std::sync::Mutex`/`Condvar` instead of transliterated syscalls; `lock_order` conflicts, where two functions acquire the same two locks in opposite orders; and `data_race` pairs, where one function stores into a program global that another reads with no lock either side respects — one lock object held over every access suppresses the claim.

- **Memory lifecycle analysis deepening (P4.5, issues #158–#162)** — the `memory` scan now follows a block across the whole call boundary. `cross_function` findings pair an allocation in one function with a callee's release of the parameter it received. `ownership` findings report blocks handed to a callee or returned whole (`Box<T>`). `leak` findings report allocations never released and never allowed to escape. An `Rc<T>` upgrade lands when a callee stores the pointer it was handed into a global or a struct field. And paired handles spelled with a real type in the body get named `Drop` suggestions (`impl Drop for HANDLE`).

- **Algorithm recognition deepening (P3.5, issues #152–#156)** — the `algorithm` scan now resolves competing claims to one report per algorithm with the strongest evidence, and it gained a configurable minimum-confidence floor. `--patterns <file>` teaches it new control-flow signatures, string signatures, callback contracts, and correlation relationships from one JSON document: the file replaces the built-in sets whole, and entries may carry their own confidence. `cross_function` correlation hints recognize the algorithms living between functions — `divide_and_conquer`, or a `qsort` host whose named comparator actually compares its arguments. The per-function pass runs with bounded concurrency, at most eight decompiles in flight, and the skip-rate breaker still aborts a wrong-program scan.

- **Type inference deepening (P2.5, issues #143–#150)** — the `typeinfer` scan types far more of a program. Types propagate across call boundaries in both directions: a callee's own parameter readings lend types to the bare-identifier arguments at its call sites, and callers' typed arguments, string literals, and known-routine results lend types to the callee's parameters. Locals are typed through assignment chains, and return types are inferred from how callers use the result. C++ mangling is decoded: demangled qualified calls type their arguments, and MSVC-mangled listing symbols yield a calling convention, an argument count and rough types, and a return type even when the function's body never decompiles. Integer widths are bounded by comparisons, bitwise OR/XOR, and compound assignments beside wide constants. `--write-back` applies the scan's surviving hypotheses back into the open program — referenced type names created first, then function prototypes, then local-variable types — never overwriting a slot the program already types concretely, skipping records below `--confidence-floor` (default 70), and ending with an applied/skipped/failed report naming each target and reason.

- **Type database recovery deepening (P1.5, issues #137–#141)** — the `typesdb` scan now recovers the type tree, not just flat records. String-inferred struct candidates link to RTTI-confirmed vtables and take their demangled class names. Candidates split across a hub function merge on shared referencing functions. Struct fields whose type names match recovered types link into nested subtrees. STL/MFC types (`basic_string`/`CString`, `vector`, the `map`/`set` family, smart pointers) are flagged with their family so the translator maps them onto `String`/`Vec`/`BTreeMap` instead of hand-rolling layouts. And `re/analysis/typesdb/{binary}.rs` carries the recovered types as `#[repr(C)]` declarations with explicit padding, regenerated after every scan.

- **All eleven scan engines read through one shared seam (#100–#102)** — the engines' near-identical local copies of the read-source trait are gone; the shared `ScanSource` is re-exported by every engine crate, so the read cache implements it once for all of them.

- **Run-telemetry logs are bounded (#82)** — the token-usage, fault, and prompt-strategy logs keep at most the 10,000 newest entries. Aggregate totals still cover the whole run, while per-attempt detail covers only the retained window.

- **Pseudo-C text scanning now lives in one shared module** — the call-site walking, argument splitting, parenthesis matching, literal skipping, and cast stripping that every evidence crate restated is now one configured implementation, so a scanner fix lands once.

- **The pipeline table was reworked** — rows lay out as fixed aligned columns with a header (Binary, Total, Translated, In progress, Queued, Failed, Tokens, Success, Classification, Actions), long names ellipsize, and one Classification column carries the state (PAL trait, Shim → crate, Full RE, Unclassified). A new `BatchStarted` event marks the binary being prepared as **Working** before any function-level progress exists.

- **The dashboard's binary and category vocabulary has one source (#109)** — the scope panel's categories, the restart dialog's binary list, and the context-tier select now read the backend's names from server responses instead of spelling them by hand.

- **A browser reload keeps the tab you were on** — the active tab is saved on every switch and restored on load, and the Landing-view select is gone.

- **Retry-strategy overrides are a closed set, not a string (#120)** — the forced strategy is now a shared set of names covering the five retry strategies. An unknown label is refused at the request boundary (422), and persisted labels are unchanged.

### Removed

- **Ghidra engine retired — Kuna is the only analysis engine (issue #214, epic X5/#203; ADR-0041 supersedes ADR-0001 and ADR-0007)** — the GhidraMCP HTTP client and the headless-JVM lifecycle it sat on — bootstrap, extension pairing, pid files, orphan reaping, boot budgets, port selection, wrong-program guard — are deleted. Configuration and the CLI stop offering a choice: the `[ghidra]` block, the `analysis.engine` key, the `--engine` flag, and the `GHIDRA_*` and `CALXGLOSS_GHIDRA_*` environment variables are gone, and a stale configuration that still names them arrives as a parse error naming the keys — no compatibility shim. `doctor` drops the Ghidra probes and checks only that the Kuna analysis engine loads the target. The engine failure vocabulary renames `GhidraError` to `EngineError`, the fetch-phase events and phases drop the Ghidra name, and `--refresh-ghidra-cache` becomes `--refresh-cache`. What stays: the scan seam itself, the two-tier read cache (now `CachedScanSource` over `KunaSource`, format v2 so bridge-era documents are never replayed), and the Ghidra-shaped text vocabulary Kuna reproduces.

- **Orphaned prompt templates deleted (issue #87, closes roadmap X2)** — every shipped template now has a live reference.

### Fixed

- **Kuna's function listing no longer hands consumers an ambiguous import name (issue #216)** — the #215 decompile warning came back over a 32-bit MSVC binary: a name with two executable entries — a thunk veneer per referencing object file plus the IAT slot — was listed but refused decompilation and translation, because the engine's name lookup refuses to guess between two executable candidates. The listing now keeps an entry only when the engine's own resolution settles on it, bounded to the names the enumeration spells more than once.

- **Multi-byte characters in decompiled bodies panicked the scanners' byte walks** — a non-ASCII character outside a string literal (a `ﾟ` in a comment) crashed the recursion call-site scan and the `consts` tokenizer by slicing at a non-char boundary. Both now match at the byte level, which cannot panic.

- **`auto` panicked on an explicitly named linker thunk** — a unit refused as a thunk was recorded skipped but also delivered to the per-function completion callback as a codeless success, and the git-commit handlers assumed a success always carries code and unwrapped it, crashing the run mid-batch. Refused units never reach the callback, and the handlers now skip results with no code.

- **Scope controls treated one function as two entries when the binary was cased differently (Fixes #107)** — adds, checks, and removals now share one match rule: binary names match case-insensitively, function names exactly.

- **The live view's "needs calxgloss live" notice was replaced by a generic error (issue #108)** — the client now reads the HTTP status from the error it throws, and the live view branches on the 404, instead of matching a message string the server may overwrite.

- **The LLM I/O view's Clear button cleared only the browser buffer** — a new `POST /api/llm-io/clear` deletes the persisted log and answers how many entries it dropped. If the server refuses, the view says so instead of pretending the history is gone.

- **The output-budget estimate was optimistic for code-heavy prompts** — disassembly-and-template prompts tokenize at ~3.4 characters per token, not ~4, so the EverQuest run's prompts overflowed the context window with a 400 on every retry. The estimate now assumes ~3 characters per token with the same headroom.

- **Empty prompt sections cost tokens** — the templates rendered "nothing available" filler headers and separator rules for every absent section, fourteen filler sections on the escalate prompt alone. Optional sections now render only when they have content, and every render passes through a blank-line normalizer.

- **The scratch PAL crate never compiled, failing every verification** — `//!` module-doc lines in the embedded template are rejected (E0753) inside the `include!` expansion, so every translated function failed on scaffold code the LLM never wrote and the retry loop burned attempts fixing the verifier's own header. The template now uses plain comments, and an existing workspace's stale scaffold fixes itself on the next run.

- **Import thunks no longer go to the LLM** — a built-in root pattern (`^(DelayLoad_|_imp_|thunk_)`) classifies delay-load stubs, IAT symbols, and thunks as roots, so they get a deterministic stub instead of a full translation unit spent on a one-instruction jump.

- **An empty disassembly is now read as "no disassembly"** — the bridge answered 200 with an empty body for functions that own no instructions (thunks and external imports), which the client surfaced as an error and a warning on every such function. It now maps to an empty listing.

- **Commits after Classifying staged nothing** — absolute workspace-joined paths reached the git staging call, which only accepts repo-relative paths, so every classification record commit landed empty. Paths are now normalized to repo-relative form, and commit failures that used to be swallowed now surface.

- **Decompiler lines padded with trailing whitespace panicked the literal scanner** — an index-out-of-bounds on lines ending in spaces. The bounds check now comes first and the lookup answers `None`.

- **A clean start now creates the workspace git repo up front (Fixes #123)** — a fresh folder left the dashboard popping "Not a Git repository" while the run sat silently in the preflight. The repo is initialized at the top of the run, and the preflight prints a visible connecting line.

- **A warm run's activity heartbeat went silent (Fixes #121)** — the pass heartbeat counted only live engine round trips, so once the read cache had warmed, the pipeline row rendered nothing under the Working badge. The heartbeat now counts work items consumed, warm or cold.

- **Review actions can no longer silently disagree with git (Fixes #86)** — fast Accept-then-Send-Back clicks raced on the unit's single action record. Each action re-checks the persisted state before writing and fails with a 409 naming the state that won, and send-back or patch on an already-merged unit is refused outright.

- **A stalled browser tab no longer freezes live updates (Fixes #85)** — one hidden or throttled tab that stopped draining its WebSocket blocked the broadcast loop for every other client and overflowed the event channel. Delivery is now non-blocking, and a client whose buffer fills is disconnected and resyncs.

- **Double patch clicks no longer double the retry (Fixes #84)** — a second "Request Patch" created the same next attempt twice and spawned two retry loops racing on one branch. A patch already in flight answers `patch_already_in_progress` and creates nothing.

- **Accepting a conflicting unit fails honestly (Fixes #83)** — the merge now checks for conflicts before committing anything, names the conflicting files, leaves main and the unit's status untouched, and the accept record says `conflicts:` instead of claiming a merge happened.

- **Run logs survive a crash mid-save (Fixes #81)** — killing the process mid-write could leave a half-written JSON artifact that the next run read as corrupt and overwrote. Every persisted document now lands atomically (temp file plus rename), so a reader always sees the previous or the new document whole.

- **Phantom-clean evidence scans when every decompile failed (Fixes #71)** — a wrong-program scan skipped every function and finished "successfully", persisting an empty record indistinguishable from a clean one. The evidence scans now abort once more than half the listing fails to decompile, naming the counts, and persist nothing.

- **Function-name hints never invent a `.dll` (Fixes #70)** — the call graph's function-to-binary detector appended `.dll` to every extension-less name, so hints from an `.exe` target never resolved. Candidates now resolve against the workspace's classified binaries, and an unmatched candidate resolves to nothing.

- **Dashboard baseline test counts never showed (Fixes #67)** — the baseline scan looked at the wrong directory level and the unit-side lookup cut the key at the wrong segment, so the two sides never joined. Baseline artifacts now attach on the verbatim `{binary}/{function}` identity.

- **Dashboard bounce and graph reshuffle during live runs** — every progress event rebuilt the status cards and re-ran the dependency graph's layout in filesystem order. WebSocket refreshes are now coalesced, cards update in place only when their values change, and graph nodes and edges order deterministically.

- **Crate-replacement classifications read back honestly** — the strategy's tagged-object form broke both readers of the classification records, rendering those binaries "Unclassified" after a restart. Both forms are now read.

- **Empty pipeline table after restarting a live run** — rows were derived only from the current process's event stream, so a restart over prior work showed "No binaries discovered yet". Classifications now load from the persisted `re/classify` artifacts, with live events still taking precedence.

- **Debug builds panicked on char literals in decompiled bodies** — a `']'` literal underflowed the argument splitter's nesting counter. Char literals are now skipped when matching parentheses and splitting arguments, and the counter saturates on malformed input.

- **Stale cached UI assets** — static files were served with no cache headers, so browsers mixed old CSS/JS with new. Responses now carry an ETag with `no-cache` revalidation.

- **Recent activity cycled and claimed "just now"** — units were stamped with the build clock and the list followed filesystem order. Accepted units now carry their commit time, and the list is ordered newest-first.

- **Live progress events applied out of order (issue #65)** — one task per event raced for the progress-state lock, so updates could land reordered or dropped. Events now flow through a single ordered consumer.

- **The retry loop accepted non-compiling first attempts (issue #64)** — success ignored the `compiled` flag, so a first attempt that failed to compile counted as successful and no retry strategy ever ran. Success now requires compilation plus all tests passing.

- **Fast-forward merge logs once (issue #87)** — the double debug line per merge is gone.

### Refactored

- **The pre-batch scan phase fans out (#234, issues #236–#241)** — the eleven evidence scans now run through one shared preamble, so the CLI and web batch paths can no longer drift apart, each scan as an owned job under one phase-scoped heartbeat, with a completion latch ordering the one real dependency: callback detection awaits the type-inference document. The scans run four at a time over the shared scan read cache — measured on a real target: the cold scan phase of a 4,076-function binary went 142.7 s → 113.9 s. Every function is still decompiled exactly once across the whole phase, and the persisted documents are byte-identical to the sequential schedule.

- **Web router table consolidation** — the plain-`serve` and live surfaces are assembled from one shared route table plus a live-only table, so live pipeline endpoints answer only in live mode.

- **Frontend split into ES modules** — the single `app.js` is now one module per view plus shared fetch and format helpers, loaded natively by the browser with no build step.

### Documentation

- **`docs/data_flow.md` now covers every analysis methodology** — the data-flow doc was rewritten to match the shipped pipeline. It names all eleven evidence-scan methodologies plus the call graph, saying what each detects, the Rust shape it suggests, and the prompt section its findings render into, and its batch-flow, progress-event, filesystem-layout, web-endpoint, and retry/escalation sections were corrected.

- **Architecture diagrams audited against the implementation (roadmap X4)** — the README and design-doc diagrams were redrawn to the shipped workspace: the real command surface, the translator's real flow (read cache ▸ evidence warmup ▸ fetch ▸ prompt ▸ translate ▸ verify ▸ retry ▸ commit, with context-tier escalation), every evidence crate named, and unimplemented phases annotated as such.

## [0.2.0] — 2026-10-06

### Added

#### Output & pipeline

- **Crate-based output layout** — `translate` and `batch-translate` now write a Rust crate per DLL: `crates/<dll_stripped>/Cargo.toml`, one `src/<function>.rs` per function, and an auto-generated `mod.rs` that registers every translated function. The DLL or EXE extension is stripped from the crate name (e.g. `EqGame.exe` → crate `EqGame`).
- **Complexity-based prompt selection** — the tool classifies each function by instruction count, branch density, call depth, and API-category diversity. It then sends the function to a Minimal, Standard, Rich, or Detailed prompt, with matching Ghidra context.
- **Failure-informed retry prompts** — when earlier attempts failed, every retry strategy adds a "PREVIOUS ATTEMPT HISTORY" section to the prompt, so the LLM can see and avoid the earlier mistakes.
- **Per-attempt token usage logging** — every LLM call records its token counts to `re/analysis/token_usage.json`. This covers initial, retry, and tier-escalated attempts, each with its DLL, function, attempt, strategy, context tier, and outcome. The batch summary prints a total-tokens line.
- **Experiment logging** — each retry attempt is recorded to `re/analysis/prompt_strategy_log.json` with its category, strategy, and outcome, so aggregate pass/fail statistics can be computed from that file.

#### Context tiers

- **Context tier selection** — five context tiers (`Signature`, `Disassembly`, `WithTests`, `ModuleContext`, `FullModule`) control how much context the LLM receives for one function. The starting tier is chosen automatically from function complexity and API call count. Each tier has its own prompt, from a minimal signature-only prompt up to full-module context with neighboring functions, shared data structures, shim layer source, and PAL trait definitions.
- **Automatic context tier escalation** — after a failed attempt, a retry can step the context tier up one level and rebuild the prompt with the larger context. This works independently of retry-strategy escalation.

#### Fault detection & analysis logging

- **Fault logging** — detected faults are saved to `re/analysis/fault_log.json` with aggregate statistics.
- **Context-window detection** — the tool checks LLM responses against the model limit for truncation markers, and it checks oversized prompts before sending them. Disassembly can be split into chunks for the LLM.
- **Hallucination detection** — generated code is checked against Ghidra symbols and the PAL catalogue. References to APIs that do not exist are logged and emitted as progress events.
- **Infinite-loop detection** — when the same (prompt, output) pair repeats across retries, the run detects it before more tokens are spent on the dead end.
- **Behavior-divergence detection** — code that passes baseline tests but fails generated edge-case inputs is flagged in the retry loop, with confidence scoring and recovery advice.
- **Resource-exhaustion monitoring** — repeated failures and timeouts (OOM, swap thrash, HTTP 429/503/507) are tracked. The retry loop backs off, records faults, and can suggest queueing work or switching models.

#### New analysis crates

Each scan saves its results as a per-binary JSON document under `re/analysis/<name>/<dll>.json`. Every document carries scan provenance shared by all scans (binary name, finish timestamp, duration), and every finding is scored with the shared 0–100 `Confidence` type.

- **`calxgloss-typesdb` — data structure recovery**: recovers named types from the Ghidra Type Manager. It detects vtables — resolving method pointers and following the MSVC RTTI chain to class and base-class names, and flagging COM interfaces — and it infers struct candidates from string literals.
- **`calxgloss-typeinfer` — type inference**: detects C++ `this` pointers from vtable dispatch, narrows parameter types from string-function usage and integer bit patterns, and propagates types from known signatures (`malloc`, `strlen`, `CreateFileW`, …). Competing readings are resolved by confidence.
- **`calxgloss-algorithm` — algorithm recognition**: recognizes algorithm families (sorting, hashing, checksums, compression, …) from control-flow signatures, string markers, and callback contracts (e.g. a `qsort` compare function).
- **`calxgloss-memory` — memory lifecycle / RAII detection**: pairs allocations with releases (suggesting `Box<T>`/`Vec<T>`, or stack allocation for short-lived blocks), handle opens with closes (RAII guard suggestions), and reference-count bumps with drops (`Rc<T>`, narrowed to `Arc<T>` when shared across threads).
- **`calxgloss-sync` — concurrency detection**: pairs lock acquires with releases (`Mutex`/`RwLock`), detects interlocked/atomic calls (`AtomicU32`/`AtomicU64`), and detects thread spawns with or without joins (`std::thread::spawn` vs `tokio::spawn`).
- **`calxgloss-callback` — callback & function-pointer detection**: finds calls through function-pointer arrays, registration→callback pairs, and jump-table dispatches, and suggests `Vec<Box<dyn Fn(...)>>`, `Box<dyn Fn(...)>`, or `match`/dispatch tables.
- **`calxgloss-controlflow` — control-flow pattern recognition**: detects switch-shaped if-else chains, self-recursion (with tail-call detection), and state-machine patterns, and suggests `match`, loops, or `enum State`.
- **`calxgloss-stringctx` — string & configuration context**: classifies strings into nine categories (format strings, paths, error messages, …), maps strings to functions through body parsing and xrefs, and infers argument types from format specifiers.
- **`calxgloss-apidetect` — library & API identification**: identifies linked libraries from the import table and maps them to Rust crates (DirectX 9, SDL2, zlib, PNG, the C runtime, …). For each function it summarizes which APIs the function reaches directly and which through its callees.
- **`calxgloss-consts` — constant & enum recovery**: recovers bitflag groups from bitwise operations, enum candidates from contiguous switch cases, and repeated literals as named constants.
- **`calxgloss-serialize` — endianness & serialization detection**: detects byte-swap calls, bit-packing shift/mask chains, and magic-byte comparisons (PNG, gzip, ZIP), and suggests `byteorder` readers, field masking, or format decoders.

#### `calxgloss-ghidra`

- **New Ghidra bridge capabilities** — the bridge can now page through string, data-type, and data-item listings automatically, look up struct layouts and enum values, read raw memory, and tag functions. It also supports multiple open programs: it can list them and switch which one queries run against.

#### `calxgloss-cli`

- **On-demand analysis commands** — the `typesdb`, `typeinfer`, `algorithm`, `memory`, `sync`, `controlflow`, `callback`, `stringctx`, `apidetect`, `consts`, and `serialize` commands each run their scan against the program open in Ghidra and save the result to the matching `re/analysis/<name>/<dll>.json` cache that the batch pipeline reads. `--show` prints a cached result (counts, confidence, findings) without connecting to Ghidra. `--no-tag` keeps the vtable scan read-only.
- **`auto` subcommand** — checks the project's state and continues the workflow by itself: it scans the target directory for DLLs, runs classification when records are missing, and then batch-translates. Running with no subcommand is the same as `auto`. It supports `--target`, `--dlls`, `--all-functions`, `--classify-only`, and `--skip-git`.
- **`init` subcommand** — creates a `calxgloss.toml` containing a fully commented template of every `[ghidra]` and `[llm]` key.
- **`auto-shim` subcommand** — generates shim layers for all crate-replacement DLLs, in one flow: API mappings (LLM) → source code → tests → verify → persist to `re/shims/<dll>/`, committed to git.
- **`dashboard` subcommand** — builds and renders the review dashboard from git branches and records. It supports `view`, `accept`, `reject`, and `accept-all` (batch acceptance in dependency order), plus a `--follow` mode that keeps watching for changes.
- **`serve` subcommand** — starts the web review UI's HTTP server (port 3000 by default).
- **`live` subcommand** — runs batch translation and the web UI together in one process, streaming progress over a WebSocket.
- **`gc` subcommand** — archives stale unmerged translation branches to `refs/archive/…` instead of deleting them. It supports `--days` and `--dry-run`.
- **Config-driven directories** — `target_dir` and `workspace` can be set in `calxgloss.toml` or overridden by the global `--target-dir` / `--workspace` flags. `live` and `serve` use the current directory unless explicitly overridden.
- **Incremental git commits during batch translation** — each function is committed and merged as soon as it succeeds, instead of leaving all git work to the end of the batch.
- **`classify` generates shim layer suggestions** — for crate-replacement DLLs, `classify` saves complexity estimates as shim suggestions to `re/shims/suggestions.json`.

#### Git & review workflow

- **Review records** — accepting a branch writes an acceptance record to `re/accepts/`. Sending it back writes a rejection record to `re/rejections/`. Archiving renames a stale branch to `refs/archive/…` so it stays reachable.
- **Shim-layer dependency enforcement on branch creation** — branch creation can check that the required shim layers (e.g. `d3d9.dll` → `re/shim/wgpu`) are already merged. It runs in one of three modes: `Skip`, `Warn`, or `Enforce`.
- **Dependency graph** — the tool builds a graph (a DAG) of DLL classifications → shim layers → function translations from classification and call-graph data. It saves the graph to `re/analysis/dependency_graph.json` and orders it topologically, level by level, for batch operations.
- **Shim layer generation** — the LLM generates the API mappings. Shim source code (complete or skeletal) and per-mapping tests with mock call recorders are generated from the mapping table, and each shim layer is verified in a sandboxed Cargo project.

#### Web review UI

- **Axum API server** (`server` feature) — endpoints for the dashboard, unit detail, dependency graph, dependency-sorted queue, line-by-line diff, Ghidra context, and health checks, plus accept / send-back / patch review actions that run through git and the translation pipeline. A patch request starts a retry translation.
- **WebSocket progress streaming** — pipeline milestones, per-attempt status, and full LLM request/response events stream to the UI; a live "LLM I/O" tab shows the log.
- **Dependency-sorted review queue** — the queue endpoints and the dashboard report units in dependency order, with queue metadata and position. `Blocked` units are flagged.
- **Diff & Ghidra context viewers** — a tabbed detail panel with line-by-line highlighted diffs against `main`, and decompiler/disassembly context read from on-disk analysis artifacts.
- **Interactive dependency graph** — layered layout with Bézier edges, hover tooltips, click-to-select that highlights the node's neighbors, click-to-detail, status dots, fit-to-view, wheel zoom toward the cursor, and keyboard shortcuts.
- **Live progress panel** — per-DLL classification/strategy, in-progress translation with a progress bar, and batch completion counts. A completed function marks its unit `Complete` in real time.
- **Stale branch cleanup** — a "Stale Branches" dashboard card and a "Branch Cleanup" view list unmerged branches past the staleness threshold and archive them from the UI.

#### `calxgloss-types`

- **Review dashboard data model** — work units, review statuses, the dependency graph, status counts, and review actions are now one set of records shared by the reports, web, and CLI, replacing the duplicate scaffolding in `calxgloss-web`.
- **Dependency-ordered queueing** — units carry a processing level (classification → shim → PAL → test → function → integration → fix). The dependency graph sorts them topologically, breaking ties by level, and the dashboard automatically blocks units whose dependencies are in a failing state.

### Fixed

- **Wrapped decompiler signatures parse** — Ghidra sometimes writes one function signature across several lines, and those lines failed to parse. Every scan that reads the whole function listing silently skipped those functions — about 41 of eqmain.dll's 4,358. Signature lines are now joined until the parameter list or body begins. Fixes #54.
- **Dashboard dependency edges (issue #10)** — the dashboard builder now records the shim→function dependency edge that the branch-creation policy already enforces, so a sent-back shim cascades `Blocked` to everything translating on top of it. - **Patch records were never found** — the patch-record reader walked the wrong tree depth, so it never found records at `re/patches/{dll}/{function}/vN.json`, and `PendingReview` was unreachable in built dashboards. The walk depth is corrected.
- **Review actions 500'd on slashed unit ids** — accept, send-back, and patch requests failed when writing the audit trail for unit ids containing `/`, because the nested parent directories under `re/actions/` were not created. They are now created.
- **Default allocator names missed Ghidra's underscore-form `operator_new`/`operator_delete`** — the live 6.x decompiler writes the underscore form in function bodies, so whole-name matching never fired and allocation findings were missed. The default sets now carry both spellings. Fixes #6.

- **Web server panicked at startup (Axum 0.8)** — the routers used the legacy `:id` capture syntax, which Axum 0.8 rejects at startup. All routes now use the `{id}` syntax.
- **Static file serving** — JS and CSS returned 404: assets resolved against the process CWD instead of the crate directory, and the fallback handler was set up wrong. Both are fixed.
- **Live units 404'd in the unit detail endpoint** — a function still translating in this run had no stored unit to look up. The endpoint now consults the live progress state and creates a synthetic in-progress unit.
- **LLM request/response log rendered HTML-entity-encoded** — content now renders as raw text with minimal escaping, so JSON and code display correctly.
- **Unit detail error handler crashed** — when the detail view failed, its error handler could not reference the code body it meant to report, because the declaration was inside the `try/catch`. The declaration moved outside it.

- **Trims leading/trailing whitespace** from disassembly and decompiler output before sending to the LLM, keeping prompts cleaner and avoiding wasted tokens.

## [0.1.0] — 2025-09-27

### Added

#### `calxgloss-translator`
- **Batch translation** (`batch-translate` CLI subcommand) — translates multiple functions from a single DLL in one invocation. It enumerates all exported functions with `--all-functions` or takes a comma-separated list with `--functions`. Every function gets a pass/fail report, and the summary shows success and failure counts with the pass rate. `--skip-git` runs the batch without touching git. Each successful function is automatically committed and merged to a git branch.
- **Full translation pipeline** — an end-to-end workflow: GhidraMCP → analysis → test generation → LLM → Rust code. It also translates directly from pre-collected data and estimates parameters from decompiler output.
- **Retry logic** — on failure, the translator escalates its retry strategy (CompileFix / TestFix / Escalate), with dedicated compile-fix and test-fix prompts.

#### `calxgloss-ghidra`
- **GhidraMCP HTTP client** — keeps a session against the GhidraMCP bridge and answers DLL queries (list, info, imports, exports) and function queries (disassembly, decompiler output, call graph, full analysis), with tracing logs throughout.

#### `calxgloss-llm`
- **Local LLM client** (Ollama/vLLM compatible) — sends non-streaming and SSE streaming completions through the OpenAI-compatible `chat/completions` API, strips code fences from replies, and carries tracing logs.

#### `calxgloss-prompts`
- **Prompt templates built with the Askama template engine** — translation prompts covering disassembly, decompiler output, Windows API mappings, and baseline tests, plus compile-fix and test-fix prompts.

#### `calxgloss-pal`
- **Platform abstraction layer** with a full Windows API → Rust equivalent mapping table: 100+ mappings across 10 categories (Win32 Core, GDI, DirectX, Win32 GUI, Audio, COM, Win32 Networking, Win32 Registry, VB6 Runtime).

#### `calxgloss-analysis`
- **DLL classification, call graph analysis, and Windows API tagging** — classification heuristics with lookup tables for 70+ Windows OS DLLs, 15 Microsoft SDK DLLs (→ wgpu/tiny-skia/skrifa), and 40 known third-party DLLs (→ fmod-rs/cpal/mlua/pyo3/flate2/vb6runtime etc.). A classified DLL takes one of the `PalMapping` / `CrateReplacement` / `ReverseEngineer` strategies. The analysis also scans disassembly for dynamically-loaded APIs.

#### `calxgloss-testgen`
- **Test generation** — generates FFI bindings with comprehensive Windows type parsing (60+ type mappings, calling conventions, pointer handling). Test inputs are generated with signature-based and disassembly-driven edge case detection. A baseline runner compiles and runs the tests in a temporary Cargo project, and baseline results save/load as JSON at `re/baseline/{dll}/{function}/baseline.json`.

#### `calxgloss-verify`
- **Sandboxed verification** — scaffolds a temporary Cargo project, runs `cargo check`, and verifies behavior against baseline tests. It generates the test harness and parses `cargo test` output, and provides PAL stub types for graphics, audio, filesystem, window, and thread abstractions.

#### `calxgloss-git`
- **Git automation for the translation workflow** — names branches `re/{dll}/{function}v{N}`, performs fast-forward and 3-way merges, writes patch record JSON files for failed translations, and provides branch, commit, merge, and revert operations.

#### `calxgloss-reports`
- **Terminal report formatting** — colored ANSI output for translation, verification, and classification reports, with pass-rate color-coding and batch summaries that mark each function with a checkmark or cross.

#### `calxgloss-web`
- **Web UI data models and an axum API router scaffold** behind the `server` feature flag, including a dependency-sorted review queue with status counts.

#### `calxgloss` (meta-lib)
- **Meta-lib** re-exporting all workspace crates.

#### `calxgloss-config`
- **Configuration crate** — loads settings from file, environment, and flags in that precedence order, validates each section, exposes typed settings, and reports the paths it searched when a value is missing.

#### `calxgloss-types`
- **Shared data structures**, organized by module: DLL analysis, function metadata, test cases, translation, verification, and Git automation.

#### `calxgloss-cli`
- **Full CLI binary** — `clap`-based `classify`, `translate`, and `verify` subcommands run the full pipeline (Ghidra → analysis → test generation → LLM prompt → code → write → verify → git branch/commit/merge → report), with configurable retries, LLM config, and `tracing-subscriber` logging.

#### Infrastructure
- **Project scaffolding** — 14 workspace crates and a workspace-root `Cargo.toml` with shared dependencies.
